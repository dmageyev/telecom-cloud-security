1. Три стани даних та їх захист

Кожні дані в системі існують в одному з трьох станів, і для кожного стану існують специфічні механізми захисту.

1.1 Дані в спокої (Data at Rest)

Визначення: Дані, що зберігаються на фізичних або логічних носіях і наразі не передаються.

Приклади: файли на дисках, записи в БД, архіви, резервні копії, snapshots.

Механізми захисту: шифрування дисків, шифрування на рівні файлів або об'єктів, управління ключами (KMS, CloudHSM).

1.2 Дані у русі (Data in Transit)

Визначення: Дані, що передаються мережею між компонентами, сервісами або кінцевими точками.

Механізми захисту: TLS/SSL, VPN, HTTPS, mTLS (Mutual TLS).

Ризики без захисту: man-in-the-middle атаки, прослуховування трафіку, replay attacks.

1.3 Дані у використанні (Data in Use)

Визначення: Дані, що активно обробляються процесором або завантажені в оперативну пам'ять.

Механізми захисту: Confidential Computing (TEE), AWS Nitro Enclaves, Intel SGX, AMD SEV.

💡 Тріада CIA: Конфіденційність (шифрування), Цілісність (хешування/підписи), Доступність (резервування).

2. Симетрична криптографія

Симетрична криптографія використовує один і той самий ключ для шифрування та дешифрування.

2.1 AES (Advanced Encryption Standard)

AES — міжнародний стандарт симетричного шифрування (NIST FIPS 197, 2001). Блоковий шифр з розміром блоку 128 біт, ключі 128/192/256 біт.

2.2 Режими роботи AES

РежимОсобливостіЗастосування
AES-GCMШифрування + автентифікація (AEAD)AWS KMS, TLS 1.3 ✅ Рекомендований
AES-CBCБлоковий, потребує paddingСтарі реалізації TLS 1.2
AES-CTRПотоковий режим, паралелізуєтьсяDisk encryption
DES/3DESЗастарілий стандарт❌ Заборонено
⚠️ Проблема розповсюдження ключів: N сторін потребують N×(N-1)/2 унікальних ключів. Для 100 сторін — 4950 ключів. Вирішується асиметричною криптографією (ECDH).

3. Асиметрична криптографія

Використовує пару ключів: публічний (відкритий) та приватний (закритий). Публічний ключ можна поширювати відкрито; приватний — ніколи не передається.

3.1 Алгоритми

АлгоритмОсноваЗастосуванняСтатус
RSA-2048/4096Факторизація чиселTLS, підписДопустимо
ECDSA/ECDH (P-256)Еліптичні кривіTLS 1.3, підпис✅ Рекомендовано
Ed25519Edwards curvesSSH, JWT✅ Найсучасніший

3.2 Алгоритм Діффі-Геллмана (ECDH)

Дозволяє двом сторонам виробити спільний секрет через незахищений канал без передачі самого секрету. ECDH (Elliptic Curve DH) — ефективніша версія на еліптичних кривих, що використовується в TLS 1.3 для Perfect Forward Secrecy.

💡 Perfect Forward Secrecy (PFS): Кожна TLS-сесія використовує ефемерні ECDH-ключі. Навіть якщо довгостроковий приватний ключ сервера скомпрометовано, раніше захоплений трафік не може бути розшифрований.

4. Хешування та цілісність даних

4.1 Властивості криптографічних хеш-функцій

  • Детермінованість: однакові вхідні дані → однаковий хеш
  • Необоротність: з хешу практично неможливо відновити вхідні дані
  • Лавинний ефект: 1 біт зміни вхідних даних → ~50% бітів хешу змінюються
  • Стійкість до колізій: практично неможливо знайти два різних входи з однаковим хешем

4.2 HMAC — автентифікований хеш

HMAC (Hash-based MAC) поєднує хешування з симетричним ключем, гарантуючи і цілісність, і автентичність.

AWS SigV4: кожен API-запит до AWS підписується HMAC-SHA256 з включенням timestamp, що запобігає replay-атакам.

5. Конвертне шифрування (Envelope Encryption)

Envelope Encryption — дворівнева схема шифрування, що вирішує проблему ефективного шифрування великих обсягів даних при централізованому управлінні ключами.

5.1 Чому не шифрувати KMS-ключем напряму?

  • KMS обмежує розмір даних: максимум 4 КБ
  • Кожен виклик KMS API платний (~$0.03/10K викликів)
  • Мережева затримка: 5-20 мс на виклик

5.2 Схема шифрування

--- ШИФРУВАННЯ ---
1. KMS.GenerateDataKey(CMK) → (PlaintextDEK, EncryptedDEK)
2. AES_256_GCM.Encrypt(PlaintextDEK, PlaintextData) → CiphertextData
3. Видалити PlaintextDEK з пам'яті!
4. Зберегти: CiphertextData + EncryptedDEK

--- ДЕШИФРУВАННЯ ---
1. KMS.Decrypt(CMK, EncryptedDEK) → PlaintextDEK
2. AES_256_GCM.Decrypt(PlaintextDEK, CiphertextData) → PlaintextData
3. Видалити PlaintextDEK з пам'яті!
✅ Переваги: Дані будь-якого розміру шифруються локально (швидко). KMS викликається лише 1 раз на дешифрування. Цей підхід автоматично використовується в S3 SSE-KMS, EBS, RDS.

6.2 Ротація ключів

При ротації AWS генерує новий матеріал ключа, але Key ID залишається незмінним. Старий матеріал зберігається для дешифрування раніше зашифрованих даних. Не потрібно перешифровувати існуючі дані.

6.3 KMS Multi-Region Keys

Один логічний ключ, матеріал якого реплікується в кілька регіонів. Дані, зашифровані в одному регіоні, розшифровуються в будь-якому регіоні з реплікою — без необхідності перешифрування.

6.4 Key Policy — приклад

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "Enable IAM User Permissions",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::123456789012:root" },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Sid": "Allow App to use the key for S3 only",
      "Effect": "Allow",

      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "s3.eu-west-1.amazonaws.com"

      }
    }

  • Compliance mode: ніхто (навіть root) не може видалити до закінчення retention period

8. AWS Encryption SDK

Клієнтська бібліотека (Python, Java, JavaScript, Go, C) для реалізації envelope encryption на стороні клієнта.

import aws_encryption_sdk
from aws_encryption_sdk.identifiers import CommitmentPolicy

client = aws_encryption_sdk.EncryptionSDKClient(
    commitment_policy=CommitmentPolicy.REQUIRE_ENCRYPT_REQUIRE_DECRYPT
)
kms_key_provider = aws_encryption_sdk.StrictAwsKmsMasterKeyProvider(
    key_ids=['arn:aws:kms:eu-west-1:123:key/abc']
)
ciphertext, header = client.encrypt(
    source=b'sensitive CDR data',
    key_provider=kms_key_provider
)
💡 Key Commitment: Гарантує, що зашифровані дані можуть бути розшифровані лише тим ключем, яким були зашифровані. Захист від key confusion attacks.

9. Шифрування EBS та RDS

EBS Encryption

  • Шифрується весь том, snapshots та копії
  • Прозоро для EC2 (без впливу на продуктивність)
  • Можна увімкнути за замовчуванням у регіоні
  • Не можна зашифрувати існуючий том — потрібен snapshot → зашифрувати → новий том

RDS Encryption

  • Вмикається при створенні, не може бути змінено пізніше
  • Шифруються: storage, backups, snapshots, read replicas

Примусовий TLS для RDS

-- PostgreSQL (Parameter Group):
rds.force_ssl = 1

-- MySQL/Aurora (Parameter Group):
require_secure_transport = ON

11. Шифрування Lambda та середовищ виконання

Захист змінних середовища Lambda

  • За замовчуванням: env vars зашифровані AWS Managed Key
  • Рекомендовано: CMK для додаткового контролю
  • Найкращий підхід: не зберігати секрети в env vars — використовувати Secrets Manager

Патерн: Lambda + Secrets Manager з кешуванням

from functools import lru_cache
import boto3, json

@lru_cache(maxsize=1)
def get_secret(secret_name: str) -> dict:
    client = boto3.client('secretsmanager')
    return json.loads(
        client.get_secret_value(SecretId=secret_name)['SecretString']
    )

def handler(event, context):
    config = get_secret('prod/telecom/rds')  # кешується в execution env
    # use config['host'], config['password']

AWS Lambda Code Signing

Підпис deployment пакету через AWS Signer. Lambda перевіряє підпис перед виконанням — захист від розгортання скомпрометованого коду.

12. AWS Nitro Enclaves — Confidential Computing

Nitro Enclaves — ізольоване обчислювальне середовище всередині EC2 без збереженого сховища, без інтерактивного доступу, без зовнішньої мережі. Базується на AWS Nitro Hypervisor.

Механізм Attestation

Кожен Enclave генерує криптографічний атестаційний документ (signed by AWS Nitro Attestation PKI), що містить PCR-вимірювання образу. AWS KMS може видати ключ лише після верифікації цього документу — гарантія незміненості коду.

Сценарії для телекому

  • Обробка MSISDN, IMSI, CDR без доступу для операторів AWS
  • Генерація ключів SIM/eSIM та аутентифікаційних векторів 5G (SQN, AK, IK, CK, RAND)
  • Обробка платіжних транзакцій без витоку PAN

14. AWS Certificate Manager (ACM)

Безкоштовні публічні TLS-сертифікати з автоматичним оновленням. Приватний ключ зберігається в ACM — не можна завантажити.

Підтримувані ресурси для автоматичного розгортання

ALB, NLB, CloudFront, API Gateway, App Runner, AppSync, Elastic Beanstalk, CloudFormation.

ACM Private CA

Власний ієрархічний PKI для внутрішніх сертифікатів (мікросервіси, VPN, IoT-пристрої, mTLS). Вартість: ~$400/міс за CA.

16. AWS CloudHSM

Виділений HSM-пристрій у вашій VPC. FIPS 140-2 Level 3. Лише ви маєте доступ до ключів — AWS не має. Підтримує PKCS#11, JCE (Java), OpenSSL.

Коли вибирати CloudHSM замість KMS

  • Регуляторні вимоги повного контролю над ключовим матеріалом
  • Власна PKI-інфраструктура оператора зв'язку
  • Підписання кореневих сертифікатів (Root CA offline)
  • Захист ключів SIM/eSIM (Ki, OPc)
  • PCI DSS HSM для платіжних терміналів

18. Amazon Macie

ML-сервіс для автоматичного виявлення та класифікації чутливих даних в Amazon S3.

Типи знахідок

  • SensitiveData:S3Object/Personal — ПІБ, email, телефони, паспортні дані

20. Zero Trust та криптографія

Принципи Zero Trust: "Ніколи не довіряй, завжди перевіряй." Кожне з'єднання та операція аутентифікується криптографічно — незалежно від того, чи запит надходить з корпоративної мережі чи Інтернету.

Криптографічні основи Zero Trust

  • mTLS — взаємна аутентифікація кожного з'єднання між сервісами
  • SPIFFE/SPIRE — X.509 SVID-сертифікати для workload identity
  • JWT/OIDC — підписані токени для API-авторизації
  • Короткоживучі сертифікати — автоматична ротація через ACM Private CA

5G Zero Trust

3GPP TS 33.501: кожна Network Function аутентифікується за сертифікатом X.509 при взаємодії через HTTP/2 SBI. SEPP виконує міжоператорський захист (N32 інтерфейс) з mTLS.

Архітектура рівнів захисту

  • Control Plane: TLS 1.3 + mTLS для SIP, Diameter, HTTP/2 (5G SBI)
  • User Plane: SRTP для голосу, DTLS для WebRTC, IPsec для GTP-тунелів
  • Зберігання (CDR/білінг): S3 SSE-KMS + Object Lock, RDS шифрування, Macie
  • Ключі: CloudHSM для PKI оператора, KMS CMK для хмарних ресурсів

25. Defence in Depth — Ешелонована оборона

Жоден один механізм захисту не є достатнім. Кожен рівень захищає від різних векторів атак і є незалежним від інших.

РівеньAWS-механізмиЗахищає від
ІдентичністьIAM, MFA, SCP, IAM Roles AnywhereНесанкціонованого доступу
МережаVPC, Security Groups, NACLs, PrivateLink, WAFМережевих атак
ШифруванняKMS, SSE, TLS/mTLS, ACM, CloudHSMВитоку даних при скомпрометованому доступі
ЗастосунокВалідація вхідних даних, parameterized queriesInjection, logic flaws
ВиявленняGuardDuty, Macie, CloudTrail, Config, Security HubАктивних атак та невідповідностей
ВідновленняAWS Backup, Multi-region DR, VersioningRansomware, data loss
🎯 Золоте правило: Шифруйте все за замовчуванням, керуйте ключами через KMS, зберігайте секрети в Secrets Manager, автоматизуйте через IaC, перевіряйте відповідність через Config та Security Hub.
