Три стани даних та їх захист

💾 Дані в спокої (at rest)

Збережені на носіях: диски, бази даних, архіви

Захист: шифрування дисків, БД, об'єктних сховищ

🔄 Дані у русі (in transit)

Передаються мережею між системами або компонентами

Захист: TLS/SSL, VPN, HTTPS, mTLS

⚙️ Дані у використанні (in use)

Обробляються в пам'яті (RAM) або CPU

Захист: Confidential Computing, AWS Nitro Enclaves

🎯 Мета захисту

  • Конфіденційність — лише авторизовані можуть читати
  • Цілісність — дані не змінено несанкціоновано
  • Доступність — дані доступні, коли потрібно

Симетрична криптографія

Принцип роботи

Один і той самий ключ використовується для шифрування і дешифрування

Алгоритми

  • AES-128/256 Advanced Encryption Standard — стандарт для захисту даних
  • ChaCha20 Сучасний потоковий шифр
  • DES/3DES Застарілі, не рекомендуються

Режими роботи AES

  • AES-GCM — шифрування + автентифікація (AWS KMS)
  • AES-CBC — блоковий, потребує padding
  • AES-CTR — потоковий режим

Переваги та недоліки

✅ Переваги
  • Висока швидкість шифрування
  • Ефективний для великих обсягів даних
  • Апаратна підтримка (AES-NI в CPU)
⚠️ Недоліки
  • Проблема розповсюдження ключів
  • N сторін → N*(N-1)/2 ключів
  • Безпечний обмін ключем — складне завдання

AWS KMS використовує AES-256-GCM для шифрування даних

Асиметрична криптографія

Принцип роботи

Відкритий ключ (public key) — для шифрування або перевірки підпису

Закритий ключ (private key) — для дешифрування або підпису

Алгоритми

  • RSA-2048/4096 Класичний алгоритм, сертифікати TLS
  • ECDSA/ECDH Еліптичні криві — компактніші ключі
  • Ed25519 Сучасний, швидкий, безпечний

Конвертне шифрування (Envelope Encryption)

Чому не шифрувати KMS-ключем напряму?

  • KMS обмежує розмір даних (max 4 КБ)
  • Кожен виклик KMS API — платний і повільний
  • Величезні файли неможливо передати в KMS

Рішення: дворівневе шифрування

  1. Генерується Data Key (DEK) — симетричний AES-ключ
  2. Дані шифруються DEK (локально, швидко)
  3. DEK шифрується Key Encryption Key (KEK) в KMS
  4. Зашифровані дані + зашифрований DEK зберігаються разом

Схема роботи

🔒 Шифрування:

Plaintext Data → зашифровано DEK → Ciphertext

DEK → зашифровано KMS CMK → Encrypted DEK

🔓 Дешифрування:

Encrypted DEK → KMS розшифровує → DEK

Ciphertext → розшифровано DEK → Plaintext Data

💡 Цей підхід використовується в S3, EBS, RDS та інших AWS-сервісах автоматично

AWS Key Management Service (KMS)

Що таке AWS KMS?

  • Централізований сервіс управління ключами шифрування
  • Підтримує симетричні та асиметричні ключі
  • Інтегрований з >100 сервісами AWS
  • Автоматична ротація ключів
  • FIPS 140-2 Level 3 HSM-підтримка
  • Повний аудит через CloudTrail

Типи ключів KMS (KMS Keys)

  • Customer Managed Key — ви створюєте та керуєте
  • AWS Managed Key — AWS керує, ви не маєте доступу до матеріалу
  • AWS Owned Key — лише AWS, безкоштовно, приховано

KMS — Операції та керування доступом

Основні операції KMS API

  • GenerateDataKey — генерація DEK (plaintext + encrypted)
  • GenerateDataKeyWithoutPlaintext — тільки encrypted DEK
  • Encrypt — зашифрувати до 4 КБ
  • Decrypt — розшифрувати
  • Sign / Verify — цифровий підпис
  • ReEncrypt — перешифрувати під новий ключ

Ротація ключів

При ротації: новий матеріал ключа для нових шифрувань. Старий матеріал зберігається для дешифрування раніше зашифрованих даних.

Key Policy — контроль доступу до ключа

{
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123:root"
      },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123:role/AppRole"
      },
      "Action": [
        "kms:Decrypt",
        "kms:GenerateDataKey"
      ],
      "Resource": "*"
    }
  ]
}

Шифрування даних у Amazon S3

Серверне шифрування (SSE)

SSE-S3

  • AWS керує ключами повністю
  • AES-256, включений за замовчуванням
  • Безкоштовно, без видимості ключів

SSE-KMS

  • KMS-ключ (AWS Managed або CMK)
  • Аудит через CloudTrail
  • Крос-акаунт підтримка, додаткова вартість API

SSE-C

  • Клієнт надає власний ключ при кожному запиті
  • AWS не зберігає ключ

Клієнтське шифрування (CSE)

  • Дані шифруються до відправки в S3
  • AWS ніколи не бачить дані в plaintext
  • Потребує AWS Encryption SDK або власної реалізації
  • Максимальний контроль

Додаткові механізми захисту S3

  • Versioning — захист від перезапису
  • MFA Delete — MFA для видалення версій
  • Object Lock — WORM-захист (write once, read many)
  • Block Public Access — заборона публічного доступу
  • S3 Replication — резервування в інших регіонах

Шифрування EBS та RDS

Amazon EBS Encryption

  • Шифрується весь том (boot volume, data volumes)
  • Використовує AES-256 через KMS
  • Прозоро для EC2 (без впливу на продуктивність)
  • Шифруються також snapshot та копії
  • Можна увімкнути шифрування за замовчуванням в регіоні

⚠️ Незашифрований том не можна зашифрувати напряму. Спосіб: зробити snapshot → зашифрувати snapshot → створити новий том.

Amazon RDS Encryption

  • Шифрування вмикається при створенні БД
  • Шифруються: storage, automated backups, snapshots, read replicas
  • Використовує KMS CMK
  • Підтримується всіма рушіями: MySQL, PostgreSQL, Oracle, MSSQL, Aurora

Шифрування in-transit для RDS

Примусовий SSL/TLS через параметри БД:

rds.force_ssl = 1 (PostgreSQL)

require_secure_transport = ON (MySQL)

Захист даних у русі: TLS/SSL

TLS Handshake (спрощено)

  1. ClientHello — підтримувані cipher suites, версії
  2. ServerHello — обраний cipher suite + сертифікат
  3. Key Exchange — ECDH для спільного секрету
  4. Finished — підтвердження шифрованого каналу
  5. Дані передаються зашифровано (AES-GCM)

Mutual TLS (mTLS)

Обидві сторони (клієнт і сервер) пред'являють сертифікати

  • Критично для API між мікросервісами
  • Використовується в 5G (мережа оператора)
  • AWS App Mesh, API Gateway підтримують mTLS

AWS-сервіси що забезпечують TLS

  • ALB / NLB — termination TLS на балансувальнику
  • CloudFront — TLS до кінцевих користувачів
  • API Gateway — TLS для REST/HTTP API
  • ACM — безкоштовні сертифікати

AWS Certificate Manager (ACM)

Що надає ACM?

  • Безкоштовні публічні SSL/TLS-сертифікати
  • Автоматичне оновлення (без ручного втручання)
  • Інтеграція з ALB, CloudFront, API Gateway, AppRunner
  • Підтримка wildcard-сертифікатів (*.example.com)
  • DNS або Email-валідація домену

ACM Private CA

Власний Центр Сертифікації (CA) для внутрішніх сертифікатів:

  • Для внутрішніх мікросервісів, VPN, mTLS
  • Інтеграція з IoT (телеком-пристрої)
  • Вартість: ~$400/міс за CA

Типи сертифікатів

AWS Secrets Manager

Призначення

  • Зберігання та управління секретами (паролі, ключі API, рядки з'єднання)
  • Автоматична ротація секретів
  • Шифрування через KMS
  • Аудит доступу через CloudTrail
  • Fine-grained IAM-контроль

Автоматична ротація

  1. Lambda-функція генерує новий секрет
  2. Оновлює значення в цільовому сервісі (наприклад RDS)
  3. Тестує новий секрет
  4. Встановлює як активний

Вбудована підтримка ротації для RDS, Redshift, DocumentDB

Приклад: отримання секрету

import boto3, json

client = boto3.client(
    'secretsmanager',
    region_name='eu-west-1'
)

response = client.get_secret_value(
    SecretId='prod/telecom/db-password'
)

secret = json.loads(
    response['SecretString']
)
db_password = secret['password']

💡 Ніколи не зберігайте секрети у коді, env-файлах або git-репозиторіях

AWS CloudHSM

Що таке HSM?

Hardware Security Module — спеціалізований фізичний пристрій для безпечного зберігання та використання криптографічних ключів

AWS CloudHSM

  • Виділений HSM-пристрій у вашій VPC
  • FIPS 140-2 Level 3 сертифікований
  • Лише ви маєте доступ до ключів (не AWS)
  • Підтримує PKCS#11, JCE, OpenSSL
  • Кластер для HA (мін. 2 HSM)

Вартість: ~$1.45/год за HSM (~$1050/міс)

Класифікація даних та модель відповідальності

Рівні класифікації даних

🔴 Критичні / Таємні

Ключі шифрування, паролі адміністраторів, PII, фінансові дані

🟡 Конфіденційні

Внутрішня документація, конфіги мережі, метадані клієнтів

🟢 Публічні / Внутрішні

Публічна документація, загальна конфігурація

Модель спільної відповідальності

AWS відповідає за:
  • Фізичну безпеку дата-центрів
  • Шифрування даних між зонами/регіонами
  • Безпеку інфраструктури KMS/HSM
Ви відповідаєте за:
  • Увімкнення шифрування для ваших ресурсів
  • Управління ключами (ротація, доступ)
  • Класифікацію та маркування даних
  • Відповідність регуляторним вимогам

Amazon Macie — виявлення чутливих даних

Що таке Amazon Macie?

  • ML-сервіс для виявлення та захисту чутливих даних в S3
  • Автоматично знаходить PII, фінансові дані, облікові дані
  • Оцінює ризики безпеки: публічні бакети, незашифровані дані
  • Сповіщення через EventBridge

Типи знайдених даних

  • PII Імена, Email, номери телефонів
  • Credentials AWS-ключі, паролі у файлах
  • Financial Номери кредитних карт, IBAN
  • Health Медичні записи (HIPAA)

Типові сценарії в телекомі

📋 Аудит S3 бакетів на наявність:

  • MSISDN (номери абонентів)
  • IMSI / IMEI пристроїв
  • CDR (Call Detail Records)
  • Особисті дані клієнтів (GDPR)
  • Незашифрованих конфігураційних файлів

Macie допомагає відповідати вимогам GDPR, PCI DSS, HIPAA

Захист даних у телекомунікаційних системах

Специфічні вимоги телекому

  • GDPR/CCPA — захист персональних даних абонентів
  • CALEA — законний перехват комунікацій (LI)
  • 3GPP TS 33.501 — безпека 5G (шифрування сигналізації)
  • GSMA FS.16 — безпека хмарних телеком-систем
  • NIS2 — захист критичної телеком-інфраструктури

Чутливі категорії даних

  • CDR / xDR (деталі дзвінків та сесій)
  • Ідентифікатори абонентів (MSISDN, IMSI)
  • Геолокаційні дані
  • Контент повідомлень (якщо зберігається)

Архітектура захисту телеком-даних в AWS

Рівень сигналізації (Control Plane)

TLS 1.3 + mTLS для SIP, Diameter, HTTP/2 (5G SBI)

Рівень даних (User Plane)

SRTP для голосу, DTLS для WebRTC, IPsec для GTP-тунелів

Зберігання (CDR, білінг)

S3 SSE-KMS + Object Lock, RDS шифрування, Macie-аудит

Управління ключами

CloudHSM для PKI оператора, KMS CMK для хмарних ресурсів

Перевірка відповідності шифрування: Config & Security Hub

AWS Config — правила шифрування

  • s3-bucket-server-side-encryption-enabled
  • encrypted-volumes (EBS)
  • rds-storage-encrypted
  • kms-cmk-not-scheduled-for-deletion
  • acm-certificate-expiration-check

Config відслідковує зміни конфігурацій та виявляє ресурси, що не відповідають політиці шифрування

AWS Security Hub — стандарти

AWS Foundational Security Best Practices

  • KMS.1: CMK rotation enabled
  • S3.4: S3 encryption enabled
  • EC2.3: EBS volumes encrypted
  • RDS.3: RDS instances encrypted

PCI DSS / CIS AWS Benchmark

Перевіряє відповідність платіжних систем та загальних вимог безпеки хмарного середовища

Кращі практики захисту даних в AWS

🔑 Управління ключами

  • Використовуйте Customer Managed Keys (CMK) для чутливих даних
  • Увімкніть автоматичну ротацію ключів (1 рік)
  • Розмежуйте ключі за середовищами (dev/staging/prod)
  • Обмежте доступ до ключів через key policy + IAM
  • Ніколи не вбудовуйте ключі в код або CI/CD змінні

💾 Шифрування сховищ

  • Увімкніть шифрування за замовчуванням для EBS у регіоні
  • Використовуйте SSE-KMS для критичних S3 бакетів
  • Увімкніть S3 Block Public Access на рівні акаунту

🌐 Транспортна безпека

  • Мінімально TLS 1.2, рекомендовано TLS 1.3
  • Використовуйте ACM для управління сертифікатами
  • Налаштуйте нагадування про закінчення сертифікатів
  • Увімкніть HSTS для веб-застосунків

🔐 Секрети та конфігурації

  • Зберігайте секрети у Secrets Manager, не в коді
  • Увімкніть автоматичну ротацію для БД-паролів
  • Налаштуйте Macie для виявлення витоків PII в S3
  • Регулярно перевіряйте Config Rules на відповідність

Практичне завдання

Сценарій

Телеком-оператор переносить систему зберігання CDR в AWS. Система складається з:

  • S3-бакет для зберігання CDR-файлів
  • RDS PostgreSQL для білінгових даних
  • REST API (EC2 або Lambda)
  • Налаштувань конфігурації (рядки підключення, паролі)

Типові вразливості та атаки на дані

Вразливості конфігурації

  • 🪣 Відкриті S3-бакети — публічний доступ без шифрування
  • 🔑 Hardcoded secrets — ключі API та паролі в коді/git
  • 📋 Незашифровані snapshots — копії БД без захисту
  • 🔄 Відсутність ротації — старі ключі та паролі
  • 📉 Слабкий TLS — TLS 1.0/1.1, застарілі cipher suites

Підсумок лекції

Ключові концепції

  • Три стани даних: at rest, in transit, in use
  • Симетрична (AES) та асиметрична (RSA, ECDH) криптографія
  • Конвертне шифрування: DEK + KEK
  • AWS KMS: CMK, AWS Managed Key, автоматична ротація
  • S3: SSE-S3, SSE-KMS, SSE-C, CSE
  • EBS та RDS: шифрування при створенні
  • ACM: безкоштовні TLS-сертифікати з авторенуванням
  • Secrets Manager: зберігання та ротація секретів
  • CloudHSM: повний контроль над ключами
