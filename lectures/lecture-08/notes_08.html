1. Навіщо моніторинг безпеки — масштаб проблеми

Моніторинг безпеки є одним із фундаментальних стовпів сучасної стратегії кіберзахисту. Принцип «неможливо захистити те, чого не бачиш» лаконічно відображає ключову цінність цього напрямку: лише тоді, коли організація має повну видимість (visibility) власного середовища, вона здатна своєчасно виявляти загрози, мінімізувати збитки та забезпечувати виконання регуляторних вимог. Відсутність належного моніторингу перетворює навіть найбільш захищену архітектуру на «чорну скриньку», де зловмисник може діяти непоміченим місяцями.

Статистика підтверджує масштаб проблеми. Відповідно до Verizon DBIR 2024, медіанний час перебування зловмисника в скомпрометованій системі (dwell time) без виявлення становить 194 дні. Ще більш тривожним є той факт, що 68% зламів виявляються не власними службами безпеки, а зовнішніми агентами — клієнтами, партнерами або регуляторами. IBM Cost of a Data Breach Report 2024 фіксує середню вартість витоку даних на рівні $4,88M, причому організації з розвиненим SOC скорочують цей показник у середньому на 49%.

Мета моніторингу охоплює чотири взаємопов'язані завдання: Detection (виявлення аномальної активності в реальному часі), Investigation (збір доказів та відтворення хронології інциденту), Response (нейтралізація загрози) та Compliance (документальне підтвердження виконання вимог PCI DSS, GDPR, ISO 27001). AWS Well-Architected Framework визначає Detection як обов'язковий елемент Security Pillar поряд з Identity Management та Infrastructure Protection.

2. Модель видимості: шари моніторингу в хмарному середовищі

Ефективний моніторинг безпеки хмарного середовища будується за принципом багатошарової видимості, що охоплює всі рівні технологічного стека. Кожен шар генерує специфічні типи подій та вимагає специфічних інструментів збору та аналізу.

  • Мережевий рівень (Network Layer): VPC Flow Logs, DNS logs, GuardDuty network analysis — виявлення аномального трафіку, C2-з'єднань, сканування.
  • Рівень хоста (Host Layer): System logs, auth events, file operations — AWS Systems Manager, Inspector v2.
  • Прикладний рівень (Application Layer): HTTP access logs, DB logs, API Gateway logs — CloudWatch Logs, WAF logs.
  • Рівень ідентичності (Identity Layer): CloudTrail (усі API-виклики), IAM Access Analyzer — повний аудит who did what when.
  • Рівень даних (Data Layer): S3 access, RDS, Secrets Manager — Macie, S3 Data Events в CloudTrail.

Цикл моніторингу безпеки є безперервним процесом: Collect → Normalize → Correlate → Analyze → Alert → Investigate → Respond → Learn. Кожен етап є необхідним: пропуск Normalize унеможливлює кореляцію, відсутність Learn призводить до повторення одних і тих самих інцидентів.

3. Основи логування: формати, рівні, структура

Лог-файли є первинним артефактом моніторингу безпеки. Якість та повнота логування безпосередньо визначають можливість виявлення та розслідування інцидентів.

Структурований лог (JSON)

{
  "timestamp": "2024-03-15T14:22:31.123Z",
  "level": "WARNING",
  "service": "auth-service",
  "event_type": "authentication_failed",
  "user_id": "user-1234",
  "source_ip": "198.51.100.42",
  "attempt": 5,
  "user_agent": "python-requests/2.31.0",
  "request_id": "req-abc-xyz"
}

Обов'язкові поля безпекового лог-запису: timestamp (ISO 8601 UTC), event_type, severity, actor (user/service), source_ip, resource, action, outcome (success/failure), request_id для трасування.

Що обов'язково логувати

  • Усі успішні та невдалі спроби автентифікації
  • Зміни привілеїв та IAM-прав
  • Зміни конфігурацій (Security Group, S3 Policy, IAM Policy)
  • Доступ до чутливих даних
  • Мережева аномальна активність
⚠️ Заборонено в логах: паролі, ключі API, номери карток (PAN), SSN, персональні дані без маскування — вимога PCI DSS та GDPR.

4. Архітектура збору та зберігання логів в AWS

Централізована архітектура логування є необхідною умовою ефективного моніторингу, особливо в multi-account середовищах. Типова архітектура: Log Sources → Kinesis Data Firehose → S3 (archive) + OpenSearch (real-time search) + CloudWatch Logs (operational).

КомпонентРольЗберігання
CloudTrail TrailАудит API-викликівS3 (1–7 років)
VPC Flow LogsМережевий трафікCloudWatch Logs / S3
ALB/CloudFront LogsHTTP трафікS3
CloudWatch LogsЗастосунки, OS1–365 днів
S3 (log archive)Централізоване сховищеObject Lock WORM

Цілісність логів забезпечується через S3 Object Lock (WORM-режим) та CloudTrail Log File Validation (SHA-256 digest-файли). Шифрування KMS (CMK) є обов'язковою вимогою PCI DSS та ISO 27001.

resource "aws_cloudwatch_log_group" "security" {
  name              = "/security/audit"
  retention_in_days = 365
  kms_key_id        = aws_kms_key.logs.arn
}

5. SIEM: Security Information and Event Management

SIEM є центральним компонентом зрілого SOC, що виконує функцію «мозку» системи безпеки — агрегує, нормалізує, корелює та аналізує події безпеки з усього середовища в реальному часі.

Функціональні компоненти SIEM

  1. Data Collection — прийом логів із сотень різнорідних джерел
  2. Normalization — уніфікована схема (OCSF, ECS)
  3. Storage — Elasticsearch/OpenSearch + S3 archival
  4. Correlation — правила виявлення паттернів атак
  5. Alerting — пріоритизовані сповіщення для SOC
  6. Reporting — compliance звіти

6. Кореляція подій та правила виявлення (Sigma Rules)

Кореляція подій — процес зіставлення множини окремих подій для виявлення складних паттернів атак, жодна з яких поодинці не є індикатором компромісу. Sigma — відкритий стандарт правил виявлення, транслюється в різні платформи.

title: AWS IAM Privilege Escalation via Policy Attachment
status: stable
logsource:
  product: aws
  service: cloudtrail
detection:
  selection:
    eventSource: iam.amazonaws.com
    eventName:
      - AttachUserPolicy
      - AttachGroupPolicy
      - PutUserPolicy
    requestParameters.policyArn|contains:
      - 'AdministratorAccess'
      - 'PowerUserAccess'
  timeframe: 15m
  condition: selection
level: high
tags:
  - attack.privilege_escalation
  - attack.t1098

Типові правила виявлення AWS

  • Публічний S3: PutBucketPublicAccessBlock з дозволеним доступом
  • Зміна SG: AuthorizeSecurityGroupIngress 0–65535 від 0.0.0.0/0
  • Видалення CloudTrail: DeleteTrail або StopLogging
  • Підозрілий IAM: >20 різних API-дій за 1 хвилину
  • Root account usage: будь-яка дія від root

7. UEBA: User and Entity Behavior Analytics

UEBA — перехід від детекції за сигнатурами до виявлення аномалій на основі ML та статистичного моделювання. Ключова інновація: формування індивідуального «поведінкового базису» для кожного user/entity, і виявлення відхилень від нього.

Технічні підходи UEBA

  • Peer grouping — порівняння з аналогічними за роллю колегами
  • Time-series analysis — чи типово виконувати дії о 3 AM?
  • Entity graph analysis — незвичні зв'язки між ресурсами
  • Geographic anomaly — логін з двох континентів за 5 хвилин

AWS GuardDuty як UEBA

GuardDuty аналізує VPC Flow Logs, CloudTrail Events та Route 53 DNS Logs через ML-моделі, побудовані на мільярдах подій. Автоматично формує behavioral baseline для кожного ресурсу та виявляє відхилення без ручного налаштування порогів. Severity Score: 0.1 (мінімальний) до 8.9 (критичний).

8. MITRE ATT&CK: Framework для виявлення загроз

MITRE ATT&CK — структурований каталог тактик та технік реальних APT-угруповань. Ключовий принцип: фокус на ЩО робить зловмисник (поведінка), а не ЧИМ (конкретний інструмент/сигнатура).

9. AWS CloudWatch: метрики та тривоги

CloudWatch є центральним сервісом моніторингу AWS, що охоплює метрики, логи, події та трейси. CloudWatch Metrics — часові ряди від AWS-сервісів та custom метрики застосунків.

aws cloudwatch put-metric-data \
  --namespace "Security/AuthMetrics" \
  --metric-name "FailedLoginAttempts" \
  --value 7 \
  --dimensions Service=auth-api,Environment=prod

CloudWatch Alarms для безпеки

resource "aws_cloudwatch_metric_alarm" "root_activity" {
  alarm_name          = "root-account-usage"
  metric_name         = "RootAccountUsageCount"
  namespace           = "CloudTrailMetrics"
  statistic           = "Sum"
  period              = 300
  evaluation_periods  = 1
  threshold           = 1
  comparison_operator = "GreaterThanOrEqualToThreshold"
  alarm_actions       = [aws_sns_topic.security_alerts.arn]
  treat_missing_data  = "notBreaching"
}

CloudWatch Anomaly Detection застосовує ML для автоматичного встановлення динамічних порогів із урахуванням сезонності — особливо цінно для метрик без фіксованих «нормальних» значень.

10. AWS CloudWatch Logs та Logs Insights

CloudWatch Logs є сервісом централізованого зберігання та аналізу лог-даних. Logs Insights — інтерактивний аналіз із власною мовою запитів.

fields @timestamp, sourceIPAddress, userAgent, errorCode
| filter eventSource = "signin.amazonaws.com" 
  and eventName = "ConsoleLogin"
  and errorCode = "Failed authentication"
| stats count(*) as failCount by sourceIPAddress, userIdentity.arn
| sort failCount desc
| limit 20

Metric Filters перетворюють паттерни в логах на CloudWatch Metrics для тригерування Alarms:

resource "aws_cloudwatch_log_metric_filter" "unauthorized_api" {
  name           = "UnauthorizedAPICalls"
  log_group_name = aws_cloudwatch_log_group.cloudtrail.name
  pattern = "{ ($.errorCode = \"*UnauthorizedAccess*\") || ($.errorCode = \"AccessDenied*\") }"
  metric_transformation {
    name      = "UnauthorizedAPICallsCount"
    namespace = "CloudTrailMetrics"
    value     = "1"
  }
}

11. AWS CloudTrail: аудит API-викликів

CloudTrail записує кожен API-виклик до AWS-сервісів: хто (IAM identity), що (eventName), де (sourceIPAddress, region), коли (eventTime), з якими параметрами, і з яким результатом.

Типи подій CloudTrail

  • Management Events — адміністративні операції (CreateVPC, AttachRolePolicy). Зберігаються 90 днів у Event History безкоштовно.
  • Data Events — операції над даними (S3 GetObject, Lambda Invoke). Потребують явного увімкнення.
  • Insights Events — незвичні паттерни Management Events.
resource "aws_cloudtrail" "main" {
  name                          = "main-trail"
  s3_bucket_name                = aws_s3_bucket.trail_logs.id
  include_global_service_events = true
  is_multi_region_trail         = true
  enable_log_file_validation    = true
  cloud_watch_logs_group_arn    = "${aws_cloudwatch_log_group.trail.arn}:*"
  kms_key_id                    = aws_kms_key.trail.arn
}
🚨 Підозрілий запис: dev-alice прикріпила AdministratorAccess о 3:14 AM — класичний privilege escalation!

12. CloudTrail: аналіз та розслідування інцидентів

Amazon Athena дозволяє виконувати SQL-запити до CloudTrail-логів у S3 — найефективніший спосіб аналізу мільйонів подій при forensic-розслідуванні.

-- Хронологія дій конкретного IAM user
SELECT eventtime, eventsource, eventname, 
       sourceipaddress, requestparameters, errormessage
FROM cloudtrail_logs
WHERE useridentity.arn LIKE '%dev-alice%'
  AND eventtime > '2024-03-14'
ORDER BY eventtime;
-- Виявлення bulk S3 download (data exfiltration)
SELECT sourceipaddress, useragent, sum(1) as request_count
FROM cloudtrail_logs
WHERE eventsource = 's3.amazonaws.com'
  AND eventname IN ('GetObject', 'ListBucket')
  AND errorcode IS NULL
GROUP BY sourceipaddress, useragent
ORDER BY request_count DESC;

Amazon Detective автоматизує цей процес: граф взаємозв'язків між ресурсами, IP-адресами та часовими вікнами дозволяє за кілька кліків відповісти на питання щодо scope of blast radius.

13. AWS Config: безперервний моніторинг конфігурацій

AWS Config фіксує стан кожного ресурсу у кожний момент часу та оцінює відповідність визначеним правилам (Config Rules). CloudTrail = WHO did WHAT; Config = СТАН ресурсів у часі.

Config RuleЩо перевіряє
s3-bucket-public-read-prohibitedS3 bucket не дозволяє публічне читання
encrypted-volumesEBS томи зашифровані
mfa-enabled-for-iam-console-accessMFA активовано для консольного доступу
cloudtrail-enabledCloudTrail активований у всіх регіонах
rds-storage-encryptedRDS-інстанси зашифровані

Auto Remediation через SSM Automation: при спрацьовуванні Config Rule автоматично виправляє невідповідність — наприклад, видаляє правило SG 0.0.0.0/0 → SSH або вмикає шифрування S3.

14. AWS Security Hub: єдина панель безпеки

Security Hub агрегує findings від GuardDuty, Inspector, Macie, Config, IAM Access Analyzer та сторонніх партнерів у єдиному інтерфейсі. Використовує стандартний формат ASFF (Amazon Security Finding Format).

Стандарти відповідності, що оцінюються автоматично: AWS Foundational Security Best Practices, CIS AWS Foundations Benchmark v1.4.0, PCI DSS v3.2.1, NIST SP 800-53 Rev 5.

# Lambda автоматизації через EventBridge
def lambda_handler(event, context):
    finding = event['detail']['findings'][0]
    severity = finding['Severity']['Label']
    
    if severity in ['CRITICAL', 'HIGH']:
        quarantine_ec2(finding['Resources'][0]['Id'])
        revoke_iam_keys(finding)
        notify_soc(finding)

Best practice: автоматично закривати INFORMATIONAL знахідки через 30 днів, якщо не підтверджені аналітиком — для боротьби з alert fatigue.

15. AWS GuardDuty: ML-детекція загроз

GuardDuty — managed service виявлення загроз на базі ML, що аналізує VPC Flow Logs, CloudTrail та Route 53 DNS Logs. Не потребує агентів. Автоматично формує behavioral baseline.

  name = "guardduty-high-severity"

16. AWS Inspector, Macie та Detective

AWS Inspector v2

Безперервне сканування EC2 та ECR на CVE-вразливості через SSM Agent. Числовий Risk Score (0–10). Аналіз reachability: чи доступна вразлива служба з Інтернету через конфігурацію Security Groups.

Amazon Macie

ML-сервіс для автоматичного виявлення PII (номери карток, SSN, медичні дані) в Amazon S3. Ключовий інструмент GDPR-compliance: автоматичне сканування + findings у Security Hub. Виявляє також публічні S3 buckets та buckets без шифрування.

Amazon Detective

Forensic-розслідування через граф взаємозв'язків між ресурсами. Відповідає на питання: «Які ресурси спілкувались із цим EC2?», «З яких IP входив цей IAM user?», «Що ще зробила ця роль?». Особливо цінний для визначення scope of blast radius при компрометації.

17. VPC Flow Logs: мережевий моніторинг

VPC Flow Logs захоплюють метадані мережевих потоків (не payload): src/dst IP, порт, протокол, байти, пакети, ACCEPT/REJECT. Формат запису:

2 123456789012 eni-0abc1234 10.0.1.15 192.168.1.1 45621 443 6 15 7548 ... ACCEPT OK
2 123456789012 eni-0abc1234 198.51.100.42 10.0.1.15 0 22 6 4 240 ... REJECT OK

Аналіз REJECT-записів — детектор розвідувальної активності. Аналіз в Athena:

-- Виявлення port scanning
SELECT srcaddr, count(distinct dstport) as ports_scanned
FROM vpc_flow_logs
WHERE action = 'REJECT'
  AND start > unix_timestamp(NOW() - INTERVAL 1 HOUR)
GROUP BY srcaddr
HAVING ports_scanned > 50
ORDER BY ports_scanned DESC;

Сценарії виявлення загроз

  • Внутрішнє сканування — lateral movement між EC2
  • Великий аутбаунд трафік — data exfiltration
  • DNS tunneling — аномальні DNS пакети
  • З'єднання до known-bad IP

18. Threat Hunting: проактивне виявлення загроз

Threat Hunting — проактивний пошук прихованих зловмисників, що не були виявлені автоматичними системами. Базується на гіпотезах: «Що якщо зловмисник вже в мережі?»

Методологія

  1. Гіпотеза — наприклад, «Скомпрометовані IAM-credentials виконують S3 discovery»
  2. Збір даних — CloudTrail, VPC Flow Logs за відповідний period
  3. IoC/IoA пошук — Athena запити для аномальних паттернів
  4. Верифікація — підтвердження або спростування гіпотези
  5. Документування — закриття або ескалація до інциденту
-- Hunt: S3 discovery anomaly
SELECT useridentity.arn, sourceipaddress, count(*) as api_count
FROM cloudtrail_logs
WHERE eventname IN ('ListBuckets', 'ListObjects', 'GetBucketAcl', 'GetBucketPolicy')
  AND eventtime > '2024-03-01'
GROUP BY useridentity.arn, sourceipaddress
HAVING api_count > 100
ORDER BY api_count DESC;

19. SOAR: автоматизація реакції на інциденти

SOAR (Security Orchestration, Automation and Response) автоматизує повторювані playbook-реакції та оркеструє дії між системами. Ключова цінність: скорочення MTTR з годин до хвилин.

Playbook: Compromised IAM Key

def compromised_iam_key_playbook(event, context):
    finding = event['detail']['findings'][0]
    iam_user = extract_iam_user(finding)
    
    # Step 1: Відкликати access key
    iam.update_access_key(
        UserName=iam_user,
        AccessKeyId=finding['Resources'][0]['Details']['...']['AccessKeyId'],
        Status='Inactive'
    )
    # Step 2: Прикріпити Deny-all policy
    attach_deny_policy(iam_user)
    # Step 3: Зберегти CloudTrail snapshot для forensic
    save_cloudtrail_snapshot(iam_user, hours_back=24)
    # Step 4: Відкрити тікет + сповістити SOC
    create_incident_ticket(severity='HIGH', user=iam_user)
    notify_soc_channel(f"Compromised IAM key for {iam_user} - auto-revoked")

Цей playbook виконується автоматично за 5–30 секунд після GuardDuty finding — задовго до того, як аналітик відкриє консоль.

20. Alert Fatigue та пріоритизація алертів

Alert fatigue — стан, коли SOC-аналітик механічно або ігнорує алерти через їх надмірну кількість. За EY GISS, 44% алертів ігноруються. Це підвищує ризик пропустити справжній інцидент.

Стратегії зниження шуму

  • False positive analysis — тюнінг правил на основі закритих як FP алертів
  • Контекстуальне збагачення — бізнес-контекст у кожному алерті
  • Auto-close INFORMATIONAL — через 30 днів без підтвердження
  • Suppression Rules — ігнорування відомо-дозволених паттернів

Оптимальна черга SOC

CRITICAL + NEW → HIGH + NEW → MEDIUM (за наявності часу) → LOW (лише при аудиті). Security Hub Score (0–100) відстежує загальний прогрес покращення постури безпеки.

21. Моніторинг телекомунікаційних та 5G мереж

Телекомунікаційні мережі мають специфічні протоколи (SS7, Diameter, SIP), що відрізняють їх моніторинг від стандартного ІТ-середовища.

CDR Analysis та SS7

CDR (Call Detail Record) фіксує IMSI/IMEI, A/B-party, час дзвінка, тип з'єднання. Аномалії в CDR є індикатором SS7-атак: IMSI Catchers (масові Location Update без реального руху), SIM-card fraud, clone attacks. SS7 Firewall (GSMA FS.11) аналізує кожне повідомлення та блокує підозрілі.

SIP/VoIP моніторинг

Session Border Controller (SBC) логує SIP-трейси. Виявляє: toll fraud (несанкціоновані міжнародні дзвінки), SIP brute-force (масові REGISTER), SIP flooding (INVITE flood DoS). Fail2ban-інтеграція для автоматичного блокування атакуючих IP.

5G Core Monitoring (3GPP TS 33.501)

AMF логує Authentication, Authorization та Registration Events. SMF — PDU Session Establishment. 5G NF генерують JSON-логи через N-інтерфейси → CloudWatch через Kinesis Agent. Ключова метрика: Authentication Success Rate — падіння нижче 95% = аномалія (IMSI Catcher або SIM fraud).

22. SOC: Security Operations Center

SOC — підрозділ, відповідальний за безперервний моніторинг, виявлення та реагування на інциденти 24/7/365. Трирівнева ієрархія: Tier 1 (Alert Analyst) → Tier 2 (Incident Responder) → Tier 3 (Threat Hunter).

23. Compliance моніторинг: PCI DSS, GDPR, ISO 27001

PCI DSS v4.0 — Requirement 10

  • Логування всіх доступів до CDE (Cardholder Data Environment)
  • Зберігання логів ≥12 місяців (3 місяці онлайн)
  • Захист логів від неавторизованих змін (S3 Object Lock)
  • Щоденний огляд логів критичних систем

GDPR

  • Article 30: Records of Processing Activities — документація
  • Article 33: Повідомлення supervisory authority за 72 год при витоку
  • Article 25: Privacy by Design — виключення PII з логів або маскування

ISO 27001

A.12.4 Logging and Monitoring → CloudTrail, CloudWatch. A.16 Incident Management → Security Hub, SOAR. AWS Audit Manager автоматично збирає evidence для ISO 27001, PCI DSS, SOC 2.

24. Централізований моніторинг Multi-Account AWS

AWS Organizations + Security Hub Delegated Administrator: один Security Tooling Account отримує aggregated findings від усіх member accounts — єдина точка видимості для SOC.

AWS Control Tower автоматично налаштовує security guardrails при провіжнингу нових акаунтів: CloudTrail у всіх регіонах, Config, GuardDuty, централізовані лог-архіви до Log Archive Account.

AWS Security Lake (OCSF-формат) — managed data lake, що агрегує безпекові дані з усіх акаунтів та регіонів у стандартизованій схемі для cross-source кореляції:

}

25. Виявлення інсайдерських загроз та ML-аномалії

Інсайдерські загрози — одні з найважко виявних. 20% усіх витоків пов'язані з інсайдерами (IBM). Три типи: злочинний інсайдер, недбалий інсайдер, компрометований інсайдер.

Індикатори підозрілої поведінки

  • Download before resignation — різке зростання S3 GetObject за 2 тижні до звільнення
  • Доступ до незвичних ресурсів (DBA, що читає HR-документи)
  • Нічні операції від акаунту, що завжди активний лише вдень
  • Використання особистих хмарних сховищ для передачі корпоративних даних

ML у Security

CloudWatch Anomaly Detection (ML для метрик), GuardDuty ML (мережа + API), Amazon Detective (graph ML для forensic), Amazon SageMaker (custom ML-детектори на CloudTrail features).
