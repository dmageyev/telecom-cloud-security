🎯 Цілі моніторингу безпеки

  • Видимість (Visibility) — знати, що відбувається у інфраструктурі
  • Виявлення загроз — ідентифікувати атаки якомога раніше
  • Відповідність (Compliance) — зберігання логів за вимогами PCI DSS, GDPR
  • Forensics — реконструкція інциденту після факту
  • Оперативна реакція — скоротити MTTD і MTTR
  • Аудит — хто, що, коли змінив
🌐 Принцип: "Неможливо захистити те, чого не бачиш" — моніторинг є основою всіх інших заходів безпеки

📦 Структурований лог (JSON)

  "timestamp": "2024-11-15T10:23:45Z",
  "level": "ERROR",
  "service": "auth-service",
  "event": "login_failed",
  "user": "bob@example.com",

🎯 Що обов'язково логувати

  • Аутентифікація — успішний/невдалий вхід, MFA, logout
  • Авторизація — доступ до ресурсів, відмова в доступі
  • Зміни конфігурації — хто, що і коли змінив
  • Привілейовані дії — sudo, root, IAM changes
  • Помилки застосунку — exceptions, failed queries
  • Мережеві з'єднання — нові з'єднання, відмови
  • Фінансові транзакції — PCI DSS вимога
⚠️ Заборонено в логах: паролі, ключі API, номери карток (PAN), SSN, персональні дані без маскування

Архітектура збору та зберігання логів в AWS

🏗️ Централізована архітектура логування

  • Джерела: EC2, Lambda, ECS, RDS, ALB, CloudFront, API GW
  • Агент: CloudWatch Agent, Fluent Bit, Kinesis Agent
  • Транспорт: CloudWatch Logs → Kinesis Data Firehose
  • Сховище: Amazon S3 (довгострокове), OpenSearch (аналіз)
  • Захист: шифрування KMS, immutable storage (S3 Object Lock)
🔐 Цілісність логів: S3 Object Lock (WORM) — логи не можна змінити або видалити, що забезпечує докази для розслідувань та compliance

⚙️ Terraform: CloudWatch Log Group

resource "aws_cloudwatch_log_group" "app" {
  name              = "/app/production"
  retention_in_days = 365

  # Шифрування KMS
  kms_key_id = aws_kms_key.logs.arn

  tags = {
    Environment = "production"
    Compliance  = "PCI-DSS"
  }
}

# Передача до S3 через Firehose
resource "aws_kinesis_firehose_delivery_stream" "logs" {
  name        = "logs-to-s3"
  destination = "extended_s3"

  extended_s3_configuration {
    bucket_arn = aws_s3_bucket.logs.arn
    prefix     = "logs/year=!{timestamp:yyyy}/"
  }
}

SIEM — Security Information and Event Management

🏛️ Що таке SIEM

  • SIM (Security Information Management) — зберігання та аналіз логів
  • SEM (Security Event Management) — реальний час, кореляція подій
  • SIEM = SIM + SEM — уніфікована платформа безпеки

🔧 Функції SIEM

  • Збір та нормалізація логів із різнорідних джерел
  • Кореляція подій за часом та сутностями
  • Виявлення аномалій та відхилень
  • Генерація алертів та тікетів у ITSM
  • Візуалізація та дашборди для SOC
  • Forensic analysis та звітність
📊 Популярні SIEM: Splunk, IBM QRadar, Microsoft Sentinel, Elastic SIEM, AWS-native (Security Hub + OpenSearch)

Кореляція подій та правила виявлення

🔗 Кореляція подій

  • Часова кореляція — події в межах часового вікна (5 невдалих входів за 60 сек)
  • Просторова — той самий IP атакує різні сервіси
  • Entity-based — той самий обліковий запис, але різні геолокації
  • Ланцюжкова — послідовність: scan → exploit → lateral movement

📋 Sigma Rule — стандарт правил

title: AWS Suspicious IAM Activity
status: stable
logsource:
    product: aws
    service: cloudtrail
detection:
    selection:
        eventName:
            - CreateAccessKey
            - AttachUserPolicy
        userIdentity.type: IAMUser
    filter:
        userIdentity.arn|contains: '/terraform-'
    condition: selection and not filter
level: high

UEBA — User and Entity Behavior Analytics

🧠 Що таке UEBA

  • Аналіз поведінки на основі базових ліній (baseline)
  • Виявлення аномалій без написання явних правил
  • Оцінка ризику кожного користувача та сутності
  • Виявлення insider threats — законний акаунт, але підозріла поведінка
  • Виявлення скомпрометованих облікових записів

📊 Ознаки аномальної поведінки

  • Вхід у незвичний час (3:00 AM в будній день)
  • Вхід із незвичної геолокації або пристрою
  • Масове завантаження файлів (S3 GetObject x1000)
  • Перехід на нові API-виклики, яких не було раніше
  • Escalation of privileges після довгого простою

☁️ AWS GuardDuty як UEBA

  • Machine Learning — аналіз CloudTrail, VPC Flow, DNS логів
  • Автоматичне навчання на поведінці акаунту (14 днів)
  • Виявлення: незвичних API-викликів, Tor-виходів, coin mining

MITRE ATT&CK — Framework для виявлення загроз

🗺️ Що таке MITRE ATT&CK

  • База знань тактик і технік реальних атакуючих
  • Стандартна мова для опису загроз і виявлень
  • 14 тактик (Tactics) → техніки (Techniques) → підтехніки
  • Матриці: Enterprise, Mobile, ICS, Cloud

📋 Тактики ATT&CK (Enterprise)

TA0002ExecutionLambda abuse, SSM RunCommand
TA0003PersistenceNew IAM user + access key
TA0004Privilege EscalationAttachUserPolicy + admin role

TA0009CollectionS3 bulk download
TA0010ExfiltrationS3 → external bucket via policy

🔗 ATT&CK і детекція в AWS

  • Mapping: кожен GuardDuty finding → ATT&CK technique
  • Coverage: Security Hub показує % покриття матриці
  • Hunt: Threat Hunting на основі ATT&CK TTP

AWS CloudWatch — Метрики та моніторинг

📊 CloudWatch Metrics

  • Namespace — простір імен (AWS/EC2, AWS/Lambda)
  • Dimension — тег для фільтрації (InstanceId)
  • Resolution — стандартна (1 хв) або висока (1 с)
  • Retention — до 15 місяців для агрегованих даних
  • Custom Metrics — власні метрики застосунку

⚙️ AWS CLI — публікація метрики

aws cloudwatch put-metric-data \
  --namespace "MyApp/Security" \
  --metric-data \
    MetricName=FailedLogins,\
    Value=1,Unit=Count,\
    Dimensions=[{Name=Service,\
                 Value=AuthService}]

⏰ CloudWatch Alarms

  • Threshold alarm — метрика перевищує значення
  • Anomaly detection — ML-модель нормальної поведінки
  • Composite alarm — комбінація кількох алармів
  • Дії: SNS notification, Auto Scaling, EC2 action
resource "aws_cloudwatch_metric_alarm" "brute" {
  alarm_name  = "BruteForceDetection"
  namespace   = "MyApp/Security"
  metric_name = "FailedLogins"
  period      = 300
  statistic   = "Sum"
  threshold   = 10
  comparison_operator =
    "GreaterThanThreshold"
  alarm_actions = [aws_sns_topic.sec.arn]
}

AWS CloudWatch Logs та Logs Insights

📋 CloudWatch Logs — основи

  • Log Group — контейнер для логів одного сервісу
  • Log Stream — послідовність подій (1 EC2 instance = 1 stream)
  • Retention — 1 день до 10 років
  • Metric Filter — витягує метрику з тексту лога
  • Subscription Filter — стрімінг до Lambda/Kinesis

🔎 Logs Insights — запит

# Знайти невдалі входи за останні 24 год
fields @timestamp, @message
| filter @message like /AuthenticationFailed/
| stats count(*) as failures
    by bin(1h)
| sort failures desc

# Top 10 IP за невдалими входами
fields sourceIPAddress, eventName
| filter eventName = "ConsoleLogin"
  and responseElements.ConsoleLogin
    = "Failure"
| stats count(*) by sourceIPAddress
| sort by count desc
| limit 10

🔔 Metric Filter для безпеки

# Terraform: фільтр для Root Login
resource "aws_cloudwatch_log_metric_filter"
    "root_login" {
  name           = "RootLoginFilter"
  log_group_name =
    aws_cloudwatch_log_group.cloudtrail.name
  pattern = "{ $.userIdentity.type =
    \"Root\" && $.eventName =
    \"ConsoleLogin\" }"

  metric_transformation {
    name      = "RootLoginCount"
    namespace = "Security/Auth"
    value     = "1"
  }
}

resource "aws_cloudwatch_metric_alarm"
    "root_login" {
  alarm_name  = "RootLoginDetected"

AWS CloudTrail — аудит API-викликів

📜 Що таке CloudTrail

  • Записує кожен API-виклик в AWS (консоль, CLI, SDK)
  • Три типи подій: Management Data Insights
  • Management Events — CreateBucket, RunInstances, AttachPolicy
  • Data Events — S3 GetObject/PutObject, Lambda Invoke (платні)
  • Insights Events — аномальна активність API
⚠️ За замовчуванням: CloudTrail зберігає Management Events лише 90 днів. Для compliance потрібен Trail → S3 на 1–7 років

🔒 Захист CloudTrail

  • Увімкніть LogFileValidation (SHA-256 checksums)
  • S3 Object Lock для захисту від видалення
  • Моніторинг StopLogging та DeleteTrail подій

🔍 Приклад CloudTrail запису

CloudTrail — аналіз та розслідування інцидентів

🔎 Athena для аналізу CloudTrail

-- Знайти всі дії root за 7 днів
SELECT eventtime, eventname,
       sourceipaddress, useragent
FROM cloudtrail_logs
WHERE useridentity.type = 'Root'
  AND eventtime > date_add('day',-7,now())
ORDER BY eventtime DESC;

-- Знайти видалення/зупинку логування
SELECT eventtime, eventname,
       useridentity.username,
       sourceipaddress
FROM cloudtrail_logs
WHERE eventname IN (
  'StopLogging','DeleteTrail',
  'DeleteFlowLogs','DisableKeyRotation'
)
ORDER BY eventtime DESC;

🔧 Автоматичне відновлення (Remediation)

# Config Rule + Auto Remediation
resource "aws_config_config_rule" "s3_public" {
  name = "s3-public-prohibited"
  source {
    owner             = "AWS"
    source_identifier =
      "S3_BUCKET_PUBLIC_READ_PROHIBITED"
  }
}

resource "aws_config_remediation_configuration"
    "s3_fix" {
  config_rule_name = aws_config_config_rule
                     .s3_public.name
  target_type      = "SSM_DOCUMENT"
  target_id =
    "AWS-DisableS3BucketPublicReadWrite"
  automatic = true
  maximum_automatic_attempts = 3

  parameter {
    name         = "AutomationAssumeRole"
    static_value = aws_iam_role.config.arn
  }
}

📋 Процес Threat Hunt

  1. Гіпотеза: "Зловмисник використав stolen IAM key"
  2. Дані: CloudTrail за 30 днів
  3. Пошук: незвичні API + незвичний час + новий IP
  4. Аналіз: кореляція з відомими TTP
  5. Результат: підтвердження / спростування гіпотези

🔎 Приклад Threat Hunt у AWS

-- Hunt: Нові IAM ключі, що ніколи не
-- використовувались у регіоні us-east-1
-- але раптово активувались у eu-west-1
SELECT useridentity.accesskeyid,
       useridentity.username,
       awsregion,
       min(eventtime) as first_use,
       count(*) as api_calls
FROM cloudtrail_logs
WHERE eventtime > '2024-10-01'
  AND awsregion != 'us-east-1'
  AND useridentity.type = 'IAMUser'
GROUP BY 1,2,3
HAVING min(eventtime) > '2024-10-15'
ORDER BY first_use;

Alert Fatigue та пріоритизація алертів

😫 Проблема Alert Fatigue

  • Середній SOC отримує ~10,000 алертів/день
  • До 50% алертів — хибнопозитивні (false positives)
  • Аналітики "втомлюються" і починають ігнорувати алерти
  • Реальні інциденти губляться в шумі

🎯 Стратегії зниження шуму

  • Tuning правил — виключення відомих хибнопозитивних
  • Suppression — ігнорування очікуваної поведінки (DevOps tools)
  • Aggregation — групування 100 схожих алертів в 1
  • Risk scoring — CVSS + context = пріоритет
  • Automation — auto-close очевидних FP

# Lambda: автоматична ізоляція EC2
def isolate_ec2(instance_id):
    ec2 = boto3.client('ec2')

    # 1. Snapshot диска (forensics)
    ec2.create_snapshot(
        VolumeId=get_root_volume(instance_id),
        Description=f'IR-{instance_id}-{now()}'
    )

    # 2. Ізолюючий Security Group
    ec2.modify_instance_attribute(
        InstanceId=instance_id,
        Groups=['sg-isolation-00000']  # deny all
    )

    # 3. Відключити IAM роль
    ec2.disassociate_iam_instance_profile(
        AssociationId=get_profile_assoc(
            instance_id)
    )

    # 4. Тег для SOC
    ec2.create_tags(Resources=[instance_id],
        Tags=[{'Key':'IR-Status',
               'Value':'ISOLATED'}])

📖 Сценарій: Compromised EC2 → Data Exfiltration

  1. D+0: Атакуючий отримує доступ до EC2 через вразливість у веб-застосунку
  2. D+0.5h: EC2 починає DNS-запити до відомого C&C домену
  3. GuardDuty: Backdoor:EC2/C&CActivity.B HIGH (8.0)
  4. D+1h: Атакуючий використовує IMDS для отримання IAM ролі EC2
  5. GuardDuty: CredentialAccess:EC2/AnomalousBehavior
  6. D+2h: IAM роль EC2 використовується для S3 GetObject з іншого IP
  7. GuardDuty: Exfiltration:S3/ObjectRead.Unusual CRITICAL

🔄 Автоматична реакція

  1. T+0 хв: Security Hub отримує GuardDuty CRITICAL finding
  2. T+1 хв: EventBridge → Step Functions playbook запускається
  3. T+2 хв: Lambda знімає snapshot EC2 (forensics)
  4. T+2 хв: Lambda ізолює EC2 (isolation SG)
  5. T+3 хв: Lambda відкликає credentials IAM ролі EC2
  6. T+3 хв: SNS → PagerDuty → SOC L2 отримує дзвінок
  7. T+5 хв: Jira ticket з усіма деталями
✅ MTTD: 30 хвилин (GuardDuty ML) vs. 194 дні (без SOC)
✅ MTTR: 5 хвилин (автоматизація) vs. 73 дні (вручну)
