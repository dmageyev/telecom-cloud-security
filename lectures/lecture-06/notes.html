1. Огляд обчислювальних сервісів AWS

AWS надає кілька рівнів обчислювальних сервісів — від повного контролю над ОС до повністю serverless-рішень.

СервісТипРівень управління клієнтомПриклад
EC2Віртуальні машиниОС, патчі, мережаТелеком-платформи, БД
ECSКонтейнери (керовані)Образ, Task DefinitionМікросервіси
EKSKubernetes (керований)Pod, Node конфігураціяМасштабовані застосунки
FargateServerless-контейнериОбраз + Task DefinitionЗадачі без серверів

Ключовий принцип Зі збільшенням рівня абстракції AWS бере більше відповідальності, але клієнт завжди відповідає за код, конфігурацію та права доступу.

2. Модель спільної відповідальності для Compute

☁️ AWS відповідає за

  • Фізичну безпеку дата-центрів
  • Гіпервізор та ізоляцію між клієнтами
  • Мережеву інфраструктуру AWS
  • Control Plane ECS/EKS
  • Runtime середовище Fargate та Lambda

🧑‍💻 Клієнт відповідає за

  • ОС EC2 (патчі, конфігурація, hardening)
  • Security Groups та NACL
  • Вміст та конфігурацію контейнерів
  • IAM-ролі для сервісів (Execution Role, IRSA)
  • Шифрування даних (EBS, S3, TLS)
  • Код Lambda та залежності
Важливо Більшість успішних атак на хмарні середовища — це не зломи AWS-інфраструктури, а неправильна конфігурація з боку клієнта: відкриті S3-бакети, надмірні IAM-права, незашифровані дані.

3. Безпека Amazon EC2

IMDSv2 — захист метаданих

IMDS (Instance Metadata Service) доступний за адресою 169.254.169.254 і надає EC2 тимчасові IAM credentials. IMDSv1 не вимагав токена — будь-яка SSRF-вразливість у застосунку могла привести до крадіжки credentials.

IMDSv2 вирішує це: спочатку потрібен PUT-запит для отримання сесійного токена:

TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/

SSRF-атаки зазвичай не можуть виконати PUT-запит або додати довільні HTTP-заголовки, тому IMDSv2 значно ускладнює цей вектор і знижує ризик витоку credentials. Водночас потужні SSRF-примітиви, що дозволяють довільні методи й заголовки, усе ще можуть обійти цей захист.

Примусове вмикання IMDSv2

aws ec2 modify-instance-metadata-options \
  --instance-id i-xxxx \
  --http-tokens required \
  --http-endpoint enabled

4. EC2: AWS Systems Manager та управління патчами

Чому SSM Session Manager замість SSH?

  • Не потрібно відкривати порт 22 у Security Group
  • Аудит сесій автоматично записується в S3/CloudWatch
  • Доступ через IAM — можна відкликати миттєво для конкретного користувача
  • Не потрібно управляти SSH-ключами
# Підключення без SSH
aws ssm start-session --target i-1234567890abcdef0

# Вимога: SSM Agent + IAM роль з AmazonSSMManagedInstanceCore

Patch Manager — Patch Baseline

Patch Baseline визначає, які патчі автоматично затверджуються:

  • Critical — автозатвердження через 0 днів
  • Important — через 7 днів
  • CVSSScore ≥ 7.0 — включити в baseline
Рекомендація NIST CRITICAL патчі — протягом 30 днів (NIST SP 800-190). Maintenance Window — плануйте вікно обслуговування (наприклад, вівторок 02:00–04:00 UTC) щоб не впливати на продуктивність.

6. VPC: безпечна мережева архітектура

IsolatedIsolated SubnetRDS, ElastiCacheБез виходу в інтернет

VPC Endpoints — PrivateLink

Замість виходу через інтернет для звернень до AWS API (ECR, Secrets Manager, SSM) — використовуйте VPC Endpoints:

  • Gateway Endpoint (безкоштовно): S3, DynamoDB
  • Interface Endpoint: ECR, SSM, Secrets Manager, KMS, CloudWatch
Переваги Трафік до AWS API не виходить з мережі AWS. Знижується ризик MITM-атак та витоку даних. Можна повністю заблокувати outbound інтернет-трафік для production Pods.

8. Docker: архітектура та безпека

Ієрархія Docker

dockerd (daemon, root) → /var/run/docker.sock
  └── containerd (runtime manager)
       └── runc (OCI runtime, створює namespace/cgroups)
            └── container process
Docker Socket — критична вразливість Монтування /var/run/docker.sock в контейнер дає йому повний контроль над Docker daemon, що еквівалентно root-доступу до хост-системи. Ніколи не монтуйте його в недовірені контейнери!

Зменшення привілеїв

# Non-root user
docker run --user 1000:1000 nginx

# Read-only filesystem
docker run --read-only --tmpfs /tmp nginx

# Видалити всі capabilities, додати лише потрібні
docker run --cap-drop ALL --cap-add NET_BIND_SERVICE nginx

# Rootless Docker (демон без root)
dockerd-rootless-setuptool.sh install

10. Multi-stage Build та .dockerignore

Multi-stage Build

Дозволяє розділити образ збірки (з компіляторами) та мінімальний production-образ:

# Stage 1: Build (Go компілятор ~400MB)
FROM golang:1.22-alpine AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o /app ./cmd/server

# Stage 2: Distroless (~10MB, без shell, без package manager)
FROM gcr.io/distroless/static-debian12
COPY --from=builder /app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]

.dockerignore — що виключати

.git          # git-history з можливими старими секретами
.env .env.*   # файли з паролями/ключами
secrets/      # папки з credentials
*.key *.pem   # SSL/TLS ключі
node_modules/ # зайві залежності
tests/ docs/  # не потрібні в production
Без .dockerignore — можливий витік секретів COPY . . без .dockerignore копіює весь build context: .env файли, SSH-ключі, .git з давно "видаленими" секретами у history.

11. Сканування вразливостей Docker-образів

Pipeline сканування

Developer commit
  → git-secrets / gitleaks (секрети в коді)
  → Hadolint (lint Dockerfile)
  → docker build
  → Trivy scan (CVE в образі)
  ↳ CRITICAL знайдено → FAIL (деплой заблоковано)
  → Push до ECR (тільки при успіху)
  → ECR Enhanced Scanning (безперервно)
  → Deploy
  → Falco / GuardDuty (runtime)

Trivy — основні команди

# Сканування образу
trivy image myapp:latest

# Тільки HIGH та CRITICAL
trivy image --severity HIGH,CRITICAL myapp:latest

# Вивід для GitHub Security (SARIF)
trivy image --format sarif \
  --output trivy.sarif myapp:latest

# Сканування IaC (Dockerfile, Terraform)
trivy config ./

Amazon ECR — безпека реєстру

  • Приватні репозиторії з тонким IAM-контролем
  • Basic Scanning: при push (Clair)
  • Enhanced Scanning: безперервно через Amazon Inspector
  • Lifecycle Policies: автовидалення образів старіших за N днів
  • Image Signing: cosign/Notary v2

12. SBOM та Image Signing

SBOM (Software Bill of Materials)

Машиночитаний перелік всіх компонентів ПЗ: OS-пакети, бібліотеки, версії, ліцензії.

  • Формати: CycloneDX (рекомендований для security), SPDX
  • Дозволяє миттєво знайти вразливий компонент у всьому флоті образів
  • Вимагається NIST EO 14028 (2021) для держ. ПЗ США
# Syft — генерація SBOM
syft myapp:latest -o cyclonedx-json > sbom.json

# Grype — аналіз SBOM на CVE
grype sbom:sbom.json --only-fixed

cosign — Image Signing

# Генерація ключів
cosign generate-key-pair

# Підписати образ (підпис зберігається в ECR поруч з образом)
cosign sign --key cosign.key \
  123.dkr.ecr.region.amazonaws.com/app:v1.0

# Верифікація перед деплоєм
cosign verify --key cosign.pub \
  123.dkr.ecr.region.amazonaws.com/app:v1.0
SLSA Framework Supply-chain Levels for Software Artifacts — Google-стандарт. L3: ізольоване середовище збірки + підпис artifacts. L4: відтворювана (hermetic) збірка.

Принцип: виявляй проблеми якомога раніше. Вартість виправлення на різних етапах:

GitHub Actions: Trivy у CI/CD

- name: Build Docker image
  run: docker build -t myapp:${{ github.sha }} .

- name: Scan with Trivy
  uses: aquasecurity/trivy-action@v0.20
  with:
    image-ref: myapp:${{ github.sha }}
    format: sarif
    exit-code: 1         # Fail на CRITICAL
    severity: CRITICAL,HIGH
    output: trivy-results.sarif

- name: Upload to GitHub Security
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: trivy-results.sarif

14. Kubernetes: архітектура та RBAC

Control Plane компоненти

  • kube-apiserver — єдина точка входу, автентифікація/авторизація
  • etcd — сховище стану. Шифрувати обов'язково (envelope encryption через KMS)!
  • kube-scheduler — розподіляє Pods на вузли
  • controller-manager — забезпечує бажаний стан кластера

RBAC — приклад

# Role: дозволи в межах namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]  # Тільки читання!

---
# Прив'язати Role до Service Account
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
subjects:
- kind: ServiceAccount
  name: myapp-sa
roleRef:
  kind: Role
  name: pod-reader

Network Policy — default deny

# Заборонити весь трафік (обов'язковий перший крок)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
За замовчуванням K8s дозволяє ВЕСЬ трафік! NetworkPolicy потребує CNI-плагіну з підтримкою: Calico, Cilium або AWS VPC CNI. Стандартний kubenet не підтримує.

16. Kubernetes Admission Controllers

Kyverno — Policy as Code

# Відхилити Pod без securityContext.runAsNonRoot
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-non-root
spec:
  rules:
  - name: check-runAsNonRoot
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "Pods must run as non-root user"
      pattern:
        spec:
          securityContext:
            runAsNonRoot: true

OPA Gatekeeper — заборона latest тегу

apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sDisallowedTags
metadata:
  name: no-latest-tag
spec:
  match:
    kinds:
    - apiGroups: [""]
      kinds: ["Pod"]
  parameters:
    tags: ["latest"]

17. Kubernetes Secrets: шифрування

K8s Secrets = base64, не шифрування! echo "c2VjcmV0" | base64 -d → secret. Будь-хто з kubectl get secret або прямим доступом до etcd отримує всі секрети.

External Secrets Operator — рекомендований підхід

Секрети зберігаються виключно в AWS Secrets Manager, а не в etcd:

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: my-db-secret
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: my-db-k8s-secret
  data:
  - secretKey: password
    remoteRef:
      key: prod/myapp/database
      property: password
Переваги External Secrets Автоматична ротація: при оновленні секрету в AWS Secrets Manager — K8s Secret оновлюється протягом refreshInterval. Pods автоматично отримують нові credentials.

18. Amazon EKS

IRSA (IAM Roles for Service Accounts)

Дозволяє Pod-у отримати тимчасові IAM credentials через Web Identity Federation, без статичних ключів:

eksctl create iamserviceaccount \
  --name s3-reader \
  --namespace production \
  --cluster my-cluster \
  --attach-policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess \
  --approve

# Pod автоматично отримує:
# AWS_ROLE_ARN, AWS_WEB_IDENTITY_TOKEN_FILE
# AWS SDK автоматично використовує ці credentials

Приватний Control Plane endpoint

aws eks update-cluster-config \
  --name my-cluster \
  --resources-vpc-config \
    endpointPublicAccess=false,endpointPrivateAccess=true

import boto3, re

def handler(event, context):
    user_id = event.get("userId", "")
    
    # 1. Суворо валідувати вхідні дані
    if not re.match(r'^[a-zA-Z0-9_-]{3,50}$', user_id):
        return {"statusCode": 400, "body": "Invalid input"}

    sm = boto3.client('secretsmanager')
    secret = sm.get_secret_value(
        SecretId='prod/myapp/db'
    )['SecretString']
    
    # 3. Логувати без секретів!
    print(f"Processing: {user_id}")
    
    return {"statusCode": 200}

22. Lambda: VPC та Resource Policy

Коли Lambda потрібна у VPC

  • Доступ до RDS, ElastiCache у private subnet
  • Потрібні додаткові мережеві обмеження через Security Groups
  • Організаційні вимоги безпеки
Lambda у VPC — cold start Lambda у VPC вимагає ENI (Elastic Network Interface), що збільшує cold start. Використовуйте тільки якщо справді потрібен доступ до ресурсів VPC.

Resource Policy — захист від confused deputy

{
  "Effect": "Allow",
  "Principal": {"Service": "apigateway.amazonaws.com"},
  "Action": "lambda:InvokeFunction",
  "Condition": {
    "ArnLike": {
      "AWS:SourceArn": "arn:aws:execute-api:region:123:api-id/*/GET/users"
    }
  }
}

Умова SourceArn гарантує, що тільки конкретний API Gateway endpoint може викликати цю Lambda.

25. Типові атаки на контейнери

Container Escape — Privileged Mode

# Всередині privileged контейнера:
fdisk -l                          # Бачимо диски хоста
mkdir /mnt/host
mount /dev/xvda1 /mnt/host        # Монтуємо кореневий диск хоста
chroot /mnt/host                  # Root shell на хост-системі!
CVE-2019-5736 (runc container escape) Зловмисник міг перезаписати бінарник runc через /proc/self/exe, отримуючи виконання на хості. Патч випущено через 24 години після публікації. Нагадує про критичність своєчасного оновлення container runtime.

SSRF → IMDS → IAM credentials

Сценарій Capital One (2019):

  1. Зловмисник знайшов SSRF у WAF (misconfigured AWS service)
  2. HTTP запит до http://169.254.169.254/latest/meta-data/iam/security-credentials/<role>
  3. Отримав тимчасові credentials IAM ролі
  4. Скопіював 100 млн записів клієнтів з S3

IMDSv2 повністю блокує цей вектор.

27. Моніторинг та Falco

Falco — правило виявлення shell у контейнері

- rule: Terminal shell in container
  desc: A shell was spawned in a production container
  condition: >
    container.id != host and
    proc.name in (bash, sh, zsh, fish) and
    proc.tty != 0 and
    not container.image.repository in (debug-images)
  output: >
    Shell spawned (user=%user.name
    container=%container.name
    image=%container.image.repository
    cmd=%proc.cmdline)
  priority: WARNING
  tags: [container, shell, mitre_execution]

Що відстежувати

  • Shell у production контейнері (підозрілий!)
  • Запис у /etc або /bin (підозрілий!)
  • Незвичні мережеві з'єднання (C&C, порт-скани)
  • Підвищення привілеїв (sudo, su)
  • Нові процеси у контейнері, що не відповідають образу

28. Incident Response для контейнерів

Workflow реагування

  1. Виявлення — GuardDuty / Falco alert, CloudTrail anomaly
  2. Ізоляція — застосувати NetworkPolicy "deny-all" до скомпрометованого Pod
  3. Збереження — docker export, kubectl debug, memory dump
  4. Аналіз — processes, network connections, filesystem changes, logs
  5. Remediation — оновити образ, перерозгорнути, ротувати credentials
  6. Post-mortem — timeline, root cause analysis, prevention measures

29. Zero Trust у хмарних середовищах

Принципи Zero Trust

  1. Verify Explicitly — завжди перевіряй identity, не довіряй на основі мережі
  2. Least Privilege — мінімальні права для кожного суб'єкта та транзакції
  3. Assume Breach — проектуй як якщо зловмисник вже всередині

Service Mesh (Istio) для мікросервісів

# mTLS автоматично між всіма сервісами
# AuthorizationPolicy: тільки frontend → backend
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: backend-allow-frontend
spec:
  selector:
    matchLabels:
      app: backend
  rules:
  - from:
    - source:
        principals:
        - "cluster.local/ns/default/sa/frontend-sa"
    to:
    - operation:
        methods: ["GET", "POST"]
        paths: ["/api/*"]
