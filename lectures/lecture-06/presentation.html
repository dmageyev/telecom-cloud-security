Безпека Amazon EC2

🖥️ Ключові заходи безпеки

  • Вибір перевіреного AMI (Amazon Machine Image)
  • Регулярне оновлення ОС та пакетів
  • Мінімальна поверхня атаки (вимкнути зайві сервіси)
  • SSH-доступ тільки через ключові пари
  • Використання AWS Systems Manager Session Manager замість SSH
  • Instance Metadata Service v2 (IMDSv2)

🔑 IMDSv2 — захист метаданих

  • Вимагає токен для доступу до /latest/meta-data/
  • Захист від SSRF-атак на ролі IAM
  • Обов'язково вмикати на нових інстансах

⚠️ Типові помилки EC2

  • Відкритий порт 22 (SSH) для 0.0.0.0/0
  • Використання IMDSv1 (вразливий до SSRF)
  • Надмірні IAM-права для EC2-ролі
  • Незашифровані EBS-томи
  • Публічний S3-бакет для скриптів user-data
  • Відсутність моніторингу та алертів

Мережева ізоляція EC2: Security Groups & NACL

ХарактеристикаSecurity GroupNetwork ACL
Рівень Інстанс (EC2, RDS…) Підмережа (Subnet)
Стан Stateful (відповіді дозволені автоматично) Stateless (правила для IN і OUT окремо)
Правила Тільки дозволяючі (Allow) Дозволяючі та заборонні (Allow/Deny)
Порядок Всі правила застосовуються Номер правила (нижчий = пріоритет)
Застосування Основний механізм контролю Додатковий рівень блокування
🛡️ Принцип Defense in Depth: SG + NACL + VPC Flow Logs + WAF = багаторівневий захист

Основи контейнеризації

📦 Що таке контейнер?

  • Ізольований процес з власним файловим простором
  • Спільне ядро з хост-системою
  • Швидше за ВМ, легше переносити
  • Образ (Image) = незмінний шаблон
  • Контейнер = запущений екземпляр образу

🔄 VM vs Container

VMContainer
ІзоляціяПовна (гіпервізор)Часткова (namespaces)
ЗапускХвилиниСекунди
РозмірГБМБ
ОСОкрема ОССпільне ядро

🔒 Механізми ізоляції Linux

Namespaces Ізоляція PID, мережі, файлової системи, користувачів

cgroups Обмеження ресурсів CPU, пам'яті, I/O

seccomp Фільтрація системних викликів

AppArmor/SELinux Профілі обов'язкового контролю доступу

⚠️ Shared kernel = якщо ядро скомпрометоване — всі контейнери під загрозою

Docker: архітектура та безпека

🐳 Компоненти Docker

  • dockerd — демон (root-права!)
  • containerd — runtime контейнерів
  • runc — низькорівневий OCI-runtime
  • Docker socket: /var/run/docker.sock

⚠️ Монтування docker.sock

Доступ до сокету = повний контроль над хост-системою. Ніколи не монтуйте його в недовірені контейнери!

🛡️ Запуск без root

# Запуск як non-root user
docker run --user 1000:1000 nginx

# Rootless Docker (демон без root)
dockerd-rootless-setuptool.sh install

# Read-only filesystem
docker run --read-only nginx

Обмеження capabilities

# Видалити всі capabilities, додати лише потрібні
docker run --cap-drop ALL \
           --cap-add NET_BIND_SERVICE nginx

Безпечний Dockerfile

✅ Правильний Dockerfile

# Використовувати конкретний тег образу
FROM python:3.12-slim

# Не запускати від root
RUN addgroup --system app \
 && adduser --system --ingroup app app

WORKDIR /app

# Копіювати тільки потрібні файли
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY --chown=app:app . .

# Перемкнутися на non-root
USER app

# Не відкривати зайвих портів
EXPOSE 8080

CMD ["python", "app.py"]

❌ Типові помилки

# Погано: використання latest
FROM ubuntu:latest

# (відсутній USER)

# Погано: секрети в ENV
ENV DB_PASSWORD=secret123

# Погано: весь контекст у образі
COPY . .

# Погано: привілейований режим
# docker run --privileged ...

Kubernetes: архітектура та компоненти безпеки

⚙️ Control Plane

  • kube-apiserver — точка входу, автентифікація
  • etcd — сховище стану кластера (шифрувати!)
  • kube-scheduler — розподіл Pod-ів
  • controller-manager — підтримка стану

🔑 Автентифікація в K8s

  • Сертифікати X.509
  • Service Account токени
  • OIDC (OpenID Connect)
  • AWS IAM → IRSA для EKS

🛡️ Авторизація: RBAC

🌐 Network Policy

metadata:
  name: deny-all
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
---
# Дозволити тільки frontend → backend
spec:
  podSelector:
    matchLabels:
      app: backend
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend

Amazon EKS — безпека керованого Kubernetes

☁️ Що управляє AWS

  • Control Plane (kube-apiserver, etcd)
  • Патчі control plane
  • Multi-AZ розгортання control plane
  • Шифрування etcd за замовчуванням

🔑 IRSA — IAM Roles for Service Accounts

Pod отримує IAM-роль через Service Account.

Дрібнозернистий доступ до AWS API без постійних ключів.

eksctl create iamserviceaccount \
  --name s3-reader \
  --namespace myapp \
  --cluster my-cluster \
  --attach-policy-arn \
    arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess \
  --approve

🛡️ EKS Security Best Practices

  • Приватний endpoint для kube-apiserver
  • Envelope encryption secrets через KMS
  • Managed Node Groups (автопатчі)
  • EKS Fargate — без EC2-вузлів
  • GuardDuty EKS Runtime Monitoring
  • Amazon Inspector для образів у ECR
  • AWS Security Hub для агрегації алертів

Amazon ECS та AWS Fargate

📋 Amazon ECS — компоненти

  • Task Definition — конфігурація контейнерів
  • Service — підтримання N запущених Task
  • Cluster — логічна група ресурсів
  • Task Role — IAM-роль для контейнера

🔒 Безпека Task Definition

{
  "containerDefinitions": [{
    "name": "myapp",
    "image": "123.dkr.ecr.../app:v1",
    "readonlyRootFilesystem": true,
    "user": "1000",
    "linuxParameters": {
      "capabilities": {
        "drop": ["ALL"]
      }
    }
  }]
}

⚡ Fargate — переваги безпеки

  • Немає доступу до хост-ОС
  • AWS патчить runtime середовище
  • Кожна Task має власний мікро-VM (gVisor)
  • Немає спільного ядра між Tasks
  • EphemeralStorage — тимчасова ізольована ФС

🔑 Secrets Management

  • AWS Secrets Manager → inject at runtime
  • AWS SSM Parameter Store (SecureString)
  • Ніколи не передавати секрети через ENV у Dockerfile!

Serverless безпека: AWS Lambda

⚡ Модель виконання Lambda

  • Ізольоване середовище (Firecracker MicroVM)
  • Короткострокове виконання (max 15 хв)
  • Автомасштабування AWS
  • Cold start — нова ізольована VM

🔒 Ключові ризики Lambda

  • Ін'єкції через event-дані (SQL, NoSQL, Command)
  • Надмірні права IAM у execution role
  • Секрети в змінних середовища (env vars)
  • Залежності зі вразливостями в пакетах
  • Event injection через API Gateway, SQS

✅ Безпечна Lambda

import boto3, json, os

def handler(event, context):
    # Валідація вхідних даних
    user_id = event.get("userId", "")
    if not user_id.isalnum():
        return {"statusCode": 400,
                "body": "Invalid input"}

    # Секрети — з Secrets Manager
    secret = get_secret("prod/db/password")

    # Принцип найменших привілеїв
    # Execution Role має лише потрібні права
    return {"statusCode": 200}

Управління секретами у хмарних сервісах

🔑 AWS Secrets Manager

  • Зберігання паролів, ключів, токенів
  • Автоматична ротація (RDS, Redshift, DocumentDB)
  • Інтеграція з IAM (fine-grained access)
  • Audit через CloudTrail
  • Реплікація між регіонами

📋 SSM Parameter Store

  • Безкоштовний для Standard tier
  • SecureString = зашифровано KMS
  • Ієрархічна структура параметрів
  • Підходить для конфігурацій (не тільки секретів)

❌ Де НЕ зберігати секрети

Container Escape — як це відбувається

🔓 Вектори виходу з контейнера

1. Privileged Container

# Атаки через монтування хост-ФС
docker run --privileged ubuntu \
  bash -c "mkdir /mnt/host && \
  mount /dev/xvda1 /mnt/host && \
  chroot /mnt/host"

2. Docker socket mount

docker run -v /var/run/docker.sock:/var/run/docker.sock \
  ubuntu docker run --privileged ...

🛡️ Засоби захисту

  • seccomp — блокує небезпечні syscalls
  • AppArmor — профілі доступу до ФС
  • SELinux — мандатний контроль доступу
  • gVisor — додаткове ядро-пісочниця (Fargate)
  • Kata Containers — VM-ізоляція для контейнерів
CVE-2019-5736 (runc) — приклад критичної вразливості container escape через перезапис runc бінарника. Патч вийшов за 24 год.

🔍 AWS-нативні інструменти

🦅 Falco — runtime security

Open Source runtime security для K8s і контейнерів

# Правило Falco: shell у контейнері
- rule: Terminal shell in container

  condition: >
    container and
    proc.name in (bash, sh, zsh) and

  output: >
    Shell in container

Кращі практики безпеки обчислювальних сервісів

🖥️ EC2

  • Systems Manager замість SSH (без відкритого 22)
  • IMDSv2 обов'язково
  • Patch Management через AWS SSM
  • Amazon Inspector для CVE-моніторингу
  • Мінімальні IAM Instance Profile права

🐳 Контейнери (ECS/EKS)

  • Multi-stage Dockerfile, мінімальний базовий образ
  • Non-root, read-only FS, drop capabilities
  • Приватний ECR + автосканування
  • IRSA замість статичних ключів
  • Network Policy: default deny

⚡ Lambda / Serverless

  • Execution Role з мінімальними правами
  • Валідація всіх вхідних даних
  • Secrets Manager, не ENV vars
  • VPC + Security Group для ізоляції
  • X-Ray для трасування та аудиту

🔍 Загальне

  • Шифрування даних (KMS) у стані спокою і в русі
  • GuardDuty + Security Hub + CloudTrail
  • Автоматизовані Compliance-перевірки (AWS Config)
  • Резервне копіювання та disaster recovery

Ключові концепції

  • Модель спільної відповідальності залежить від рівня сервісу (EC2 → Lambda)
  • Контейнери ≠ повна ізоляція — shared kernel = спільний ризик
  • Non-root, read-only FS, drop capabilities — базові заходи
  • IMDSv2 захищає IAM-credentials від SSRF
  • IRSA/Task Role — без статичних ключів у контейнерах
  • Secrets Manager / SSM — жодних секретів у коді
  • Сканування образів — обов'язкова частина CI/CD
  • Network Policy: default deny → явний allow
