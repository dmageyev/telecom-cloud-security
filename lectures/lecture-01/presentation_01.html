🔐 Confidentiality (Конфіденційність)

Визначення:

Інформація доступна лише авторизованим особам

Механізми захисту:

  • 🔐 Шифрування (at rest, in transit)
  • 🔑 Контроль доступу (IAM)
  • 🕵️ Класифікація даних
  • 🔒 MFA (Multi-Factor Authentication)

❌ Приклад порушення:

Публічний S3 bucket з персональними даними абонентів телеком-оператора

✅ Integrity (Цілісність)

Визначення:

Дані точні, повні та не змінені несанкціоновано

Механізми захисту:

  • ✅ Хешування (SHA-256, SHA-3)
  • ✅ Цифрові підписи
  • ✅ Контроль версій
  • ✅ Логування змін (audit trail)

❌ Приклад порушення:

Man-in-the-Middle атака на API телеком-оператора → зміна тарифних планів

⚡ Availability (Доступність)

Визначення:

Системи та дані доступні за потреби

Механізми захисту:

  • ⚡ Резервування (redundancy)
  • ⚡ Балансування навантаження
  • ⚡ DDoS-захист (AWS Shield)
  • ⚡ Backup & Recovery (RPO/RTO)

❌ Приклад порушення:

DDoS атака на DNS-провайдера Dyn (2016) → недоступність Netflix, Twitter, Reddit

📡 CIA у телекомунікаціях — приклади

Принцип Телеком-приклад Механізм
C Шифрування дзвінків TLS, SRTP, VoLTE encryption
I Цілісність SMS Підпис повідомлень, HMAC
A 99.999% uptime (5 nines) Geographic redundancy, failover

⚔️ Що таке STRIDE?

Microsoft Threat Modeling Framework

Систематичний підхід до аналізу загроз

STRIDE = 6 категорій загроз:

S Spoofing (підробка ідентичності)

T Tampering (втручанн�� в дані)

R Repudiation (відмова від дій)

I Information Disclosure (розголошення)

D Denial of Service (відмова в обслуговуванні)

E Elevation of Privilege (підвищення привілеїв)

🎭 S — Spoofing (Підробка ідентичності)

Загроза:

Атакуючий видає себе за легітимного користувача/систему

📞 Телеком-приклади:

  • Caller ID spoofing (підробка номера)
  • SIM swapping (перевипуск SIM-карти)
  • Фальшиві базові станції (IMSI catchers / Stingrays)
  • Email spoofing з доменом оператора

✅ Захист:

  • Сильна автентифікація (MFA)
  • Взаємна автентифікація (mutual TLS)
  • Certificate pinning
  • STIR/SHAKEN для телефонії

🔧 T — Tampering (Втручання в дані)

Загроза:

Несанкціонована модифікація даних або коду

📊 Приклади:

  • Зміна тарифів у біллінговій системі
  • Модифікація пакетів у мережі (MITM)
  • Injection атаки (SQL, NoSQL, Command)
  • Зміна CDR (Call Detail Records)

✅ Захист:

  • Цифрові підписи
  • Immutable infrastructure
  • Input validation & sanitization
  • File integrity monitoring (FIM)

🙈 R — Repudiation (Відмова від дій)

Загроза:

Неможливість довести, хто виконав дію

💬 Приклади:

  • "Це не я надсилав той SMS"
  • "Я не змінював конфігурацію файрволу"
  • "Я не здійснював цього дзвінка"

✅ Захист:

  • Детальне логування (AWS CloudTrail)
  • Non-repudiation (цифрові підписи з timestamps)
  • Audit trails (незмінні журнали)
  • Timestamp services (TSA)
  • Video/audio recording (з юридичною силою)

📢 I — Information Disclosure (Розголошення)

Загроза:

Неавторизований доступ до конфіденційної інформації

🗂️ Приклади:

  • Публічний S3 bucket з даними абонентів
  • Витік CDR (Call Detail Records)
  • Verbose error messages (інформація про систему)
  • SS7 перехоплення SMS з OTP

✅ Захист:

  • Шифрування (at rest + in transit)
  • Правильна конфігурація ACL/Security Groups
  • Data Loss Prevention (DLP)
  • Класифікація та маркування даних

💥 D — Denial of Service (Відмова в обслуговуванні)

Загроза:

��истема недоступна для легітимних користувачів

🌊 Приклади:

  • DDoS на SIP-сервер (SIP INVITE flood)
  • Flood атака на API billing системи
  • Resource exhaustion (CPU/Memory/Bandwidth)
  • DNS amplification attacks

✅ Захист:

  • Rate limiting / Throttling
  • AWS Shield (Standard + Advanced)
  • Auto-scaling
  • Circuit breakers
  • CDN (CloudFront) для розподілу навантаження

⬆️ E — Elevation of Privilege (Підвищення привілеїв)

Загроза:

Отримання прав вище дозволених

👑 Приклади:

  • Експлуатація вразливості для root доступу
  • IAM misconfiguration → admin доступ в AWS
  • Container escape → доступ до host OS
  • Privilege escalation через SUID binaries

✅ Захист:

  • Principle of Least Privilege (PoLP)
  • Regular security patching
  • Vulnerability scanning
  • SELinux / AppArmor
  • IAM Access Analyzer

⚖️ SRM — залежність від сервісу

Рівень відповідальності змінюється:

Сервіс Тип Відповідальність клієнта
EC2 IaaS OS, apps, data, network config, patching
RDS PaaS Data, IAM, network config (no OS patching)
S3 SaaS Data, bucket policies, encryption settings
Lambda FaaS Code, IAM roles (no infrastructure)

🎯 Золоте правило:

↑ Більше керованості AWS → ↑ Відповідальність AWS

↑ Більше контролю клієнта → ↑ Відповідальність клієнта

❌ Типові помилки SRM

Топ-5 непорозумінь:

1. "AWS захистить мої дані"

→ ❌ Ні, потрібно увімкнути шифрування та налаштувати доступ

2. "Security Groups = автоматичний firewall"

→ ❌ Так, але їх треба ПРАВИЛЬНО налаштувати

3. "AWS автоматично патчить мій EC2"

→ ❌ Ні, це ВАША відповідальність (використайте Systems Manager)

4. "IAM складно, дам всім AdministratorAccess"

→ ❌ Це катастрофа! Використовуйте Least Privilege

5. "Compliance AWS = мій compliance"

→ ❌ Ні, треба власні контролі та документацію

💥 Кейс 1: Capital One (2019)

Інцидент:

  • Витік даних 106 мільйонів клієнтів
  • Дані з AWS S3 buckets
  • Атакуючий: колишній співробітник AWS

🔍 Причина:

  • ❌ Misconfigured web application firewall (WAF)
  • ❌ IAM role з надмірними правами (ec2:DescribeInstances + S3 full access)
  • ❌ SSRF вразливість у веб-додатку

⚖️ Порушення SRM:

Клієнт Неправильна конфігурація WAF, надмірні IAM привілеї

AWS Інфраструктура працювала коректно

💰 Наслідок: $80M штраф від регуляторів + $190M settlement

🔍 Аналіз Capital One через STRIDE
