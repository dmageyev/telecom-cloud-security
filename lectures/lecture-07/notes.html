1. Ландшафт загроз веб-застосунків

1.1 Масштаб проблеми

Веб-застосунки є найпоширенішим вектором атак у сучасному цифровому світі. За даними Verizon DBIR 2024, 43% усіх підтверджених зломів безпосередньо пов'язані з вразливостями веб-застосунків. IBM Cost of a Data Breach Report фіксує середню вартість одного інциденту — $4.45 млн у 2023 році.

Тип атакиЧастка інцидентівТренд
Injection attacks (SQL, XSS, Command)32%↔ Стабільно
API abuse21%↑ Зростає
Broken Authentication18%↔ Стабільно
DDoS на веб-рівень (L7)16%↑ Зростає
Supply chain / 3rd-party13%↑ Зростає

1.2 Поверхня атаки веб-застосунку

Кожен елемент веб-застосунку є потенційним вектором атаки:

  • Вхідні дані: форми реєстрації, GET/POST параметри, HTTP заголовки, cookies, JSON/XML тіло
  • API endpoints: REST, GraphQL (особлива складність через introspection), SOAP, WebSocket
  • Залежності: npm/pip/Maven пакети, CDN-вбудований JavaScript (Supply Chain атаки)
  • Інфраструктура: конфігурація nginx/Apache, дефолтні помилки (stack trace), відкриті адмін-інтерфейси
Телеком-специфіка: BSS/OSS-портали (білінг, управління), OAM-інтерфейси, 5G NF REST API (SBI), між-операторські API роумінгу — значно розширена поверхня атаки.

2. OWASP Top 10 (2021) — деталі

2.1 A01: Broken Access Control

Найпоширеніша категорія у 2021 році. Система не коректно обмежує, що дозволено робити автентифікованим користувачам.

IDOR (Insecure Direct Object Reference): endpoint /api/invoices/1042 повертає рахунок поточного користувача. При зміні ID на 1041 — повертаються дані іншого клієнта. Захист: перевірка на backend — чи належить ресурс поточному user.
  • Вертикальна ескалація: звичайний user отримує доступ до адміністративних функцій
  • Горизонтальна ескалація: доступ до ресурсів іншого user того самого рівня
  • Захист: Deny by default, RBAC/ABAC, UUID замість integer ID, централізована авторизація

2.2 A03: Injection

SQL Injection актуальна понад 25 років. Атакуючий вводить шкідливий SQL-код у поле введення.

-- Атака: обхід аутентифікації
SELECT * FROM users WHERE login = 'admin' OR '1'='1' -- ' AND password = '...'
-- Результат: умова завжди true, login='admin' OR '1'='1'
Захист: Параметризовані запити (Prepared Statements) — основний захист. ORM (SQLAlchemy, Hibernate). Whitelist валідація. Мінімальні права БД-акаунту.

2.3 A02: Cryptographic Failures

  • Зберігання паролів у MD5 або SHA-1 — занадто швидкі для брутфорсу
  • Передача sensitive даних по HTTP (plaintext)
  • Хардкодовані ключі та секрети у git
  • Застарілі алгоритми: DES, RC4, ECB
Правильне хешування паролів: bcrypt (cost factor ≥ 12), Argon2id (рекомендований NIST SP 800-63B), scrypt.
Шифрування: AES-256-GCM (AEAD), ChaCha20-Poly1305.

2.4 A07: Authentication Failures та JWT

Credential Stuffing: автоматизоване тестування пар login/password з витоків інших сервісів. 52-65% користувачів повторно використовують паролі.

JWT-специфічні вразливості:
  • alg: none — прийняття токенів без підпису
  • Algorithm confusion: підміна RS256 на HS256
  • Відсутність перевірки iss, aud, exp

3. Специфічні атаки: XSS, CSRF, SSRF

3.1 XSS — Cross-Site Scripting

XSS дозволяє атакуючому виконати JavaScript у браузері жертви в контексті довіреного сайту. Наслідки: крадіжка cookies/токенів, кейлоггінг, redirect.

ТипМеханізмНебезпека
Reflected XSSPayload у запиті відображається у відповідіОдин запит — одна жертва
Stored XSSPayload зберігається в БД, виконується у всіхОдин запит — тисячі жертв
DOM-based XSSМаніпуляція DOM без взаємодії з серверомСкладно виявити DAST
Захист: Output encoding (HTMLentities), Content Security Policy (CSP), HTTPOnly cookie, DOMPurify, сучасні фреймворки (React auto-escape).

3.2 CSRF — Cross-Site Request Forgery

Атака змушує браузер жертви відправити автентифікований запит до цільового сайту без відома користувача. Браузер автоматично додає cookies.

<!-- evil.com — CSRF атака: -->
<img src="https://bank.com/transfer?to=attacker&amount=10000">
Захист: CSRF Token у кожній формі. SameSite=Strict cookie. Double Submit Cookie. Origin/Referer перевірка.

3.3 SSRF — Server-Side Request Forgery

Атакуючий змушує сервер виконати HTTP-запит до внутрішнього ресурсу.

Capital One (2019): SSRF через вразливий WAF → IMDS (169.254.169.254) → IAM credentials → завантаження 100 млн записів з S3. 
# Атака: SSRF до AWS IMDS
GET /fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/
# Відповідь: AWS credentials (AccessKeyId, SecretAccessKey, Token)
Захист: Whitelist дозволених URL. Блокування RFC 1918 діапазонів після резолвінгу. IMDSv2 обов'язковий. Egress filtering через Security Groups.

4. Аутентифікація та API Security

4.1 OAuth 2.0 та PKCE

OAuth 2.0 — фреймворк авторизації. Authorization Code + PKCE — єдиний рекомендований flow для веб та мобільних застосунків:

  1. Client генерує code_verifier (random) та code_challenge = SHA256(code_verifier)
  2. Redirect до Authorization Server з code_challenge
  3. AS повертає authorization_code
  4. Client обмінює code + code_verifier на access_token
  5. PKCE захищає від перехоплення authorization_code
Deprecated flows: Implicit — не використовувати. Resource Owner Password — небезпечний.

5. Транспортна безпека та HTTP-заголовки

5.1 TLS 1.3 — ключові покращення

  • 1-RTT Handshake (замість 2-RTT) — менша затримка
  • Видалено небезпечні cipher suites: RSA key exchange, MD5, SHA-1, RC4, CBC
  • Forward Secrecy обов'язкова — ECDHE для всіх cipher suites
  • Тільки 3 cipher suites: AES-128-GCM-SHA256, AES-256-GCM-SHA384, ChaCha20-Poly1305-SHA256
# Nginx — безпечна конфігурація TLS:
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
ssl_stapling on;
ssl_stapling_verify on;

6. Безпека телекомунікаційних веб-застосунків

6.1 SIP — специфіка та атаки

SIP (RFC 3261) — текстовий протокол, синтаксично схожий на HTTP. Веб-вразливості ін'єкцій транслюються у SIP-контекст.

Session Border Controller (SBC) — ключовий елемент захисту: topology hiding, сигнальний firewall, rate limiting, DoS-захист, NAT traversal.
АтакаМеханізмЗахист
SIP FloodingТисячі INVITE → вичерпання ресурсів ProxySBC rate limiting
Registration HijackingПерехоплення REGISTER → redirect дзвінківSIPS (SIP over TLS) + Digest Auth
Toll FraudНесанкціоновані дзвінки на преміум-номериCountry whitelist, anomaly detection
EavesdroppingПерехоплення RTP-медіа без шифруванняSRTP (Secure RTP)
BYE InjectionПередчасне завершення чужого дзвінкаSBC topology hiding, SIP auth

6.2 5G Service-Based Architecture (SBA)

У 5G всі мережеві функції (NF) взаємодіють через HTTP/2 + JSON — Service-Based Interface (SBI).

NFФункціяAPI Prefix
AMFУправління доступом та мобільністюNamf_*
SMFУправління PDU-сесіямиNsmf_*
UDMДані абонентів (subscription)Nudm_*
NRFРеєстр NF, OAuth 2.0 ASNnrf_*
NEFNetwork Exposure (CAMARA API gateway)Nnef_*
3GPP TS 33.501 — вимоги: TLS 1.2+ для всіх SBI. OAuth 2.0 Client Credentials для NF-to-NF. mTLS для N32 (між операторами). PRINS — шифрування roaming API.

6.3 SS7 — Legacy загрози

SS7 атаки (протокол 1975 р., без аутентифікації):
  • Location Tracking: SendRoutingInfo → знайти абонента
  • SMS Interception: перехоплення SMS OTP → обхід 2FA
  • Call Forwarding: несанкціоноване перенаправлення дзвінків
NIST SP 800-63B рекомендація: уникати SMS як єдиного фактора MFA для критичних систем через SS7-вразливість.
Захист (GSMA FS.11): SS7 Firewall з Category 1 (блокування), Category 2 (обмеження), Category 3 (аномалій-детекція). ML-моніторинг патернів сигналізації.

7. Mobile App Security (OWASP Mobile Top 10)

7.1 Зберігання даних

Android insecure storage: SharedPreferences без encryption, SQLite без SQLCipher, logcat leak (debug builds), external storage (SD card).
Android Keystore System — ключі в TEE/SE, недоступні навіть root. EncryptedSharedPreferences (Jetpack Security) — прозоре шифрування.
iOS Keychain: kSecAttrAccessibleWhenUnlockedThisDeviceOnly, Secure Enclave для приватних ключів, App Transport Security (HTTPS enforcement).

7.2 Certificate Pinning

Застосунок перевіряє конкретний сертифікат або публічний ключ сервера, а не тільки ланцюжок CA.

<!-- Android Network Security Config -->
<network-security-config>
  <domain-config>
    <domain includeSubdomains="true">api.example.com</domain>
    <pin-set>
      <pin digest="SHA-256">base64encodedPublicKeyHash==</pin>
    </pin-set>
  </domain-config>
</network-security-config>
Ризик: Якщо сертифікат ротується без оновлення застосунку — сервіс ламається. Рекомендація: pinning публічного ключа (не сертифіката) + backup pin.

13. Архітектура Defence in Depth

13.1 Принципи

  • Least Privilege: кожен компонент — мінімально необхідні права
  • Fail Secure: при помилці — заборона, не дозвіл
  • Separation of Concerns: ізольовані компоненти з мінімальними inter-service правами
  • Zero Trust: "Never trust, always verify" — навіть між мікросервісами

13.2 Архітектура захищеного телеком-порталу в AWS

  1. Route 53 + GeoDNS (обмеження за географією)
  2. CloudFront + TLS 1.3 + WAF (OWASP CRS + Bot Control)
  3. AWS Cognito + MSISDN-based auth + TOTP MFA
  4. ALB + access logs → S3
  5. ECS Fargate — non-root, read-only filesystem
  6. API Gateway + Lambda Authorizer (JWT validation)
  7. RDS Aurora — приватна підмережа, KMS encryption
  8. Secrets Manager — автоматична ротація credentials
  9. GuardDuty + Security Hub + CloudTrail — повний audit trail

14.2 Top-10 рекомендацій для телеком-оператора

  1. Замінити SMS OTP на TOTP або FIDO2 — захист від SS7-атак на 2FA
  2. SBC обов'язковий — rate limiting, topology hiding, Toll Fraud prevention
  3. SS7 Firewall (категорії 1-3) на всіх SS7-підключеннях
  4. 5G SBA: TLS + OAuth 2.0 між всіма NF (3GPP TS 33.501)
  5. CAMARA API: consent + rate limiting + OAuth 2.0 + PKCE
  6. WAF перед OAM-порталами — адмін-інтерфейси критичні
  7. IMDSv2 обов'язковий на всіх EC2 (захист від SSRF)
  8. Network Segmentation: BSS/OSS у приватних підмережах
  9. DevSecOps Pipeline з SAST/DAST для всього ПЗ
  10. Incident Response Plan для веб: playbooks для SQLi, DDoS, account takeover
🏆 Ключова думка лекції: Безпека — це не продукт, що купується одноразово, а безперервний процес: тестування, моніторинг, реагування та покращення. Shift-Left у SDLC, DevSecOps культура та Security Champions у кожній команді — організаційний фундамент технічної безпеки.
