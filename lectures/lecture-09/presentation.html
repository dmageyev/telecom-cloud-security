🎯 Цілі DDoS-атак

  • Вимагання (Ransom DDoS) — "заплати або ми продовжимо"

Класифікація DDoS-атак за моделлю OSI

📐 Три категорії атак

КатегоріяРівень OSIМетаПриклади
Об'ємніL3/L4Переповнення каналаUDP Flood, ICMP Flood
ПротокольніL3/L4Виснаження ресурсів стекаSYN Flood, Ping of Death
ПрикладніL7Виснаження вебсерверуHTTP Flood, Slowloris

🌊 Об'ємні атаки — деталі

  • UDP Flood — тисячі UDP-пакетів на довільні порти
  • ICMP Flood — масові ping-запити (smurf attack)
  • Amplification — підсилення за допомогою сторонніх серверів
  • Вимірюється в Gbps / Tbps (bits per second)

🔧 Протокольні атаки

  • SYN Flood — надсилання SYN без завершення handshake → переповнення half-open connection table
  • ACK Flood — масові ACK для завантаження TCP стеку
  • Fragmented packets — IP-фрагменти що не збираються
  • Вимірюється в PPS (packets per second)

🌐 Прикладні атаки L7

  • HTTP GET/POST Flood — легітимні запити у великій кількості
  • Slowloris — тримати з'єднання відкритими нескінченно
  • ReDoS — складні regexp що блокують CPU
  • Cache bypass — унікальні URL для обходу кешу
  • Вимірюється в RPS (requests per second)

Amplification-атаки — підсилення трафіку

📡 Принцип Amplification

  • Атакуючий надсилає малий запит із підробленим src IP (жертви)
  • Відкритий сервіс відповідає великою відповіддю до жертви
  • Коефіцієнт підсилення (BAF) = розмір відповіді / розмір запиту
ПротоколBAFПортМеханізм
DNS×28–5453/UDPANY query → large response
NTP×556123/UDPmonlist команда
Memcached×51,20011211/UDPget key → cache dump
SSDP×301900/UDPUPnP discovery
CLDAP×70389/UDPLDAP search
QUIC×20443/UDPInitial packet

🔐 Захист від Amplification

  • BCP38 (Network Ingress Filtering) — ISP не пропускає пакети з підробленими src IP
  • Response Rate Limiting (RRL) — DNS-сервери обмежують відповіді
  • Закрити UDP-сервіси — Memcached, NTP monlist недоступні з Інтернету
  • AWS Shield Advanced — автоматично виявляє та блокує amplification
💡 Memcached 2018: рекордна на той час атака 1.7 Tbps проти GitHub — один Memcached сервер надіслав ×51,200 трафіку. Після цього AWS та Cloudflare заблокували UDP/11211 за замовчуванням

  • Bots (Zombies) — заражені пристрої (IoT, сервери, ПК)
  • Command & Control (C2) — IRC, HTTP, P2P, Tor, DGA

💰 DDoS-as-a-Service (Booter/Stresser)

  • Нелегальні сервіси в darknet від $5–$200/год
  • "Легальні" IP Stresser — позиціонуються як тести навантаження
  • Не потрібні технічні знання — вибрати ціль, оплатити криптовалютою
  • Доступні потужності: до 1 Tbps "на замовлення"
⚠️ HTTP/2 Rapid Reset (CVE-2023-44487): критична вразливість дозволяла зловживати механізмом скасування потоків. Кілька ботів могли генерувати 398 мільйонів запитів/с. AWS, Google, Cloudflare одночасно виявили атаку та нашили патчі

🛡️ IoT DDoS — вектор атаки

  • Мільярди незахищених IoT-пристроїв (камери, роутери)
  • Telnet/SSH з дефолтними паролями → Mirai-подібні ботнети
  • AWS IoT Device Defender — моніторинг аномалій IoT

Layer 7 атаки — Slowloris та HTTP Flood

🐌 Slowloris Attack

  • Відкриває багато з'єднань і надсилає заголовки дуже повільно
  • Сервер чекає завершення запиту → connection pool вичерпується
  • Потрібен один звичайний комп'ютер (не ботнет!)
  • Особливо ефективний проти Apache (thread-per-connection)
# Slowloris: надсилаємо заголовок кожні 10 сек
GET / HTTP/1.1\r\n
Host: target.com\r\n
X-Custom-Header-1: ...\r\n
# (очікуємо, не надсилаємо \r\n\r\n)
# Повторюємо для тисяч з'єднань паралельно

🛡️ Захист від Slowloris

  • RequestReadTimeout в Apache/nginx
  • Обмеження LimitRequestFields
  • AWS WAF: Connection timeout rules, rate limiting
  • nginx event-driven модель стійкіша за Apache

🌊 HTTP Flood

  • Simple HTTP flood — масові GET/POST на одну сторінку
  • Cache-bypass flood — унікальний параметр (?=rand) для обходу CDN
  • POST body flood — масові POST з великим body (форми, API)
  • Важко відрізнити від легітимних користувачів

DDoS у телекомунікаційних мережах

📡 SIP/VoIP DDoS

  • INVITE Flood — масові SIP INVITE → виснаження SBC
  • REGISTER Flood — масові реєстрації → перевантаження реєстратора
  • OPTIONS Flood — ping-like атака на SIP сервери
  • BYE Flood — примусово розриває активні дзвінки
  • Захист: SBC rate-limiting, fail2ban, ACL за IP/ASN

🔴 SS7 DoS-атаки

  • MAP Cancel Location — деавторизація абонента
  • MAP Insert Subscriber Data — підміна профілю
  • SCCP flooding — перевантаження Signal Transfer Point
  • Наслідок: абонент недоступний (DoS), не може дзвонити

📊 Специфіка захисту телеком-оператора

🌐 RTBH (Remotely Triggered Black Hole): оператор через BGP community повідомляє upstream про блокування IP жертви. Трафік відкидається ще на межі мережі провайдера. Ефективно при об'ємних атаках, але жертва також недоступна

Стратегії захисту від DDoS

🏗️ Рівні захисту (Defense in Depth)

  • ISP/Upstream — RTBH, Flowspec, scrubbing на магістралі
  • CDN/Anycast — розподіл трафіку по PoP, поглинання об'єму
  • DNS layer — DNS failover, geo-routing, rate limit
  • Network perimeter — BGP communities, SYN cookies, rate limiting
  • Load Balancer — connection limits, SYN proxy
  • WAF — Layer 7 фільтрація, challenge (CAPTCHA/JS)
  • Application — caching, queue-based processing, circuit breaker

AWS Shield — захист від DDoS

🛡️ AWS Shield Standard

  • Безкоштовно для всіх AWS-клієнтів
  • Захист від найпоширеніших Layer 3/4 атак
  • SYN/UDP Flood, Reflection attacks — автоматично
  • Захищає: CloudFront, Route 53, ELB, Global Accelerator
  • Нульова настройка — вмикається автоматично

🛡️🛡️ AWS Shield Advanced

  • $3,000/міс + data transfer fees (або Enterprise Support)
  • Захист Layer 3/4 та Layer 7 (з WAF)
  • DDoS Response Team (DRT) — 24/7 підтримка від AWS
  • Cost Protection — компенсація витрат під час атаки
  • Advanced diagnostics — детальна телеметрія атаки
  • Proactive engagement — DRT сам ескалює великі атаки

⚙️ Terraform: WAF Web ACL + Rate Limiting

resource "aws_wafv2_web_acl" "main" {
  name  = "main-waf"
  scope = "CLOUDFRONT"

  default_action { allow {} }

  # Rate limiting: 2000 req/5min per IP
  rule {
    name     = "RateLimitPerIP"
    priority = 1
    action { block {} }
    statement {
      rate_based_statement {
        limit              = 2000
        aggregate_key_type = "IP"
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      metric_name                = "RateLimit"
      sampled_requests_enabled   = true
    }
  }

  # AWS Managed Rules
  rule {
    name     = "CommonRules"
    priority = 2
    override_action { none {} }
    statement {
      managed_rule_group_statement {
        vendor_name = "AWS"
        name = "AWSManagedRulesCommonRuleSet"
      }
    }
  }
}

📊 WAF Logging та аналіз

  • WAF логи → Kinesis Firehose → S3
  • Аналіз в Athena або OpenSearch
  • Кожен лог: IP, URI, правило що спрацювало, action
-- Athena: топ правил що спрацювали за 24 год
SELECT terminatingruleid,
       count(*) as blocked_requests
FROM waf_logs
WHERE action = 'BLOCK'
  AND timestamp > to_unixtime(
    current_timestamp - interval '1' day
  ) * 1000
GROUP BY terminatingruleid
ORDER BY blocked_requests DESC
LIMIT 20;

AWS CloudFront — CDN та захист на периметрі

🌐 CloudFront як засіб захисту

  • 450+ PoP по всьому світу — розподіл трафіку
  • Anycast routing — трафік іде до найближчого PoP
  • Поглинає об'ємні атаки: ємність мережі >1 Tbps
  • Origin Shield — зменшує навантаження на origin
  • Shield Standard вбудований безкоштовно
  • Приховує реальний IP-адресу origin-сервера
  • HTTPS termination на PoP → розвантаження TLS

Route 53 — DNS failover та висока доступність

🌐 Route 53 як засіб HA

  • Anycast DNS — 100% SLA від AWS, розподілено глобально
  • Health Checks — моніторинг endpoint кожні 10–30 сек
  • Failover routing — автоматичний перехід на резервний
  • Latency routing — до найближчого регіону
  • Geolocation routing — за місцем користувача
  • Weighted routing — A/B тестування, поступовий rollout

Auto Scaling — еластичність під DDoS-навантаженням

📈 Auto Scaling для поглинання DDoS

  • Горизонтальне масштабування під час атаки — absorb тактика

  • Рішення: WAF блокує до Auto Scaling → масштабуємо легітимний трафік

DDoS Response Plan — план реагування

📋 Фази реагування на DDoS

  1. Виявлення (Detect): CloudWatch алерти, Хвилина 0
  2. Класифікація (Classify): L3/L4 vs L7, volumetric vs app
  3. Ескалація: Notify SOC + AWS DRT (якщо Shield Advanced)
  4. Митигація (Mitigate): WAF rules, rate limits, geo-block
  5. Моніторинг: відстеження ефективності mitigation
  6. Відновлення: перевірка нормальної роботи
  7. Post-mortem: аналіз, покращення захисту

⚡ Runbook: Автоматична реакція на DDoS

# Lambda: автоматична реакція на DDoS алерт
def respond_to_ddos(event, context):
    waf = boto3.client('wafv2')
    cw  = boto3.client('cloudwatch')

    # 1. Отримати топ-IP за 15 хв
    top_ips = get_top_attackers_from_logs(15)

    # 2. Додати до WAF IP Set блокування
    waf.update_ip_set(
        Id=os.environ['BLOCK_IPSET_ID'],
        Name='DDoS-Block-List',
        Scope='CLOUDFRONT',
        Addresses=top_ips,
        LockToken=get_lock_token()
    )

    # 3. Знизити WAF rate limit тимчасово
    waf.update_rate_based_statement(
        limit=500  # з 2000 до 500
    )

    # 4. Увімкнути CloudFront challenge
    enable_js_challenge_for_all_requests()

    # 5. Сповістити SOC
    notify_soc(f"DDoS mitigation applied.
               {len(top_ips)} IPs blocked.")

Захист DNS-інфраструктури від DDoS

🌐 DNS як ціль та інструмент DDoS

  • DNS DDoS (як ціль): перевантажити DNS-сервер → домен недоступний
  • DNS Amplification (як інструмент): відкриті резолвери → ×28–54 підсилення
  • DNS Hijacking: підміна відповідей для редиректу трафіку
  • NXDOMAIN flood: масові запити неіснуючих доменів

🛡️ Захист DNS

  • Anycast DNS (Route 53) — розподілена відмовостійкість
  • DNSSEC — підпис зон, захист від підміни
  • Закрити recursive resolver від зовнішнього доступу
  • Response Rate Limiting (RRL) на авторитативних серверах

🔍 Synthetic Monitoring

  • CloudWatch Synthetics — canary scripts (Playwright/Puppeteer)
  • Перевіряє end-to-end user journey кожні 1–5 хв
  • Тест: login → order → checkout → підтвердження
  • Сповіщення до CloudWatch → SNS → PagerDuty

⚙️ CloudWatch Synthetics Canary

resource "aws_synthetics_canary" "checkout" {
  name          = "checkout-flow-canary"
  artifact_s3_location =
    "s3://${aws_s3_bucket.canary.bucket}/"
  execution_role_arn =
    aws_iam_role.canary.arn
  runtime_version = "syn-nodejs-puppeteer-7.0"
  handler         = "checkout.handler"

  schedule {
    expression = "rate(5 minutes)"
  }

  run_config {
    timeout_in_seconds = 120
    active_tracing     = true
  }
}

# Alarm на Canary failure
resource "aws_cloudwatch_metric_alarm"
    "canary_fail" {
  alarm_name  = "CheckoutCanaryFailed"
  namespace   = "CloudWatchSynthetics"
  metric_name = "SuccessPercent"
  dimensions  = {
    CanaryName = "checkout-flow-canary"
  }
  threshold   = 90
  alarm_actions = [aws_sns_topic.ops.arn]
}

Практичний кейс: DDoS-атака на телеком-портал

📖 Сценарій атаки

  1. D-Day 14:00: Конкурент запустив HTTP flood через ботнет — 500K RPS на портал самообслуговування
  2. 14:01: CloudWatch Alarm — ALB RequestCount >100K/хв
  3. 14:02: Shield Advanced виявляє аномалію → GuardDuty finding
  4. 14:03: EventBridge → Lambda → WAF Rate Limit знижено до 500 req/5min/IP
  5. 14:05: 95% трафіку заблоковано WAF. Решта (legitimate) — проходить
  6. 14:10: AWS DRT підключається, аналізує патерн
  7. 14:15: DRT додає сигнатурне правило WAF → блок 99.9% атаки

  • ☑ Тестування щоквартально (FIS + load test)

🏆 Best Practices

  • Завжди CDN → WAF → ALB → EC2 (ніколи EC2 напряму)
  • Мінімум 2 AZ для всіх компонентів
  • Shield Advanced для production workloads
  • Pre-configure WAF rules до атаки (не під час)
  • Тестуй failover — щоквартально Game Day
  • CloudFront Origin Shield — захист origin від прямих атак
  • DNSSEC для захисту DNS від підміни
  • Автоматизуй відповідь — MTTR хвилини, не години
